# ai-badger Contribution Workflow

How to add features to the ai-badger framework — stacks, agents, skills,
personas, invariants, instructions, task extensions — with TDD, CI checks,
and the release model.

## Architecture (must know before touching code)

ai-badger is a **stack × feature catalog** under `features/{stack}/{feature}/`:

- **stack** — a technology: `dotnet`, `react`, `python`, `hermes`, `common`
- **feature** — a kind of asset: `personas`, `invariants`, `instructions`,
  `templates` (common-only), `skills` (in-repo + external), `hooks`,
  `adjustments` (agent-level)

Installable operational skills (`welcome-ai-badger`, `feed-badger`, `den-refresh`,
`task`, etc.) live at `features/common/skills/` — agent-specific skills live at
`features/<agent>/skills/` (e.g. `features/claude/skills/auto-wm/`). All are
discovered by `iter_feature_dirs` like any other stack feature.

**External skills** (v0.7.0+): each stack can have `skills-source.json` (where
skills come from — type: marketplace/hub/tap/url/well-known, support: common or
per-agent array) and `skills.json` (which skills to install). Extension-only
stacks (e.g. github) use `{"skills": []}`. These replace the old `plugins/`
directory with `plugins.json` + `marketplaces.json`.

**Hooks** (v0.7.0+): `features/common/hooks/` contains `hooks-manifest.json`
mapping hooks to agents, plus hook implementation files (`.json` for Claude,
`.py` for Hermes). Replaces the old `hooks/` at repo root. `scaffold.py`'s
`wire_hooks()` reads this manifest and merges hook registrations into
`.claude/settings.json` with paths rewritten to `.ai-badger/skills/`.

**Scaffold `--execute` flag** (v0.8.0+): Runs collected install commands via
subprocess instead of just printing them. 30s timeout per command, failures
logged to notes without crashing. Default is advisory-only (prints commands).

**Adjustments** (v0.7.0+): `features/<agent>/adjustments/` contains
`adjustment.json` + per-feature scripts (e.g. `adjust_hooks.py`,
`adjust_task.py`) that run during scaffold. Default is nop. Replaces the old
agent-level `extension.json` pattern.

**Plugin instructions** (v0.7.0+): `features/<agent>/plugins-instructions.json`
declares how each agent installs external skills (commands with `{source}`,
`{name}`, `{scope}` placeholders). Agents with no plugin system (copilot, junie)
have empty instructions.

**Scaffolding.json**: each agent has a `features/<agent>/scaffolding.json` that
declares what files to scaffold (source, target, managed-header, template rendering).
`scaffold.py` reads these — no hardcoded fallback. Adding a new agent is a
data-only change: create `features/<agent>/stack.json` + `scaffolding.json`.

`index.json` is script-generated by `index_build.py` — never hand-edit it.

Read `docs/framework-architecture.md` and `docs/authoring-a-feature.md` before
starting.

## Worktree isolation

All contributions MUST happen in a git worktree, never in the main checkout:

```bash
cd /path/to/ai-badger
git worktree add ../ai-badger-<branch-slug> origin/main
cd ../ai-badger-<branch-slug>
git checkout -b <type>/<description>
```

Main checkout stays read-only. Clean up worktrees after merge:
`git worktree remove ../ai-badger-<branch-slug>`.

## Scaffolding declarative agent files

Each agent has a `features/<agent>/scaffolding.json` that declares what files to
write into the scaffolded project. `scaffold.py` reads these via
`_apply_scaffolding()` — no hardcoded fallback. The schema is at
`schemas/scaffolding.schema.json`.

### scaffolding.json fields

- `agent` — agent name (matches `features/<agent>/` and `config.agents`)
- `files[]` — array of file entries:
  - `source` — path relative to the feature dir
  - `target` — path in the scaffolded project
  - `managed` — true = framework overwrites on re-scaffold
  - `template` — true = render source as template with standard slots
  - `aibCopy` — optional .ai-badger/ source-of-truth path
  - `alsoTarget` — optional second target (e.g. .hermes.md alias)
  - `instructionsScoped` — true = write per-instruction copies (copilot)
  - `seedOnce` — true = written only on first scaffold

### Template rendering

When `template: true`, scaffold.py renders the source `.tmpl` file with standard
slots: `{{PROJECT_NAME}}`, `{{PROJECT_SUMMARY}}`, `{{INVARIANTS}}`,
`{{COMMANDS}}`, `{{PERSONA_ROUTING}}`, `{{PATH_INSTRUCTIONS}}`, `{{STACKS}}`,
`{{FRAMEWORK_VERSION}}`. Templates are symlinked from
`features/<agent>/templates/` to `features/common/templates/`.

### Adding a new agent

1. Create `features/<agent>/stack.json` with detection signals
2. Create `features/<agent>/scaffolding.json` declaring files to write
3. Create `features/<agent>/templates/` with symlinked templates
4. Add agent name to `schemas/config.schema.json` agents enum
5. Add agent name to `schemas/manifest.schema.json` agents enum
6. Add detection logic in `features/common/skills/welcome-ai-badger/scripts/detect.py`
7. Rebuild index: `python3 scripts/index_build.py`

## Adding a new agent (data-driven, no code changes in scaffold.py)

1. **Schema**: Add the agent name to `agents.items.enum` in
   `schemas/config.schema.json` AND `schemas/manifest.schema.json`.

2. **Detection**: Add detection logic in
   `features/common/skills/welcome-ai-badger/scripts/detect.py` → `detect_agents()`.

3. **Feature dir**: Create `features/<agent>/` with:
   - `stack.json` — detection signals, commands, description
   - `scaffolding.json` — declares files to write (see schema)
   - `templates/` — symlinked templates from `features/common/templates/`

4. **Template**: Create `features/common/templates/<AGENT>.md.tmpl` with
   agent-specific sections. Symlink from `features/<agent>/templates/`.

5. **Task extension**: Create
   `features/<agent>/skills/task-extensions/<agent>/` with `extension.json`
   and `extension.md`.

6. **Rebuild index**: `python3 scripts/index_build.py`

## Adding a new operational skill

1. **ADR**: Write an ADR in `docs/adr/` documenting the decision (follow
   ADR-0001 format).

2. **Tests first (TDD)**: Create `tests/test_<skill>.py`. Use the existing
   test patterns:
   - `tmp_path` for isolated directories
   - `load_script` fixture to import ai-badger modules
   - `root` fixture for the real framework repo path
   - Create mock frameworks with `_make_fw_file()` and `_write_fw_index()`
   - Create mock projects with `_write_config()` and `_write_manifest()`

3. **Script**: Create `features/common/skills/<name>/scripts/<name>.py` with:
   - `_bootstrap_lib()` for badger_lib discovery
   - `_load_script(relpath, base)` with fallback to script's own repo root
     (so mock frameworks in tests still work)
   - `main(argv)` accepting `--target` and `--root`
   - JSON output to stdout, exit codes: 0=success, 2=usage error

4. **SKILL.md**: Write `features/common/skills/<name>/SKILL.md` with:
   - YAML frontmatter: `name`, `description` with trigger phrases
   - Responsibility split (script vs agent)
   - Flow with exact commands
   - Rules and notes

5. **Wire into index**: `python3 scripts/index_build.py` — picks up the
   skill automatically if it has a `SKILL.md`.

## Adding a new stack

1. Create `features/<stack>/stack.json` with `description`, `detectionSignals`,
   `requires`, `commands`.

2. Add feature subdirectories: `personas/`, `invariants/`, `instructions/`,
   and optionally `skills-source.json` + `skills.json` (for external skills).

3. Run `index_build.py` + `validate.py --all`.

## Mock framework pattern for tests

When testing scripts that call scaffold/drift, create a minimal mock framework:

```python
fw = tmp_path / "fw"
fw.mkdir()
(fw / "VERSION").write_text("0.3.0\n", encoding="utf-8")
(fw / "schemas").mkdir()
# Copy the real config schema (needed for validation)
(fw / "schemas" / "config.schema.json").write_text(
    (root / "schemas" / "config.schema.json").read_text(encoding="utf-8"),
    encoding="utf-8",
)
# Create templates directory (NOT as a file!)
(fw / "features" / "common" / "templates").mkdir(parents=True)
# Write template files
(fw / "features" / "common" / "templates" / "CLAUDE.md.tmpl").write_text("...", encoding="utf-8")
# Write minimal index.json so Scaffolder can read it
_write_fw_index(fw)
```

**Pitfall**: `(fw / "path" / "CLAUDE.md.tmpl").mkdir(parents=True)` creates a
DIRECTORY at CLAUDE.md.tmpl, not a file. Always create the parent dir, then
write the file. This shows up as `IsADirectoryError` at runtime.

**Pitfall**: Mock frameworks lack `skills/` and `index.json`. Scripts that call
`_load_script()` must fall back to the real repo root when the mock framework
doesn't have the target script. Scripts that call `Scaffolder` need the mock
framework to have a minimal `index.json`.

## CI checks (run before pushing)

Always run these checks in order. **Pylint first** — CI runs it and will fail
the build on any warning, so run it locally before pushing to avoid a wasted
round trip.

```bash
# 0. Lint (CI runs pylint on non-test Python files — must be clean)
python3 -m pylint $(git ls-files '*.py' | grep -v '^tests/')

# 1. Rebuild index (picks up new features/skills, syncs version into index.json)
python3 tooling/index_build.py
python3 tooling/index_build.py --check   # fails if stale

# 2. Sync version into plugin manifests (index_build only syncs index.json)
python3 tooling/version_sync.py
python3 tooling/version_sync.py --check   # fails if plugin.json/marketplace.json stale

# 3. Changelog table index
python3 tooling/changelog_index.py --check

# 4. Validate all schemas and catalog files
python3 tooling/validate.py --all

# 5. Release guard (fails if VERSION needs bumping)
python3 tooling/release_guard.py

# 6. Full test suite
python3 -m pytest tests/ -q
```

## Final quality gate (reviewing a completed feature branch)

Reviewer posture for a finished issue branch (subagent final gate). Commands
verified 2026-08 (issue #313); the venv lives in the MAIN checkout, worktrees
have no `.venv` — use `<main>/…/.venv/bin/python3` from inside a worktree.

```bash
# Re-run these yourself — never trust the leaf's gate report alone
python3 -m pylint <every edited script>             # expect 10/10
python3 tooling/index_build.py --check              # "index.json up to date"
python3 tooling/changelog_index.py --check          # "changelog index up to date"
python3 tooling/version_sync.py --check             # index + version literals up to date
python3 tooling/gates/scaffold_freshness_guard.py   # re-scaffolds the tree; PASS = only version stamps differ
python3 -m pytest tests/test_<feature>.py -q        # the new targeted tests
```

- **Mirror identity**: welcome-ai-badger scripts ship in THREE copies
  (`features/common/skills/.../scripts/`, `skills/.../scripts/`,
  `.ai-badger/skills/.../scripts/`). `md5` all three — not byte-identical is a
  finding. A NEW script added to the skill shows up in the manifest diff as that
  skill entry's `file_count` bump (e.g. 18→19) + `sourceHash` change — expected,
  not suspect.
- **Scope guard**: for a scaffold-only change,
  `git diff --name-only | grep -E 'drift|config\.schema|template_rendering|detect\.py|validate\.py|index_build|schemas|BREAKING'`
  must be EMPTY — no drift.py/schema/template_rendering edits means no override
  or keep-region semantics leaked in.
- **Manifest triage**: `git diff -- .ai-badger/manifest.json | grep -E '^[+-]' | grep -vE 'frameworkVersion|frameworkCommit|"hash"|generatedAt'`
  — every remaining line must be explainable. Also check `frameworkCommit`
  equals the worktree HEAD (`git rev-parse HEAD`).
- **Version sweep**: VERSION, plugin.json, marketplace.json, index.json,
  config.json `frameworkVersion`, manifest `frameworkVersion`, changelog table,
  and every scaffolded "Scaffolded by ai-badger X" header must agree.
- **Test discrimination**: for each new test ask "would it FAIL against the
  pre-change code?" Tests that pass both before and after are vacuous guards —
  legitimate as regression guards, but label them as such and name the missing
  discriminating combination (feature-ACTIVE + fallback-path case, e.g.
  exclude-all invariants + non-empty local, not just empty-dir no-op). Flag test
  names that overclaim their assertion ("after all framework invariants" that
  only asserts position after one).
- **Doc claims vs code**: verify changelog claims about OTHER components against
  their code paths — e.g. "feed-badger will list the files as additions" → check
  `detect_additions.py` MANAGED dirs + rglob scan; "never pruned" → check
  `superseded_prune.py` is manifest-entry-driven. Docs are claims, code is
  evidence.

**Pitfall**: Running `index_build.py` syncs the version into `index.json` but NOT
into `.claude-plugin/plugin.json` or `.claude-plugin/marketplace.json`. After
bumping `VERSION`, you must also run `version_sync.py`. The CI check for this
appears as "Version literals (plugin.json, marketplace.json, index.json) agree
with VERSION" and fails with exit code 1. This is separate from
`index_build.py --check` which only checks index.json staleness.

**Pitfall**: Skipping `index_build.py --check` after adding new features causes
CI to fail with "index.json is missing or stale". Run it after every catalog
change.

**Pitfall**: New Python dependencies (e.g., `pyyaml`) must be added to BOTH
the CI workflow install step (`.github/workflows/pylint.yml`) AND
`scripts/requirements.txt`. Missing either one causes CI failures
(`ModuleNotFoundError`) that pass locally because the developer has the
package installed globally. After adding a new `import` to any script,
verify both files reference the dependency.

**Pitfall**: CI-invisible imports. Scripts that import packages not available
in CI (like `yaml` in hook files) need `# pylint: disable=import-error`
inline comments. Test files that use the same package do NOT get this
exemption — the package must be installed via CI dependencies. This is
because pylint skips the inline disable only, not the runtime import;
pytest collects test files at import time, so missing deps crash collection.

**Pitfall**: Pre-commit pylint hook fails on bootstrap imports. The
`import badger_lib as bl` line (after `_bootstrap_lib()`) triggers
`E0401: Unable to import` because pylint can't see the runtime sys.path
modification. Fix: add `# pylint: disable=wrong-import-position` to the
import line. Same applies to `import install_plugins`. The hook uses
`language: system` so pylint must be installed in the system python —
if it's not, the hook fails on every commit, training `--no-verify` into
the workflow.

**Pitfall**: The release guard compares against the last release TAG, not the
previous commit. If you add new shipped-surface files (anything under `skills/`,
`features/`, `schemas/`, or `index.json`), you MUST bump `VERSION`.

**Pitfall: `git commit` output can look like failure when hooks run.** The
code-review-graph hook runs on `git commit` and prints analysis output (risk
scores, changed functions, test gaps) before git's own status. The hook's output
may include text like "no changes added to commit" that looks like git rejected
the commit — but the commit actually succeeded. Verify with `git log --oneline -1`
rather than parsing the hook output for success signals.

**Pitfall**: When creating symlinks in nested directory structures, count the
depth correctly. `features/claude/templates/` is 2 levels deep from `features/`,
so the symlink to `features/common/templates/` should be
`../../common/templates/`, not `../../../common/templates/`. Always verify with
`cat <symlink> | head -1` after creating.

**Pitfall**: When tests create mock framework trees, they must include ALL files
the real framework has — including new schemas, scaffolding.json files, and
templates. If you add `scaffolding.json` for an agent, the mock trees in tests
that scaffold that agent must also include the scaffolding.json and its
referenced template files. Missing files cause `FileNotFoundError` in tests
that pass in isolation but fail in the full suite.

**Pitfall**: JSON Schema `$ref` to external files fails with `jsonschema`'s
`Draft202012Validator` — it can't resolve relative file references without a
custom `RefResolver`. The workaround is: (1) inline the enum in each schema
that needs it, (2) add a shared constant in `badger_lib.py` (e.g.
`AGENT_NAMES = ["claude", "copilot", "hermes", "junie"]`), and (3) add a
documentation-only reference file (`schemas/agents.schema.json`) listing the
canonical values. Never use `$ref: "other.schema.json#/..."` in ai-badger
schemas unless you also wire a custom resolver in `badger_lib.py`.

**Pitfall**: After moving files (e.g., `git mv skills/ features/common/skills/`),
the `index.json` is stale. Run `python3 scripts/index_build.py` immediately
after the move — tests that use the real framework root will fail until the
index is rebuilt.

**Pitfall**: Schema renames must happen atomically with code that writes the old
field. Renaming `pluginScope` → `skillScope` in config.schema.json breaks
scaffold.py which still writes `pluginScope`. Do the rename + script update in
the same commit, or the intermediate state fails validation.

**Pitfall**: `git reset --soft $(git merge-base HEAD main)` to squash commits
picks up ALL changed files between main and the working tree — including stale
`.ai-badger/` scaffolded state (renamed schemas, deleted plugin files, etc.)
that accumulated on main since the branch was created. After the soft reset,
explicitly `git add` only the files you changed; use `git checkout --` to
restore unrelated files before staging. Better: use `git rebase -i main` for
squashing — it replays commits individually without mixing in working-tree state.

**Pitfall**: `gh pr edit --body` with backticks in the body causes shell syntax
errors (backticks are shell command substitution). Always use
`gh pr edit --body-file /tmp/pr-body.md` instead.

**Pitfall: Invariant leakage — repo-specific details in generic invariants.**
Invariants in `features/common/invariants/` are scaffolded into EVERY project.
They must be generic — never reference repo-specific scripts, files, or tooling
(e.g., `version_sync.py`, `plugin.json`, `marketplace.json`). Those are
ai-badger-framework artifacts that don't exist in scaffolded projects. If an
invariant needs framework-specific steps, keep the invariant generic and document
the extra steps in the ai-badger repo's own `.ai-badger/CLAUDE.md` or this skill
instead. Caught in session: `version-changelog-required.md` had
`version_sync.py` and `index_build.py` steps that only apply to the framework
repo itself.

**Pitfall**: Docs sync is part of the task, not an afterthought. When adding a
new catalog feature, update `docs/authoring-a-feature.md` (discovery rules table
+ new section) in the same commit. User explicitly expects docs to reflect code
changes — don't defer to a separate task.

**Pitfall**: Phase ordering matters — remove old data before running validation.
If you update index.schema.json to remove a feature key (e.g., `plugins`) but
don't remove the data directory (`features/*/plugins/`), the next
`index_build.py` run will produce entries the updated schema rejects.

**Pitfall**: Cross-file references (e.g., `skills.json` entries referencing
source names in `skills-source.json`) cannot be validated by JSON Schema alone.
`validate.py` must perform a runtime check: for each stack with a `skills.json`,
verify every entry's `source` field exists in the sibling `skills-source.json`.
If this check is missing, a typo in a source name silently produces no
installation commands. The check is in `validate_all()`.

**Pitfall**: Agent enum ordering drifts silently. When the same enum appears in
multiple schemas (config.schema.json, manifest.schema.json), different files end
up with different orderings. This doesn't affect validation but creates
confusion. Align once and add "keep in sync" comments referencing
`badger_lib.AGENT_NAMES`.

**Pitfall**: Hermes plugin hook callbacks receive `**kwargs` for forward
compatibility, but pylint flags this as `W0613: Unused argument 'kwargs'`.
Prefix unused variadic kwargs with underscore: `**_kwargs`. Named parameters
that aren't used in the function body should similarly be prefixed `_param`
or omitted entirely — Hermes passes params by name, so only declare the ones
you actually need.

**Pitfall**: Hook and adjustment entry points MUST catch all exceptions and
log them. A hook that raises an unhandled exception can crash the agent
session or block session startup. Every top-level hook function
(`on_session_start`, `post_tool_call`, `pre_llm_call`) and every
`adjust()` function must be wrapped in `try/except Exception` with
`logger.debug(..., exc_info=True)` or a return dict with the error note.
Use `# pylint: disable=broad-exception-caught` on the except clause.
Never let a hook propagate exceptions to the caller.

**Pitfall**: `scaffold.py` is near pylint's 1000-line `too-many-lines` limit.
Before adding code to it, check `wc -l features/common/skills/welcome-ai-badger/scripts/scaffold.py`.
If over ~950, add `# pylint: disable=too-many-lines` at the top of the file
(line 2, after the shebang). CI runs pylint on ALL non-test `.py` files
including the `.ai-badger/` scaffolded copy — both must be in sync (see next
pitfall).

**Pitfall**: `.ai-badger/skills/welcome-ai-badger/scripts/scaffold.py` is a
scaffolded copy that pylint ALSO scans. When modifying the `features/` source,
copy it to `.ai-badger/` too: `cp features/common/skills/welcome-ai-badger/scripts/scaffold.py .ai-badger/skills/welcome-ai-badger/scripts/scaffold.py`.
The CI command `pylint $(git ls-files '*.py' | grep -v '^tests/')` picks up
both files. Failing to sync causes phantom lint failures on the stale copy.

**Pitfall: Plugin copies must be synced after any skill content change.**
Two sets of plugin copies track the source of truth in `features/`:
- `.claude/skills/` — Claude Code discovers plugin skills here, not `features/`
- `.ai-badger/skills/` — the scaffolded plugin copy; `test_repo_plugin_copy_is_in_sync` enforces parity

After editing ANY skill content in `features/<stack>/skills/`, run:
`python3 scripts/sync_plugin_skills.py`. Commit BOTH the source and the
plugin copies. Without this, skills are invisible to Claude Code when the
plugin is installed, and the sync test fails. The sync script skips skills in
`MANAGED_EXTERNALLY` (code-review-graph skills: debug-issue, explore-codebase,
refactor-safely, review-changes). Caught in session: plugin 0.15.1 broke
skill discovery because skills moved to `features/common/skills/` without
syncing to `.claude/skills/`.

**Pitfall: Cross-stack skill discovery.** Skills are NOT limited to
`features/common/skills/`. Agent-specific stacks (e.g.
`features/claude/skills/auto-wm/`) ship skills too. Both `DEFAULT_SKILLS` in
`scaffold.py` and the skill-list assembly in `refresh.py` use
`bl.iter_feature_dirs()` to collect default-scope skills from ALL stacks.
Tests that assert `DEFAULT_SKILLS` against a common-only list must account
for skills in every stack directory.

**Pitfall**: `pylint` reports line numbers for `too-many-statements` on the
`def` line of the method, not the first statement. If you add
`# pylint: disable=too-many-statements` to the wrong method (e.g. `run()`
when the issue is on `_apply_scaffolding()`), pylint still fails. Check the
actual line number in the pylint output and add the disable comment to the
correct method signature.

## den-refresh and breaking versions

`den-refresh` (the update skill) re-scaffolds only when drift is detected on
manifest entries. It cannot detect NEW framework features that weren't in the
original scaffold — the manifest only records what WAS scaffolded. To pick up
a new agent, stack, or skill, add it to `config.json` and re-run
`welcome-ai-badger`'s `scaffold.py` (not den-refresh). This is a documented
limitation from ADR-0001 decision 5: "newly-added catalog items are invisible,
because drift walks the manifest rather than the catalog."

**Post-refresh checklist** (do in the same session, don't defer):
1. Review the diff — seed-once files preserved, managed files overwritten
2. Commit the refresh
3. If framework version changed: bump `VERSION`, add `docs/changelog/` entry,
   run `version_sync.py`, update `docs/changelog/README.md` listing
4. Rebuild index if needed: `python3 scripts/index_build.py`

**Breaking versions** (v0.7.0+): `BREAKING_VERSIONS` at the framework root lists
versions that require a full re-scaffold. When den-refresh detects a transition
crossing a breaking version boundary (e.g. 0.6.0 → 0.7.0), it backs up
`.ai-badger/` to `.ai-badger.bckp/` before re-scaffolding. Helper functions:
`badger_lib.read_breaking_versions()` and `badger_lib.is_breaking_transition()`.

**den-refresh must update config.frameworkVersion unconditionally.** The version
update MUST happen outside the drift-gated re-scaffold block. If the update is
inside `if has_drift`, a refresh that finds no drift leaves config stale, causing
every subsequent refresh to re-scaffold unnecessarily. Fix: after drift detection,
always compare `scaffold_version != current_version` and update config.json
regardless of whether drift was found or re-scaffold ran.

**den-refresh stack-ignore.json (v0.16.0+):** Projects can create
`.ai-badger/stack-ignore.json` with `{"ignore": ["python"]}` to suppress
false-positive stack detection. Stacks listed are excluded from `newStacks`
output. The file is project-owned (manual), never overwritten by re-scaffold.
Use when a stack is detected as a transitive/tool dependency (e.g. `python`
from `.mcp.json` referencing `python3` for code-review-graph).

**Pitfall: Stale `sys.modules` cache after scaffold modifies files mid-session.**
When den-refresh or scaffold.py modifies schema/script files during a run,
`sys.modules` caches the old module versions. Subsequent pytest runs get
`AttributeError` on functions that exist in the updated file but not in the
cached module. Tests pass individually but fail in the full suite. Fix:
`python3 -m pytest --cache-clear -q`. NOT a test bug — it's a module-reload
ordering issue.

**Pitfall: Hook path rewriting in `wire_hooks()`.** The scaffold method must
rewrite `${CLAUDE_PLUGIN_ROOT}/features/common/skills/` to the scaffolded
project's `.ai-badger/skills/` path. `${CLAUDE_PLUGIN_ROOT}` only works when
ai-badger is installed as a Claude Code plugin, not in scaffolded projects.
For skills not in the framework's hooks.json (e.g., prompt-markers), discover
hook scripts by globbing `*_hook.py` in the skill's `scripts/` directory.

**Pitfall: Hook merge dedup must check at the hook level, not the entry level.**
The settings.json hooks format is `event → [entry → [hook]]`. When merging new
hooks into existing settings, dedup must compare individual hook `command`
strings, NOT entire entries. The old code checked each inner hook but appended
the entire outer entry — causing duplicates when an entry had multiple hooks
and only some were new. Fix: extract `merge_hooks()` as a standalone function
that builds a `registered_cmds` set, filters new entries to only genuinely
new hooks, and appends only the filtered subset. This is also more testable.

**Pitfall: hooks-manifest.json must have per-agent entries.** `wire_hooks()`
and `adjust_hooks.py` both iterate over `hooks-manifest.json` looking for their
agent key (e.g., `hook.get("agents", {}).get("copilot")`). If an agent has NO
entries in the manifest, no hooks are wired — silently. When adding a new agent's
hook support, add entries to `hooks-manifest.json` FIRST, then create the
adjustment/scaffold code. The manifest is the source of truth for which hooks
apply to which agents.

**Pitfall: Hook event name mapping between agents.** Claude uses PascalCase
(`SessionStart`, `UserPromptSubmit`), Copilot uses camelCase (`sessionStart`,
`userPromptSubmitted`). The hooks-manifest.json stores the event in the TARGET
agent's format. When an adjustment reads from the manifest and looks up the
source hooks.json (which uses Claude/PascalCase), it must reverse-map:
`sessionStart` → `SessionStart`, `userPromptSubmitted` → `UserPromptSubmit`.

**Pitfall: Directory entries (skills) use content-hash drift detection.** Skills
are directories and can't be directly hash-compared — the scaffolded copy strips
tests/evals and embeds extensions. `drift.py compare()` uses `dir_content_hash()`
from `badger_lib.py` with a two-phase approach:
1. **Structural pre-check**: compare file_count + dir_count (cheap O(n) walk)
2. **Content hash**: SHA-256 of sorted (relative_path + file_content) for each file

Files matching `SKILL_EXCLUDE_PATTERNS` (`tests`, `evals`, `__pycache__`, etc.)
are excluded — same patterns as `scaffold.py`'s `_test_ignore`. The manifest
stores both `hash` (content_hash) and `dirMeta` (file_count, dir_count) per
skill entry. When `dirMeta` is missing (old manifests), falls back to full
content hash comparison. This replaced the v0.9.3 commit-based approach which
was too aggressive (flagged ALL skills when ANY commit differed).

**Pitfall: drift must hash the TARGET, not the SOURCE.** `scaffold.record()`
hashes the scaffolded target directory (excluding `extensions/`), but
`drift.compare()` historically hashed the framework source. For skills with
config-gated extensions (e.g. `task` with github/hermes), the source always
has ALL extensions while the target has only the ones the config retained.
This caused false drift on every scaffolded project. Fix (v0.16.1):
`drift.compare()` accepts optional `target` param; when provided, it hashes
from the scaffolded output with `SKILL_EXCLUDE_PATTERNS + ["extensions"]`,
matching `scaffold.record()`. Callers (den-refresh, CLI main) must pass
`target=target`.

**Pitfall: evals/ is never distributed.** The `_test_ignore` pattern in
scaffold.py strips `evals/`, `tests/`, `test_*.py` during copytree. If you see
evals/ in the framework but not in the scaffolded project, that's correct
behavior — evals are framework-only quality-regression content.

**Pitfall: JSON schemas must allow `$schema` property.** All schemas with
`additionalProperties: false` must include `"$schema": { "type": "string" }` in
their `properties`. Otherwise, files that include `$schema` for editor validation
fail strict schema validation. Check ALL 9 schemas when adding new ones.

**Pitfall**: Don't forget changelog and VERSION after feature work. After merging
a feature PR, immediately: (1) bump `VERSION`, (2) add `docs/changelog/` entry,
(3) run `version_sync.py`, (4) update `docs/changelog/README.md` listing. Doing
this as a separate commit after the feature PR is fine, but don't defer it to
"later" — it accumulates and becomes a separate task. The invariant
`version-changelog-required` enforces this but only at release time; best practice
is to update changelog in the same PR as the feature.

**Pitfall: Parallel PRs that both bump VERSION cause merge conflicts everywhere.**
When two feature branches both bump `VERSION`, modify `scaffold.py`, and run
`version_sync.py`, merging the second one conflicts on VERSION, plugin.json,
marketplace.json, index.json, and any shared script both branches touched. The
conflicts are usually trivial (same bump to the same value, or one needs a
higher version) but noisy. Resolution: merge main into the second branch,
resolve conflicts by taking the higher version, re-run `version_sync.py` and
`index_build.py`, then merge. For shared script conflicts (e.g., both branches
added `check=False` to subprocess calls), prefer the main branch's version
since it already passed CI.

**Pitfall**: When a new skill needs extension activation conditions that the framework
doesn't support (e.g., OR logic, list membership), modify `requirement_met()` in
`scaffold.py` FIRST, then author the extension. Don't work around framework gaps by
duplicating extension content. The framework is mutable — extend it. See
`scaffold-extensions` skill for `requirement_met()` syntax reference.

**Pitfall**: Don't over-restrict extension `requires`. Before adding multi-stack
conditions, ask whether the extension content actually depends on the backend stack.
Contract alignment, accessibility, testing patterns are often frontend-only concerns.

**Pitfall: `support.json` for agent capability tracking.** When researching agent
capabilities (Copilot hooks, Hermes plugins, etc.), create or update
`features/common/support.json` with the findings. This structured matrix is the
source of truth for what each agent supports and what ai-badger scaffolds. Useful
for generating accurate articles and identifying coverage gaps.

For enabling opt-in skills / re-running `welcome-ai-badger` on a project that ALREADY has

  `include.skills`. A group name (`"documentation"`) expands to all its members; the full
  opt-in catalog, the mechanism, and the exact scaffold command are in
  `references/consumer-scaffold-operations.md`.
- **USER RULES (f: corrections, 2026-08-02):**
  1. **Enable ALL opt-in skills** — never just the group the current task needs. Do not

  2. **Scaffold on MASTER, never inside a task worktree.** Sequence: get main clean/merged

- The scaffold also writes tracked symlinks into `.claude/skills/` and `.github/skills/`

- Exclude `.ai-badger/task-tracking/*.json` from the scaffold commit: `task_tracker.py`
  writes session/token state there, and the finish protocol touches them again.

## Extending scaffold template slots

When adding a new config-driven section to CLAUDE.md/HERMES.md (e.g. `externalTools`,
`customLintRules`, any user-authored block that should survive re-scaffold):

1. **Schema**: Add the field to `schemas/config.schema.json` with `additionalProperties: false`
   on nested objects. Use `items.required` to enforce mandatory fields.

2. **Templates**: Add `{{NEW_SLOT_NAME}}` to BOTH `features/common/templates/CLAUDE.md.tmpl`
   AND `features/common/templates/HERMES.md.tmpl`. Place it before `## Framework` (the
   closing section).

3. **Scaffold**: Add a `_render_<feature>()` static/compute method near `_compute_doc_slots()`
   that reads `self.config.get("featureName", [])` and renders markdown. Add the result to
   the `return` dict of `_compute_doc_slots()`.

4. **Tests**: Write failing tests FIRST using `load_script` + `tmp_path` + `root` fixtures.
   Test: (a) instructions appear in `.ai-badger/CLAUDE.md`, (b) empty config = no extra section,
   (c) multiple items render, (d) also appears in HERMES.md, (e) schema validates.

5. **Run scaffold** against the real project to verify: `python3 features/common/skills/welcome-ai-badger/scripts/scaffold.py --config .ai-badger/config.json --target . --root . --overwrite-agent-files`

**Pitfall**: The template slot placeholder MUST appear in both `.tmpl` files or one agent's
instruction file will be missing the content. Templates are rendered independently — there's
no automatic cross-file injection.

**Pitfall**: `scaffold.py --overwrite-agent-files` replaces ALL agent discovery files. Without
it, hand-authored CLAUDE.md (lacking the managed header) is preserved and the new slot won't
appear in the root file — only in `.ai-badger/`.

## Adding a new catalog format (dependencies, tool requirements, etc.)

When a new cross-cutting concern needs to be declared per-feature (e.g., package
dependencies, runtime requirements, environment prerequisites), create a new catalog:

1. **Catalog file**: `features/common/<name>.json` with `$schema` pointing at the new schema.
   Follow the common → stack → user merge pattern if stacks can override.

2. **Schema**: `schemas/<name>.schema.json` with `$schema`, `$id`, `title`, `description`.
   Must include `"$schema": { "type": "string" }` in properties (all ai-badger schemas do).

3. **Script**: `features/common/skills/welcome-ai-badger/scripts/<name>.py` with:
   - Pure-function API (`run_dependency_check(root, target, features=None)`) callable from tests
   - CLI `main(argv)` with `--root`, `--target` flags, JSON output to stdout
   - No `_bootstrap_lib()` needed if the script doesn't use `badger_lib`

4. **Integration into scaffold.py**:
   - Add a `_check_<name>()` method on the `Scaffolder` class
   - Import the script module: `import <name>_check as nc_lib`
   - Call from `run()` after hook wiring, before config persistence
   - Append results to `self.notes` for the scaffold report
   - Return the result dict from `run()` alongside manifest/notes/pluginCommands

5. **Tests**: `tests/test_<name>.py` using `load_script` + `tmp_path` fixtures.
   Mock subprocess calls — don't actually install packages in tests.

6. **Index + version**: Run `index_build.py` and `version_sync.py`, bump `VERSION`.

**den-refresh picks up automatically** — it delegates to `scaffold.py`'s `run()`,
so any new method called from `run()` is active on refresh too.

**Pitfall**: New scripts imported by `scaffold.py` must be on `sys.path`. The script
directory is already added by scaffold.py's `_SCRIPT_DIR` logic, so imports like
`import dependency_check as dc_lib` work as long as the script lives in the same
`scripts/` directory.

## External MCP tool integration

### Testing optional catalog-declared executables

For a catalog MCP server whose declaration is conditional on a locally installed executable:

1. Add behavior tests for the catalog declaration, conditional metadata, schema acceptance, index/catalog files, and generated config. Keep the test contract at the catalog boundary rather than coupling it to a particular helper implementation.
2. Load the real standalone script first, then patch the dependency at the loaded module's lookup site (for example, `sys.modules["mcp_tools"].shutil.which`). Return deterministic fake paths for every executable the test exercises; never let the host PATH decide the result.
3. Cover both branches end to end: an available executable appears in `declared_servers()` and generated config with the expected command/args split; an unavailable executable is absent while an unrelated baseline server remains.
4. Do not trust a negative test that passes before the declaration exists: it may be vacuously true. The available-path test must fail with the missing declaration or generated entry, and the RED run should record those exact failures before production edits.
5. After the RED run, verify the worktree contains only test changes before handing implementation to the next agent.

**Stale generated-config safety:** an unavailable optional server must be removed from a prior ai-badger-generated entry, but never by name alone. Compare the existing entry against the renderer's generated shape before deleting it, preserve entries with user-authored fields such as `type`/`url`, and test home-expanded variants such as `${HOME}/.local/bin/<command>` and `${HOME}/.dotnet/tools/<command>`. Pass unavailable names through a dedicated cleanup path rather than the ordinary decline path so the ownership rule remains explicit.

**Generated-copy and matrix gate:** after changing a `features/common/skills/` source, run `sync_plugin_skills.py` and verify both the shipped plugin copy and the scaffolded `.ai-badger/skills/` copy are identical. Run the project's freshness/scaffold gate before the first push; if it reports drift, re-scaffold from the existing config, inspect generated churn, and rerun the full suite. A local Python 3.14 pass does not establish support for this Python 3.8+ project: reproduce CI-only failures under the supported floor before pushing.

**Pre-push gate mechanics (verified 2026-08-06):** the local push gate is `.lefthook/pre-push/verify.sh`, a multi-lane runner (deps/docs/release/paths/validate/scaffold/tdd/js/pylint/pytest) that takes ~2-3 min: `pytest` runs the FULL suite (~2 min), `release` fails fast if the shipped surface changed without a VERSION bump, `scaffold` runs the freshness guard. A failed lane prints a `reproduce:` line and `VERIFY_SKIP=<lane>` / `git push --no-verify` bypasses. The pre-commit hooks are the pre-commit framework installed for the SYSTEM python (`/Library/Developer/CommandLineTools/usr/bin/python3 -m pre_commit`) — there is no `pre-commit` binary on PATH, so invoke `pre-commit run <hook>` as `python3 -m pre_commit run <hook>` when probing a hook by hand. **When a gate fails, prove it is pre-existing by running the EXACT hook on the clean tree (stash → run → unstash) before declaring it unrelated** — the wrong invocation (e.g. `lefthook` instead of `pre-commit`) produces a false "passes clean" that misattributes the failure to your change.

**PR review loop:** open the draft PR after the first coherent commit, mark it ready only after local gates pass, then fetch inline Copilot comments with `gh api repos/<owner>/<repo>/pulls/<n>/comments`. Recheck every finding against the latest commit, implement all applicable findings together, rerun gates, push, and repeat until a review round has no new findings before squash-merging.

### Adding a new common MCP server catalog entry (verified recipe, ai-raccoon 2026-08-05)

To add a NEW common MCP server (beyond the existing code-review-graph/hermes), five pieces
suffice — no scaffold/schema changes are needed because the availability machinery already
exists:

1. **Catalog dir**: `features/common/mcp/<server>/` with three files:
   - `meta.json` — name, package, description, homepage, `prerequisite: {summary, check, install}`
     (e.g. check `ai-raccoon --version`, install `dotnet tool install -g arasz.ai-raccoon`).
   - `server.md` — the prose injected verbatim into agent docs as `## MCP Tools: <name>`.
   - `tools.json` — curated intents `{name, intent, tags}`. Constraints: `intent` ≤ 200 chars
     (schema-enforced), `tags` from the CLOSED vocabulary in `features/common/mcp-tags.json`
     (categories: language/action/domain/meta). Document the tool surface you OWN (repo main),
     not the installed tool's older surface.
2. **Declaration**: add `{name, command, declare: true, availability: {command: <exe>}}` to
   `features/common/stack-mcp.json`. The availability gate is `shutil.which(command)` — the
   gate binary must resolve on PATH (dotnet global tools at `~/.dotnet/tools/` count). The
   simplest configuration for a stdio server is a bare command with no args: `command:
   "ai-raccoon"` renders as `{"command": "ai-raccoon", "tools": ["*"]}` in `.mcp.json`.
3. **Index**: `index_build.py` auto-discovers `features/common/mcp/<server>` (any subdir with
   meta.json) — no manual index.json edit. Run `python3 tooling/index_build.py --check` as the
   gate.
4. **Tests** (TDD — mirror `tests/test_common_hermes_mcp_server.py` exactly): patch
   `sys.modules["mcp_tools"].shutil.which` with a fake returning deterministic paths (never let
   host PATH decide); cover available→declared+in `.mcp.json`, unavailable→omitted+removed from
   existing generated config, user-authored entry preserved, env override `=all`/`=none`/unset.
   Write the available-path test FIRST and record its RED failure before adding the declaration.
5. **Release**: VERSION minor bump (new shipped-surface feature), `docs/changelog/{v}-{slug}.md`,
   changelog README update, `index_build.py` rebuild, then refresh the repo's OWN scaffold
   (`welcome-ai-badger`) so the `MCP Tools: <name>` section lands in CLAUDE.md/HERMES.md.

**Probe the live server before writing server.md/tools.json.** Start the server yourself and
read its real prompt/tool surface over HTTP (don't guess from memory or docs):

```bash
ASPNETCORE_URLS=http://localhost:5081 <cmd> --transport http --data-root /tmp/probe-data &
curl -s -X POST http://localhost:5081/mcp -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"prompts/list"}'
# prompts/get {"name":"..."}, tools/list — same shape
```

Responses are SSE (`event: message` / `data: {...}`): extract the `data:` line, `json.loads`
it, then the payload is a second `json.loads()` of `content[0].text` (the server's `_unwrap`
helper does this). Live-probe BOTH the installed tool and the repo source when the versions
differ — the installed global tool can lag repo main by a whole feature (ai-raccoon 1.0.1
installed had `memory_configure` + no watch tools; repo main 1.0.2 removed it and added the 3
watch tools). Base the skill/catalog on the NEWER source surface since we own it, but the
skill must degrade gracefully when the installed tool lacks tools the docs promise (tell the
user `dotnet tool update -g <pkg>`).

**MCP catalog pitfalls (verified 2026-08-06, ai-raccoon serve-mode PR):**
- **`server.md` has a hard 15-line budget** (`test_every_shipped_server_md_stays_within_the_line_budget`
  in `tests/test_mcp_catalog_instructions.py`): the file is embedded verbatim in every agent
  instruction file, so it is budget-constrained by policy. The focused
  `test_common_ai_raccoon_mcp_server.py` does NOT cover this — the pre-push gate does. Count
  `strip().splitlines()` (blank lines count!) before pushing, and verify with the line-budget
  test file, not just the server's own test file.
- **The declared `.mcp.json` command form stays stdio even when the server gains an HTTP
  mode.** Clients that spawn `.mcp.json` commands expect JSON-RPC on stdout; a serve-mode
  verb never answers JSON-RPC (it prints a URL / exits 0 before initialize), so swapping the
  command is TRANSPORT-BROKEN for per-client spawns. The HTTP route is the URL entry form
  (Hermes `config.yaml` `url:`, Claude Code `.mcp.json` `type: http`). Per-client spawns on
  one fixed port also collide — the server-side answer is idempotent attach (a second launch
  probes the port, recognizes the running server, prints its URL and exits 0), not a command
  swap. Express "HTTP as the default" via catalog metadata + guidance, never by changing the
  declared command.
- **Changing `server.md`/`meta.json` = shipped-surface change = release-shaped PR**: VERSION
  bump (0.MINOR — it alters what scaffolding writes into consumer agent files), a
  `docs/changelog/{version}-{slug}.md` entry, `tooling/changelog_index.py` +
  `tooling/version_sync.py` runs, `gates/release_guard.py` green. The pre-push `release`
  lane fails the push with "shipped surface changed ... but VERSION is still X" otherwise.
- **After editing `server.md`, re-run the repo's own scaffold and commit the regenerated
  agent files** (the 7 CLAUDE.md/HERMES.md/.hermes.md/copilot-instructions copies) — the
  `scaffold-freshness-guard` fails any commit whose server.md no longer matches the tracked
  agent files. Then RESTORE the two environmental artifacts the scaffold run churns:
  `.ai-badger/manifest.json` (`frameworkCommit` bumps to the worktree HEAD — the guard
  tolerates the stale recorded value, and keeping it out of a catalog-only PR keeps the diff
  minimal) and `.github/mcp.json` (the PATH-dependent probe DROPS servers whose executables
  aren't on the runner's PATH — restore it or the PR silently removes hermes/ai-raccoon
  declarations).

### Current MCP catalog architecture

The current architecture is catalog-first: `features/<stack>/mcp/<name>/` contains `meta.json`, `server.md`, and `tools.json`; `stack-mcp.json` names relevance and `declare: true` opts into launch configuration; `index_build.py` indexes the catalog; `McpTools` is the single declaration reader. Older `externalTools` and `mcp-servers.json` sections below describe retired designs and must not be reintroduced. Common servers belong in `features/common/stack-mcp.json`; user-global Hermes configuration is proposed by the Hermes adjustment, never written by scaffolding.

There are two kinds of MCP server declarations in ai-badger:

### User-declared: `externalTools` in config.json

For MCP servers distributed as standalone packages (PyPI/npm) that a project wants scaffolded:

1. Add `externalTools` array to config schema (name, package, command, instructions, generate_mcp_json)
2. Template slot `{{EXTERNAL_MCP_INSTRUCTIONS}}` renders each tool's `instructions` markdown
3. `_generate_mcp_json()` method writes `.mcp.json` for tools with `generate_mcp_json: true`
4. Command parsing: uses package-name character heuristic (see `references/mcp-stack-declarations.md` "Command parsing heuristic")

**Portability pattern**: Use `uvx <package> serve` (Python) or `npx <package>` (JS) as the
command — ephemeral execution, no local install needed. Fall back to venv python only when
`uvx`/`npx` isn't available. Document both options in the tool's config comment.

### Stack-declared: `mcp-servers.json` in feature directories

For MCP servers that a stack *needs* (framework-curated, not user-authored):

1. Add `mcp-servers.json` to `features/{stack}/` (schema at `schemas/mcp-servers.schema.json`)
2. Scaffold reads these alongside `externalTools` and merges them (user wins on name conflict)
3. **Scope-aware output**: `scope: project` → `.mcp.json` (Claude/Hermes/Junie) or `.github/copilot/mcp-config.json` (Copilot). `scope: user` → `~/.hermes/config.yaml` (Hermes) or `~/.claude/settings.json` (Claude)
4. `refresh.py` needs no changes — re-scaffold automatically picks up new `mcp-servers.json` files

Full design and merge semantics: `references/mcp-stack-declarations.md`

### Catalog-declared: `external-tools.json` in feature directories (v0.14.0+)

External tools whose **instructions** should be auto-injected into agent instruction
files (CLAUDE.md, HERMES.md) and whose MCP server entries should be written to
`.mcp.json`. Follows the same common → stack → user merge pattern as `mcp-servers.json`.

1. Add `external-tools.json` to `features/{common,stack}/` (schema at `schemas/external-tools.schema.json`)
2. Scaffold reads common → stacks (last-writer-wins on name), then merges with `config.externalTools` (user overrides on conflict)
3. Merged list feeds into: `_render_external_mcp_instructions()` (CLAUDE.md/HERMES.md), `_generate_mcp_json()` (.mcp.json), `_merge_mcp_servers()` (agent-specific configs)
4. No `index_build.py` run needed — files are read at scaffold time, not indexed

Schema: `{"tools": [{"name", "package", "command", "instructions", "generate_mcp_json?}]}`

**Merge order**: catalog (common first, then stacks) → user `config.externalTools` (user wins on name conflict). This is the same precedence as mcp-servers.json.

**Lazy init pattern**: `_merged_external_tools` is computed in `run()` but `_generate_mcp_json()` can be called directly from tests. The class initializes `_merged_external_tools = []` and `_external_tools_merged = False` in `__init__`; `_generate_mcp_json()` checks the flag and computes the merge lazily if needed.

**Pitfall**: `externalTools` and stack `mcp-servers.json` both write to `.mcp.json`. If both
declare the same server name, the `externalTools` entry (user intent) takes precedence. The
merge happens in `_merge_mcp_servers()` before writing.

**Pitfall**: `hermes mcp add --args` captures ALL remaining arguments. If you pass
`--connect-timeout 60` after `--args -m code_review_graph serve`, the timeout flag gets
stored as a server argument. Always pass hermes-level flags BEFORE `--args`, or use
`echo "y" | hermes mcp add ...` with connect-timeout as a hermes flag.

**Pitfall**: `hermes mcp add` tests the connection during registration. If the server needs
a warm-up (e.g. `uvx` downloading a package), the first attempt may fail with "Connection
closed". Use `echo "y" | hermes mcp add ... --connect-timeout 60` to save the config anyway,
then `hermes mcp test <name>` to verify once the package is cached.

## Changelog and version bump rules

Every release must: (1) bump `VERSION` per semver rules below, (2) add a
`docs/changelog/{version}-{slug}.md` entry, (3) update `docs/index.md` if
adding new doc sections. Enforced by `version-changelog-required` invariant at
`features/common/invariants/version-changelog-required.md`.

### VERSION bump rules (semver for a catalog)

- **0.MINOR** — anything that changes what scaffolding does: new/removed/renamed
  features, changed target paths, new detection behavior, new agents.
- **0.x.PATCH** — content fixes to existing files that don't alter scaffold shape.

Pre-1.0, the minor slot is the breaking slot. Adding a new agent, skill, or
stack is always a minor bump.

## Test conventions

- Tests live ONLY in top-level `tests/` — never in `skills/*/tests/`
- `scaffold.py` excludes `test_*.py`/`tests/` from every copy
- Use `load_script` fixture (defined in `conftest.py`) to import scripts
