## Findings

### F1 — An SSH key can replace the passphrase: the sound derivation is the ed25519 **seed** (32 uniform bytes) through a domain-separated HKDF/SHA-256, following the age pattern; the seed is the whole secret, and it is exactly 256 bits [READ]

The age/rage "SSH keys as identities" pattern works on the ed25519 seed: `filippo.io/age/agessh` (still on `main`) parses the OpenSSH private key, takes `ed25519.PrivateKey.Seed()` (the 32-byte seed), and derives the decryption scalar as `SHA-512(seed)[:32]` (`ed25519PrivateKeyToCurve25519`, `agessh.go:287-292`), domain-separated by the HKDF info label `"age-encryption.org/v1/ssh-ed25519"` (`agessh.go:200,233`). For AiRaccoon the cleanest variant keeps the full 256 bits and skips the curve conversion entirely: `key = HKDF-SHA-256(ikm = seed, salt = "", info = "ai-raccoon-db-key/v1")` (or plain `SHA-256(label ‖ seed)` — both measured in F2). The X25519-conversion variant loses ~5 bits because the scalar is clamped per RFC 7748 §5 (3 low bits cleared, top bit cleared, second-top bit set), so it is *not* preferred when the seed is available raw. RSA keys are also supported by age (`ssh-rsa` identities, minimum 2048 bits — `doc/age.1.ronn:186`), but see F4 for why ed25519 is the right default here. Note the current C2SP age spec (`c2sp.org/age` and the editor's copy in `C2SP/C2SP` `age.md`) no longer documents SSH stanzas — SSH support lives at the implementation/man-page level (age README §"SSH keys", `doc/age.1.ronn` §"SSH keys") — so "the age spec pattern" is best cited as the implementation plus the man page, not the normative spec.

**Evidence:** `https://raw.githubusercontent.com/FiloSottile/age/v1.1.1/agessh/agessh.go` lines 200, 233, 287-292 (retrieved 2026-08-05); age README and `doc/age.1.ronn` on `main` (retrieved 2026-08-05, "SSH keys" sections, incl. "RSA keys must be at least 2048 bits" and "keys held on hardware tokens such as YubiKeys or accessed via ssh-agent(1) are not supported"); `https://raw.githubusercontent.com/C2SP/C2SP/main/age.md` and `https://c2sp.org/age` (retrieved 2026-08-05 — no SSH stanzas); RFC 7748 §5 clamping (READ, https://www.rfc-editor.org/rfc/rfc7748.html#section-5).

### F2 — Measured end-to-end: an actual `~/.ssh`-style ed25519 key (and an RSA-2048 key) parses via the openssh-key-v1 format, yields a stable 256-bit derived key, and that key opens/reopens a SQLCipher bank through the proven `Password = "x'…'"` channel with wrong-key rejection — no provider changes needed, only the returned string [MEASURED]

Throwaway keys generated with `ssh-keygen` (macOS 26.5.2, `/tmp/sshkey-probe/`): an `ed25519` and an `rsa -b 2048` key, both unencrypted (`ciphername=none kdfname=none` per the PROTOCOL.key header parse). A pure-Python parser (PROTOCOL.key wire format) extracted the ed25519 seed; the public key embedded in the private section equals the `.pub` file, and a from-scratch RFC 8032 Edwards-point multiply of the seed reproduces the published public key — proving the extracted 32 bytes are the seed, and that the derivation is stable across the pub/priv pair. `SHA-256("ai-raccoon-db-key/v1" ‖ seed)` and `HKDF-SHA-256(ikm=seed, salt="", info=label)` both give 64-hex-char keys; re-derivation is byte-identical; `SHA-256(pubkey)` differs from the derived key (public material alone cannot derive it). The RSA key was serialized canonically to PKCS#1 DER (927 bytes) and hashed the same way. Then a net10.0 console probe (Microsoft.Data.Sqlite 10.0.10 + SQLitePCLRaw.bundle_e_sqlite3mc 2.1.11, same provider-init pattern as `SqliteEncryptionInit.cs`) ran the F3 channel against both derived keys: create+open with `Password="x'<derived>'"` OK; reopen with the same derived key and row read-back OK; reopen with a different derived key throws `SqliteException`. Output: `ALL DOTNET PROBES PASSED`. (The probe again emitted NU1903 for `SQLitePCLRaw.lib.e_sqlite3` 2.1.11 — the sibling report's F15 advisory still applies.)

**Evidence:** `/tmp/sshkey-probe/probe.py`, `probe2.py`, `DerivedKeyProbe/` (Program.cs, csproj; `dotnet run` output "ALL DOTNET PROBES PASSED", 2026-08-05, macOS 26.5.2, dotnet SDK 10.0.302); `/tmp/sshkey-probe/derived-ed25519.hex`, `derived-rsa.hex`; OpenSSH `PROTOCOL.key` (openssh-portable master, retrieved 2026-08-05, wire format and bcrypt KDF options).

### F3 — Entropy analysis, measured at scale: ed25519 seeds are uniform 256-bit material; RSA private blobs are high-entropy but structurally non-uniform — yet *both* hash to a full-strength 256-bit key, so the RSA objection is encoding stability, not entropy [MEASURED]

Across 200 generated ed25519 keys (6400 seed bytes): Shannon entropy 7.972 bits/byte, zero-byte rate 0.39% (≈ expected 1/256), all 256 byte values present — consistent with uniform CSPRNG output; the seed is by construction 32 bytes = 256 bits of nominal key material (RFC 8032 §5.1.5: seed is random 32 bytes). Across 30 RSA-2048 keys (27,773 bytes of canonical PKCS#1 DER): Shannon 7.972 bits/byte but **zero-byte rate 0.90%** — 2.3× the uniform expectation — plus per-blob structure: fixed DER sequence headers, a 3-byte exponent (65537), leading-zero-padded integers. So the claim "hashing an RSA private key is NOT 256-bit strength" is wrong as stated: the private material (two 1024-bit random primes p, q ≈ 1014 bits of entropy each) contains far more than 256 bits, and SHA-256 of the canonical blob yields a 256-bit key whose security rests on the RSA private components being secret — recovering it from the hash output is at least as hard as factoring n. The real RSA downsides are (a) no single canonical encoding: PKCS#1 vs PKCS#8 vs OpenSSH containers, optional CRT parameters, leading-zero conventions — re-encoding or migrating the key file can silently change the derived key unless the serialization is pinned (e.g. hash fixed-width `p ‖ q`); (b) the measured structural markers make the *file* distinguishable as RSA key material (matters only for steganographic-style privacy, not key strength). Ed25519 has exactly one canonical secret encoding (the seed), which is why age's SSH support and this proposal prefer it. Caveat: a 32-byte sample is far too small for per-byte entropy estimates (measured 4.94 bits/byte on a single seed — a small-sample artifact; corrected by the N=200 measurement).

**Evidence:** `/tmp/sshkey-probe/probe2.py` run output (2026-08-05: seed Shannon 7.9720/7.9748, RSA 7.9716, zero rates 0.3906% vs 0.90%); RFC 8032 §5.1.5 (READ); single-seed artifact from `probe.py` phase 1 (2026-08-05).

### F4 — Passphrase-protected SSH keys do not work as a drop-in DB key source: the seed is encrypted with bcrypt_pbkdf + AES-256-CTR, ssh-agent cannot export it, and the passphrase becomes the de-facto secret [MEASURED]

Measured on a passphrase-protected copy of the probe key: header switches to `ciphername=aes256-ctr kdfname=bcrypt` with a 16-byte salt and `rounds=24`, and the private section no longer starts with the plaintext checkint pair — the seed is unrecoverable without the passphrase (bcrypt_pbkdf per PROTOCOL.key §2). Three escape routes, all bad for this tool: (1) ssh-agent holds decrypted keys but its protocol is sign-only — the agent never returns key material (local `man ssh-agent`; age documents `ssh-agent` as unsupported, `doc/age.1.ronn:206`); (2) typing the passphrase at server start breaks the MCP spawn model (sibling report F14 — no TTY); (3) storing the passphrase in the keychain just re-creates the secret-management problem the SSH key was supposed to remove, now with a *weaker* secret (human passphrase vs 256-bit key). Verdict: support unencrypted ed25519 keys only in v1, fail loudly with "key is passphrase-protected" otherwise; SSH.NET (`PrivateKeyFile(fileName, passPhrase)`) can unlock encrypted OpenSSH keys if a future version wants it, but the bootstrap secret then needs its own channel. This mirrors age's own posture — the man page asks for the password interactively when the identity matches, and notes SSH keys "might not be protected long-term, since they are revokable when used only for authentication".

**Evidence:** `probe.py` passphrase section output (2026-08-05); `PROTOCOL.key` §2/§4 (retrieved 2026-08-05); `man ssh-agent` (local, 2026-08-05, "Authentication passphrases and private keys never go over the network" — the agent signs, it does not export); `doc/age.1.ronn:127-129,204-210` (retrieved 2026-08-05); `https://raw.githubusercontent.com/sshnet/SSH.NET/develop/src/Renci.SshNet/PrivateKeyFile.cs:212` + README key-format list (retrieved 2026-08-05).

### F5 — Key-reuse, rotation, and platform facts: the SSH key becomes a second secret of equal value (SSH access AND the bank), rotation means `PRAGMA rekey`, and Windows uses the same `%USERPROFILE%\.ssh` layout [READ]

Reuse: the same key protecting SSH access now also protects the DB — if the key file leaks, both leak; the DB's offline-brute-force resistance (sibling F1/F2: raw key kills the offline KDF attack) is unchanged, but the *key's* exposure surface doubles. For a local-first tool whose DB holds agent memories (not credentials), that is a real but bounded trade-off — the age project itself frames SSH keys as revocable authentication material, not long-term encryption keys. Rotation: replacing/regenerating the SSH key changes the derived DB key, so the bank must be migrated with `PRAGMA rekey` (sibling F5/F3-probe-5 — the double-quoted form through Microsoft.Data.Sqlite); the setup verb should offer `--rekey-from <old-key-path>` or a plain "rekey to new SSH key" flow. Stability: the `.pub` file is derived from the seed (F2 measured), so regenerating the public half alone cannot break the derivation; only replacing the private key does. Windows: OpenSSH ships with Windows and uses `C:\Users\<user>\.ssh` by default (ssh-keygen's default save path) — same file layout, so a path-based provider is portable; macOS-specific hardening (Keychain) does not apply to the SSH option, which is deliberately just a file. Note this option needs **no new NuGet dependency** if v1 restricts to unencrypted openssh-key-v1 parsing (a ~60-line format parse, not crypto) — relevant to the repo invariant "no hand-rolled crypto or security orchestration": the parse is format decoding; the derivation uses `System.Security.Cryptography` HKDF/SHA-256 primitives with a domain label. Whether the labelled-derivation composition itself needs an ADR under that invariant is flagged in "Still open".

**Evidence:** Reasoning from F1/F2/F4; `doc/age.1.ronn:188-189` ("SSH keys might not be protected long-term by the recipient, since they are revokable when used only for authentication"); `https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement` (retrieved 2026-08-05, default path `C:\Users\username/.ssh/`); repo `.ai-badger/CLAUDE.md` invariant "No hand-rolled crypto or security orchestration" (READ).

### F7 — Azure auth bootstrap: `DefaultAzureCredential` tries environment → workload identity → managed identity → Visual Studio → VS Code → Azure CLI → Azure PowerShell → Azure Developer CLI → interactive; the realistic local path is the **Azure CLI login state** (`~/.azure`, `%USERPROFILE%\.azure`) or env vars — all files outside the DB, readable pre-open [READ]

MS Learn (Azure.Identity 1.21 docs, retrieved 2026-08-05) lists the chain in order: `EnvironmentCredential`, `WorkloadIdentityCredential`, `ManagedIdentityCredential`, `VisualStudioCredential`, `VisualStudioCodeCredential`, `AzureCliCredential`, `AzurePowerShellCredential`, `AzureDeveloperCliCredential`, `InteractiveBrowserCredential`, `BrokerCredential` — stopping at the first token. For a developer desktop, the realistic members are: (1) `EnvironmentCredential` — `AZURE_CLIENT_ID`/`AZURE_TENANT_ID`/`AZURE_CLIENT_SECRET` (or certificate path); (2) `AzureCliCredential` — shells out to `az account get-access-token`, backed by the CLI's cached login under `$AZURE_CONFIG_DIR` defaulting to `~/.azure` (Linux/macOS) or `%USERPROFILE%\.azure` (Windows) — the CLI writes its config and MSAL token cache there; (3) VS/VS Code tokens (machine-bound, not headless-friendly). Interactive/broker credentials are opt-in (`IncludeInteractiveCredentials`), so a headless server spawn never pops a browser by default — the failure mode is "no token, run `az login`", which is exactly the right loud failure. Key structural point: **the bootstrap (CLI token cache / env vars) lives outside the encrypted DB and is readable before the bank opens** — the vault stores the 256-bit raw key, and the *Azure identity* gates access to it. Two operational deltas vs local stores: token expiry (the CLI token must be refreshed by re-running `az login`; `AzureCliCredential` surfaces "please run az login" errors), and a network dependency at server start. Whether this machine currently has `az` login state was **not** probed (credential-directory inspection denied by the user) — the local-state column in the ranking is UNVERIFIED.

**Evidence:** `https://learn.microsoft.com/en-us/dotnet/api/azure.identity.defaultazurecredential` and `.../azure.identity.azureclicredential` (retrieved 2026-08-05, chain order and "using Azure CLI to obtain an access token"); `https://learn.microsoft.com/en-us/cli/azure/azure-cli-configuration` (retrieved 2026-08-05: `AZURE_CONFIG_DIR` default `$HOME/.azure` / `%USERPROFILE%\.azure`).

### F8 — Azure API shape: `SecretClient.GetSecretAsync(name, version = default)` → `Response<KeyVaultSecret>` (`.Value` is the secret string); versions are implicit (latest when omitted), soft-delete exists, and access is RBAC/access-policy-gated [READ]

`GetSecretAsync(string name, string version = default, ...)` returns `Task<Response<KeyVaultSecret>>`; `KeyVaultSecret.Value` is the secret's current value, and omitting `version` returns the latest — rotation in the vault is *transparent* to the consumer unless a specific version is pinned (pinning would freeze the DB key; unpinned means vault-side rotation changes the DB key out from under the bank — so the operator must coordinate: rotate = rekey, or keep versions immutable and rotate via a new secret name + rekey). Azure Key Vault has soft-delete (deleted secrets recoverable for a retention window; strongly encouraged on by default per Microsoft docs). Access control is via RBAC (`Key Vault Secrets User` grants read) or legacy access policies; the caller needs `Get` permission. Network is required per call (no offline cache in this design; the secret value is fetched at every server start, and — like Bitwarden — could be cached to the key file as a recovery copy). Throttling and transient failures are handled by Azure.Core's retry policy.

**Evidence:** `https://learn.microsoft.com/en-us/dotnet/api/azure.security.keyvault.secrets.secretclient.getsecretasync` (retrieved 2026-08-05: signature + `KeyVaultSecret`); `https://learn.microsoft.com/en-us/azure/key-vault/general/soft-delete-overview` (retrieved 2026-08-05: soft-delete exists, permanent deletion without it).

### F10 — AWS auth bootstrap: the standardized chain is env vars → shared config/credentials files → SSO/IAM Identity Center → container → IMDS; the realistic local paths are the **shared credentials file** (`~/.aws/credentials`) or the **SSO token cache** (`~/.aws/sso/cache`), both plaintext files outside the DB [READ]

AWS SDKs and Tools Reference Guide ("Understand the credential provider chain"): access keys via environment variables (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`), web identity/OIDC, console-login (SSO) credentials, IAM Identity Center, assume-role, container (ECS/EKS), process, IMDS — searched in order until valid credentials are found, with automatic renewal. Shared config/credentials files live at `~/.aws/config` + `~/.aws/credentials` on Linux/macOS and `%USERPROFILE%\.aws\` on Windows (plaintext, per AWS docs "plaintext files"); SSO tokens are cached under the `sso/cache` directory keyed by session name (AWS CLI docs). For a local-first desktop tool the realistic members are the shared credentials file (static long-term keys — the repo's own S3 sync already uses this style via `BasicAWSCredentials(accessKey, secretKey)` in `S3CloudStore.cs:35-36`) or an SSO profile (short-lived tokens, refreshed by `aws sso login`). All bootstrap state is machine-local and DB-independent — same structural point as Azure: the *AWS identity* gates the secret, the secret never sits in client configs. Deltas vs Azure: no single CLI-token dependency (the chain is richer), but the shared-credentials-file path can contain long-term static keys whose compromise is total (mitigated by preferring SSO profiles; the .NET SDK resolves profiles via `CredentialProfileStoreChain`, which handles both files and SSO).

**Evidence:** `https://docs.aws.amazon.com/sdkref/latest/guide/standardized-credentials.html` (retrieved 2026-08-05: provider chain); `https://docs.aws.amazon.com/sdkref/latest/guide/file-location.html` (retrieved 2026-08-05: `~/.aws/config`, `~/.aws/credentials`, Windows path, "plaintext files"); `https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sso.html` (retrieved 2026-08-05: "authentication token is cached to disk under the sso/cache directory"); `src/AiRaccoon.Infrastructure/Sync/S3CloudStore.cs:35-36` (repo, READ).

### F11 — AWS API shape: `GetSecretValueAsync(new GetSecretValueRequest { SecretId = name })` → `SecretString`/`SecretBinary`; version stages (`AWSCURRENT`/`AWSPREVIOUS`) instead of opaque versions; KMS-backed at rest; rotation via a scheduled Lambda; every call is CloudTrail-logged [READ]

The Secrets Manager API: `GetSecretValue` takes `SecretId` (name or ARN), optional `VersionId`, optional `VersionStage` (default `AWSCURRENT`; `AWSPREVIOUS` to read the previous version); returns `SecretString` or `SecretBinary`; the docs recommend client-side caching (the SDK ships `SecretsManagerCache`). Rotation is a Lambda + `RotateSecret` flow that stages `AWSCURRENT`/`AWSPREVIOUS` — same coordination note as Azure: vault-side rotation without a DB rekey breaks the bank (the DB key must be the same bytes; the operator rotates the *vault secret* and rekeys the DB, or treats the secret as immutable). Secrets are encrypted at rest with AWS KMS (a per-secret CMK or the default `aws/secretsmanager` key); access control is IAM (a policy + role/credential with `secretsmanager:GetSecretValue`). Every `GetSecretValue` produces a CloudTrail log entry — DB opens become auditable events, a genuine delta vs local stores.

**Evidence:** `https://docs.aws.amazon.com/secretsmanager/latest/apireference/API_GetSecretValue.html` (retrieved 2026-08-05: request syntax, `SecretString`/`SecretBinary`, `AWSPREVIOUS`, caching recommendation, CloudTrail note).

### F12 — Threat-model delta for both clouds: the stolen DB is useless without the cloud identity (strongest at-rest story of all options), but server start gains a network dependency and a third-party account becomes a single point of compromise; token expiry is a new failure mode [INFERRED]

Reasoned from F7-F11 against the sibling report's table: at-rest theft — the DB alone yields nothing, and unlike keychain/keyfile there is no key material on the machine at all (unless cached); same-user snooping — no plaintext secret file to read, and the cloud calls are observable (CloudTrail) rather than silent; backups — nothing secret in the repo or config tree (only the vault/secret *names*, which are not secrets); offline start — **broken** (network + valid token required at every server start; a cached key file would fix this but re-introduces the local plaintext); account compromise — the cloud account (or a leaked `az` token / static AWS key) becomes equivalent to DB compromise, plus cloud-side misconfiguration (over-broad RBAC/IAM, soft-delete vs purge) is a new class of failure the local options don't have; unattended start — works while the CLI/SSO token is valid, fails with a *fixable* message otherwise. Cost: both services bill per secret (Azure Key Vault has a free tier; AWS Secrets Manager bills per secret per month — exact current prices NOT verified). The common pattern is the real value: **every cloud option reuses the machine's existing cloud-identity credentials as the bootstrap — no new secret to manage**; the vault/secret store holds the only new artifact, a 256-bit random value that can be generated by the setup verb.

**Evidence:** Reasoning from F7-F11 and sibling F9-F16; price claims deliberately left UNVERIFIED.

### F13 — Updated ranking: Keychain → raw-key file → SSH key (ed25519) → Azure Key Vault → AWS Secrets Manager → env var (removed); all new options slot below the local stores, above the status quo, and each is one PR [INFERRED]

Reasoned from F1-F12 and the sibling report: the local stores keep the DB openable offline and their exposure is bounded by the machine's trust boundary, which is the right threat model for a local-first MCP server; the SSH key is the best "no new secret" option because the bootstrap is a file the developer already protects (and 0600 by default), but it double-uses one secret and gains nothing over the key file in at-rest terms (both are a local file; the key file can even be *generated* with the same tooling). Azure KV vs AWS SM are functionally tied — both store a 256-bit raw key, both boot from existing CLI/SSO state, both add network+account dependence; Azure edges ahead for this repo only if the developer is Azure-aligned (the `.azure` CLI state question is machine-specific and UNVERIFIED here), AWS edges ahead on *implementation* because the repo already ships AWS SDK v4 (F9) — but that is a code-shape argument, not a security one, so the ranking keeps them adjacent. Env var stays last (sibling F16). One-PR feasibility: SSH provider — yes (no new packages for the unencrypted-ed25519 v1; ~60-line parser + provider + verb + rekey flow); Azure — yes (2 packages, `DefaultAzureCredential` provider, setup verb, ~150 lines); AWS — yes (1 package already in the same generation, `AmazonSecretsManagerClient` + `GetSecretValueAsync`, setup verb). What is *not* one PR is doing all three plus the keychain/key-file migration in a single change — pick the SSH provider first (zero-dependency, reuses an existing secret, matches the owner's question), then the cloud provider aligned with the developer's actual login state.

## Recommendation

1. **SSH-key provider is feasible and is the best answer to the owner's question** — derive from the **ed25519 seed** (not RSA; not passphrase-protected keys), `SHA-256("ai-raccoon-db-key/v1" ‖ seed)` or HKDF with the same label, return `x'<hex>'` through the existing `Password` channel (measured, F2). It ranks third overall, after Keychain and the raw-key file, because it adds no new secret to manage while reusing one the developer already protects — at the cost of doubling that secret's blast radius and being a plaintext file (F5, F13).
2. **Azure Key Vault (4.11.0 + Azure.Identity 1.21.0, both MIT/net10) and AWS Secrets Manager (4.0.100.7, Apache-2.0/net10, same SDK generation as the repo's AWSSDK.S3) are both one-PR integrations** with the same shape: raw 256-bit key in the vault, existing machine cloud-identity as the bootstrap (DefaultAzureCredential's AzureCliCredential path / the AWS shared-files-or-SSO chain — F7/F10), config (never secrets) in the settings table. Both drop to rank 4/5 for a local-first tool solely because server start becomes network- and token-dependent (F12).
3. **Implement in this order: SSH provider first (zero new dependencies, directly answers the question), then whichever cloud matches the developer's existing login state** — that machine-specific fact is UNVERIFIED (credential-directory probe declined), so the cloud choice should be gated on `az account show` / `aws sts get-caller-identity` presence at setup time rather than assumed.
4. Do **not** support passphrase-protected SSH keys or ssh-agent (F4); do **not** pin vault secret versions without a coordinated rekey flow (F8/F11); treat vault-side rotation as "rotate the secret AND rekey the DB" in one operation.
5. Reconcile the verb namespace (`ai-raccoon encryption <source>` vs the sibling's `config db-key`) before implementation; both reports agree the prompt belongs at setup time, never at server start (F14, sibling F14).
