## 1. Verdict summary

**Conditional approval — the feature shape is testable and most gates are honest, but three acceptance gates cannot pass as written and two more cannot fail when the feature is broken.**

- **MUST-FIX (design, not code):** A5's `IdleWatchdogTests` plan ignores verified FakeTimeProvider semantics (the first `Advance` after `StartAsync` is reliably lost; the "advance < timeout → not called" negative is vacuously passable). A6 contradicts §3.3 (1-minute poll vs "shutdown within ~5s" with a 2s timeout) and its "request reset the timer" half is unprovable in real time. A8's "idle test runs with extraction enabled" is vacuous (extraction interval floor is 1 minute — an extraction pass cannot fire inside a 2–5s window).
- **SHOULD-FIX:** A13's gate cannot fail if the `Program.cs ["serve"]` branch is forgotten (needs a routing seam); ServeRunnerTests block-forever/visibility mechanics are unspecified (needs ct-stop seam + case split); ServeRunnerTests are exposed to `AIRACCOON_DB_PASSPHRASE` poisoning (must use `TestData.EnvVarGate`); A4's busy-port test must hold the listener open (port-race).
- **Verified claims:** the "no test churn" claim HOLDS — zero literal `new ServerConfig(` in tests; exactly one target-typed 3-arg positional construction (`McpServerSetupHostTests.Config`) plus one in src (`CliOptionsExtensions.ToServerConfig`); a 4th positional `TimeSpan IdleTimeout = default` keeps both compiling (the design does say `default`, §3.5). The host-shape pattern (`GetServices<IHostedService>()` ShouldContain/ShouldNotContain), the FakeTimeProvider pattern, and the `WebApplicationFactory<Program>` + `HttpClientTransport` + `McpClient` E2E pattern all exist exactly as the design claims.

## 2. Findings

| ID | Severity | Gate | Why | Concrete fix |
|----|----------|------|-----|--------------|
| F1 | **MUST-FIX** | A6 | **Poll-interval contradiction.** §3.3 fixes the loop at `PeriodicTimer(TimeSpan.FromMinutes(1), …)`; A6 demands shutdown "within ~5s real time" with `IdleTimeout = 2s`. Worst case the shutdown fires one full poll late: 2s timeout + 60s poll → up to ~62s. A6 is unsatisfiable as written. | Derive the poll interval from the timeout: `poll = timeout < 4min ? timeout/2 : 1min` (bounded below, e.g. ≥ 250 ms). 2s timeout → 1s poll → shutdown ≤ ~3s ✓. Add a unit test pinning the derivation (e.g. `IdleWatchdog.PollIntervalFor(timeout)`), and state the formula in §3.3. Also: A6's real-time bound should be generous (≤15s) — precision lives in the deterministic test (F3), not in CI timing. |
| F2 | **MUST-FIX** | A5 | **FakeTimeProvider semantics.** Verified: `StartAsync` does not run `ExecuteAsync` on the caller thread; the first `Advance` immediately after `StartAsync` is reliably **lost** (timer not yet registered). A5's first case — "advance < timeout → `StopApplication` not called" — is exactly the vacuous-negative trap from the project's hosted-service testing skill: it passes when the advance is lost *and* fails (despite correct behavior) if the timer ever registers in time. The reset case ("NotifyActivity mid-way resets the timer") is also unassertable without counters. | Rewrite the A5 plan with the repo's proven `ExtractionHostedServiceTests.ExecuteAsync_PollLoop_…` mechanics: (1) `StartAsync` → real settle (`await Task.Delay(50, …)`) **before** the first `Advance`; (2) settle (`Task.Delay(100, …)`) after **every** `Advance` before asserting; (3) assert on a **`StopApplication`-call counter** in a fake `IHostApplicationLifetime` (interface — trivially fakeable: record `StopApplication()` calls, back the three events with `CancellationTokenSource`), asserting `count == 1`, never on "no throw"; (4) the reset case asserts via an **invocation counter**: `Advance` to 0.9×timeout → `NotifyActivity()` (counter==1) → `Advance` past the original deadline → `StopApplication` count still 0 → `Advance` past the *new* deadline → count==1. Also pin the §3.3 baseline: zero requests → fires at exactly one timeout. |
| F3 | **MUST-FIX** | A6 | **Real-time flakiness + unprovable reset half.** With `IdleTimeout = 2s` and a real `TimeProvider`, "start, make one tool call, shutdown within ~5s" requires the call to land inside the 2s window on a CI box; under load the watchdog can fire first and the test still passes ("shutdown within 5s" holds) — i.e. **a broken `NotifyActivity` wiring passes the gate**. Also the reset case is proven only if the request *succeeded* before shutdown, which the gate text doesn't demand. | Split A6: **(a) deterministic wiring test** — in-process real host (`McpServerSetup.CreateServerHost`), real HTTP traffic through the real middleware, but a **fake TimeProvider injected via a host seam**: add an optional `TimeProvider?` param to internal `CreateServerHost` (or replace the DI `TimeProvider.System` singleton; it is already a DI singleton, `Dependencies.cs:33`). Start host (`IdleTimeout=2s` in config) → settle → make a real `CallToolAsync` over `HttpClientTransport` → `Advance` past timeout → settle → assert `StopApplication` fired and the run task completed 0. This proves wiring (middleware→signaler→watchdog) with real traffic and zero timing flakiness. **(b) real-time smoke** — no requests, 2s timeout, assert shutdown within a generous 15s bound (after F1). **(c)** `--idle-timeout 0` never shuts down — assert with the fake clock (advance far past any timeout → still running), not by real-time waiting. |
| F4 | **MUST-FIX** | A8 | **Vacuous extraction variant.** "A6's idle test runs with extraction enabled" cannot fail: `ExtractionConfigKeys.ParseIntervalMinutes` requires `minutes > 0` (floor = 1 minute, default 30), so an extraction pass **cannot land inside a 2–15s real-time window** — the gate is green even if `ExtractionHostedService` called `NotifyActivity` every pass. | Replace the timing-based variant with a **shared-clock unit test**: construct `ExtractionHostedService` (FakeStore with an extraction-call counter, `extract.interval-minutes.global = 1`) and `IdleWatchdog` on the **same** `FakeTimeProvider` + a fake lifetime; start both; `Advance` past the extraction interval → settle → extraction counter > 0 **and** `StopApplication` count == 0 (extraction passes do not reset); `Advance` past the watchdog timeout → settle → count == 1. This is deterministic and pins exactly the §3.3 "What is NOT activity" claim. Keep the grep as a named **review** gate (see §3, A8 — a review gate is legitimate); a reflection/IL pin is not worth it (no Mono.Cecil in the repo; source-scan tests don't know the repo path at runtime in CI). |
| F5 | SHOULD-FIX | A13 | **The routing gate cannot fail on the primary bug.** The `CliCommandRunnerTests` negative ("no serve path leaks into `ConfigCommands`") pins only the runner's catch-all (`ConfigCommands.cs:71` → exit 1 "unhandled command"). It passes **both** when Program.cs routes `["serve"]` correctly *and* when the branch is forgotten (then the runner *is* what runs serve — same behavior, bug shipped, gate green). | Extract the dispatch decision into an internal seam Program.cs calls, e.g. `internal static class EntryPointRouter { Task<int> RunAsync(CliParseResult, ServerConfig, TextWriter stdout, TextWriter stderr, TextReader stdin, CancellationToken) }` with an injectable `IServeRunner` (or a `Func<…>` delegate). Test: serve args → `ServeRunner` invoked, `ConfigCommands` not; config-verb args → `ConfigCommands` invoked, `ServeRunner` not. Keep the negative pin as a secondary assertion. (A `WebApplicationFactory<Program>`-based routing test is the wrong tool: ServeRunner blocks on `WaitForShutdownAsync` and the factory path swaps Kestrel for TestServer, so bound-URL/blocking semantics are not representative.) |
| F6 | SHOULD-FIX | A2/A3/A9 | **Blocking-run mechanics unspecified.** `ServeRunner.RunAsync` blocks until shutdown; a plain `StringWriter` only reveals stdout **after** the run returns. A3's "an `McpClient` reaches `/mcp` at that URL" needs the URL *while* the server is running — impossible with `StringWriter` for `--port 0`. | Specify the stop seam: `RunAsync` uses `host.WaitForShutdownAsync(ct)` (same as `HostExtensions.RunAsync`), and `HostingAbstractionsHostExtensions` semantics make **ct-cancellation trigger `StopApplication`** — tests cancel a CTS and assert exit 0. Split A3: (a) `--port 0` → assert the bound URL in stdout **post-hoc** after the ct-stopped run (works with `StringWriter`); (b) client-reachability → use a **fixed free port** (URL known a priori, no mid-run stdout read), run `RunAsync` on an un-awaited Task, connect `McpClient`/`HttpClientTransport`, call a tool, cancel ct, await exit 0. For A9's renderer integration the same post-hoc pattern suffices. If any test needs the line mid-run, use a small line-signaling `TextWriter` (writes push to a `TaskCompletionSource`). |
| F7 | SHOULD-FIX | A2/A3/A4/A9 | **Env-var poisoning.** ServeRunner resolves the encryption key and probes bank decryption; a dev machine's `AIRACCOON_DB_PASSPHRASE` can turn A2's "exits 0" into `ExitCode.FailedToOpenEncryptedBank` (2) on an unencrypted temp bank. `CliCommandRunnerTests` already gates this ("process-global … must be cleared during a run"); ServeRunnerTests must too. | In ServeRunnerTests/ServeE2ETests fixtures: clear `EnvEncryptionKeyProvider.EnvVarName` under `TestData.EnvVarGate` (exact `CliCommandRunnerTests.Run` pattern) for every run that probes decryption. |
| F8 | SHOULD-FIX | A4 | **Port-race flakiness.** `McpServerSetupHostTests.FreePort()` binds port 0 and *releases* before use — between release and Kestrel bind another socket can take the port, turning a "busy-port" test into a green unrelated-to-bug pass (or worse, a bind-success). The design says "with the port held by a `TcpListener`" but doesn't pin the mechanics. | Bind `new TcpListener(IPAddress.Loopback, 0)`, `Start()`, read the port from `LocalEndpoint`, **keep the listener open** for the entire `RunAsync` (dispose in `finally`). Zero race. Also: ServeRunner's catch around `StartAsync` must target bind failures (`IOException`/`SocketException`/`AddressInUseException`), not `Exception` — otherwise a ct-cancel during startup is misreported as `PortInUse`. |
| F9 | SHOULD-FIX | A2 (trait) | **"Unit/Fast" vs embedding bootstrap.** ServeRunner calls `EnsureEmbeddingAvailabilityAsync` (best-effort, 30s bound, may download the bundled ONNX model on a fresh machine — `EmbeddingAvailability.cs`). A "Unit/Fast" `ServeRunnerTests` could burn up to 30s or hit the network on first CI run. | Pre-ensure the model in the fixture via `TestData.CreateBundledModel().EnsureAsync(...)` (E2E precedent), or mark `ServeRunnerTests` Slow. |
| F10 | NIT | A12 | **Unpinned "still logs" half.** A12 claims bare `--transport http` "still logs `HttpTransportListening` on stderr", but no existing test pins that log (the only LoggerMessage pin is `LoggerMessageTests` → `McpServerSetup.Log.HttpsTransportNotSupported`; E2E factories run at Warning minimum, so the Information EventId-2 line is invisible there). "Full `dotnet test`" would go green even if the log vanished. | Either add a `LoggerMessage`-style pin for `HostExtensions.Log.HttpTransportListening` (EventId 2, Information) alongside `McpServerSetup.Log`'s, or reword A12 to assert what the suite actually covers (host-shape green + watchdog-default behavior change documented). |
| F11 | NIT | A11 | **Parser matrix gaps.** `90s/30m/4h/1d/0` + `4x`/``/`-1` is specified; whitespace, uppercase units (`4H`), fractional (`1.5h`), and **overflow** (`999999999h` → `TimeSpan` constructor throws unless guarded) are not. | Extend the matrix: reject whitespace/case/fractional (or pin them accepted — decide explicitly), and require overflow to render a parse error, never a crash. `0` and `0s` equivalence. |
| F12 | NIT | §3.5 | **Claim wording.** "existing direct `ServerConfig` constructions in tests" — literally there are **zero** `new ServerConfig(` in tests; exactly one target-typed `new(port, transport, …)` (3 positional args, `McpServerSetupHostTests.cs:158`) and one in src (`CliOptionsExtensions.cs:29`). Substance is correct: a 4th defaulted positional param keeps both compiling (design does say `= default`). | No code impact; reword to "positional constructions" for precision. |

## 5. Missed test cases (not covered by A1–A13)

1. **Middleware unit test** — the only direct pin that *any* request to `/mcp` (initialize, ping, list, GET stream) signals, not just tools/call (Q2's decision); also that non-`/mcp` paths don't signal.
2. **Zero-request baseline** — fresh server lives a full timeout with no traffic (§3.3 states it; no gate names it; add to IdleWatchdogTests).
3. **Idempotent shutdown** — `StopApplication` exactly once across multiple overdue ticks, and a late `NotifyActivity` after shutdown initiated → no throw (Interlocked path).
4. **Poll-interval derivation** (F1) — `PollIntervalFor(2s) ≤ 1s`, `PollIntervalFor(4h) = 1min`.
5. **ServeRunner stdout hygiene** — stdout contains exactly the one URI/JSON line, nothing else (logs stay on stderr); assert `stdout` equality, not `ShouldContain`.
6. **Force-http on serve** — config with `Transport = Stdio` passed to ServeRunner still binds HTTP and reports the URL.
7. **`--transport` conflict warning** (Q5) — one-line stderr warning; warning path only when the flag was explicit.
8. **Watchdog shutdown exit code** — E2E asserts the run task returns `ExitCode.Success` (0) after idle shutdown.
9. **LoggerMessage EventId pins** for `ServeRunner.Log` (601–604) and `IdleWatchdog.Log` (610–612) — today only `McpServerSetup.Log` is pinned; the design's EventId-allocation appendix would otherwise be unenforced.
10. **IdleTimeoutParser overflow/case/whitespace/fractional matrix** (F11).
11. **`--idle-timeout 0` at the host level** — HTTP host with Zero registers no watchdog (A7 covers presence; add the behavioral twin: advance a fake clock far past any timeout with Zero → nothing happens — cheap, closes the DI-registration-dropped hole from the other side).
12. **E2E collection hygiene** — `ServeE2ETests` must opt into `E2ETestCollection` (serial) or it will race the other E2E tests on the env/port surface.

## 6. Bottom line

The design's gate table is ~70% honest and ~100% feasible with existing infrastructure — every named file exists (`McpServerSetupHostTests`, `ExtractionHostedServiceTests`, `CliCommandTreeTests`, `CliArgsTests`, `CliCommandRunnerTests`, `McpServerFactory` + `HttpClientTransport`/`McpClient`). The four MUST-FIX items (F1–F4) are all **design-doc edits, not code** — fix the poll interval, respecify A5/A6 around verified FakeTimeProvider semantics and a TimeProvider host seam, and replace A8's timing variant with the shared-clock test. A5, A6, A8, and A13 are not honest gates as written and would certify broken or vacuous behavior; the rest are strong, and the "no test churn" claim is verified correct.
