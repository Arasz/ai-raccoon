## Attack-point judgments

**(a) Probe false-positive surface — acceptance is sound.** The discriminator set {400, 405, 406} deliberately excludes 404 (the most common foreign-server answer for an unknown `/mcp` path); a plain web server's 400/405/406 bodies (HTML/text) never contain the literal `jsonrpc`. The only realistic false-positive is a **different JSON-RPC/MCP-speaking server** answering `POST /mcp` with a JSON-RPC error body. That requires (foreign server) ∧ (path `/mcp`) ∧ (error status in set) ∧ (`jsonrpc` in body) — a narrow intersection, and the resulting damage is bounded: serve prints the URL, emits the attach-provenance line on stderr (EventId 605 — a human watching the log sees "attached to the server already listening"), exits 0, and the client that later dials the URL gets an MCP-ish server rather than garbage. No stronger discriminator exists without a protocol addition (banner handshake — deferred by R15 for measured reasons: no standard, ~110-line SDK fork). The R14 acceptance is therefore honest: the body check is the strongest cheap signal, the failure mode is self-limiting and diagnosable, and the alternative (no attach, PortInUse) would burn the primary use case. Residual risk accepted by design — no finding beyond noting it is now an explicit, documented trade-off.

**(b) Attached-mode `--mcp-entry` staleness — NOT a finding.** The printed entry is a snapshot of a live server, exactly like the URL the **owning** process itself prints: the owner's watchdog can shut that server down 4 h later, making the owner-printed URL equally stale. Staleness is inherent to any printed locator; the watchdog is the designed reclamation mechanism, and a client actually configured against the URL generates the traffic that resets the deadline. Attached mode adds no new staleness class — and the stderr provenance line distinguishes attach from ownership for anyone scripting it. Behavior matches R14 §3.7 item 3 exactly ("print the same URL line to stdout … exit 0").

**(c) Static `ProbeClient` — acceptable.** Process-lifetime singleton with a 1 s `HttpClient.Timeout`; loopback targets only; no DNS/channel staleness concerns; socket reuse is desirable for the 2-attempt probe. Non-disposal is correct for the process lifetime. See F2 for the static-class-rule nuance.

**(d) `ResolveIdleTimeout` fallback — acceptable.** The validator makes invalid values unreachable (`CliArgs.TryParse` returns false → Program renders errors and exits before ServeRunner). The defensive `TryParse ? value : 4h` fallback is dead code in practice and arms the watchdog (fail-safe direction) if it ever becomes reachable through a refactor. No finding.

**(e) Real-time smoke flakiness — LOW risk, one hardening change.** Mode A (host dies before the URL prints) requires the pre-URL phase — temp-bank creation + SHA-256 of the 23 MB bundled model + Kestrel start — to exceed 2 s against a deadline that starts at host construction. Measured ≈0.2–0.3 s here (≈10× margin); every evidence run passed. The window is real but narrow; F1's one-line bump removes it cheaply. Mode B (shutdown > 10 s after URL) has ~8 s slack and is safe.

**(f) Full-suite flake — NOT caused by this feature; marginal load contributor at most.** The failing step is `FileWatcherSteps.cs:1348` `ThenExactlyOneContentSetHoldsThatPath`, which polls via `StepUntilAsync` (FileWatcherFeatureContext.cs:113) bounded by **5 real seconds** while a digest pipeline performs real ONNX embedding + SQLite writes. That bound is starved by any CPU/IO spike in the same process. One premise correction: the real-time serve smokes are `Category=Unit`/`Fast` with no `[Collection]`, so they run in the **default parallel collection** (alongside the 899-test unit suite), not the serialized E2E collection — they add ~7–15 s of wall time and transient load (≈10 real Kestrel hosts, MCP clients, timer churn) to the parallel lane, which runs concurrently with the non-parallelizable Reqnroll features. So the serve tests are a *plausible* contributor to the load that starves the BDD poll, but the flake mechanism is pre-existing timing sensitivity (it can equally be triggered by any other collection's spike, machine state, or a cold ONNX first-load). No serve code path touches the watcher/digest pipeline. Recommendation: do not block on it; if the re-run flakes again, (1) lengthen `maxRealSeconds` for that step, and/or (2) move the three real-time ServeRunner tests into a serialized collection, as cheap insurance.
