### Q1 — Raw-spelled shared rows: servable, so the ingest rule is correct and the prose is wrong

**Verdict: a raw-spelled shared row IS servable in a shared/all-scope bank query.** The alias fold is a *project-id* fold (gate + project predicate); the shared context is project-agnostic on both legs:

| leg | predicate | source |
|---|---|---|
| FTS / filter | `scope = 'shared'`, no project filter | `ContextFilterProvider.cs:23` |
| vector KNN partition | `ctx = 'shared'` for every `scope='shared'` row, regardless of `project_id` | `MemorySql.cs:813` |
| project/custom | `project_id = @projectId AND scope = 'project'` (canonical id after `ToolGate.RequireAsync` fold) | `ToolGate.cs`, `ProjectRows.ProjectScope` |

Copy/store facts confirm substance: `aib` has 1 row and it is shared; `job-search-ai-assistant` has 8 shared rows; all 237 shared rows are in the harness store. For the 106 raw-spelled **committed** rows the reason is right (project predicate can never match them); for the 9 shared ones it is false.

**Therefore:** the ingest rule (`OR scope='shared'` with no project filter) is **parity-correct — do not change it**. Parity is not contaminated; no re-run is required for the numbers. The artifacts needing fixing are `build_project_corpus.py` (reason + split counts), the regenerated corpus header, and consequently the manifest copy in `params.json`/`results.json`/the report — with the regeneration flow described in F2. If the golden is frozen before the corpus is regenerated, `report._exclusion_lines` must at least render the committed-vs-shared truth from the store's observed buckets.

**On the report line "project buckets in this store: … aib … job-search-ai-assistant …":** substance yes — those project_ids *are* present in the store (via their shared rows), so `_bucket_projects` is literally correct. Wording no — listing them among project buckets implies their committed rows were ingested when they were explicitly excluded. Fix per F3.
