# Research: fixing the zero-shot promotion classifier's non-discrimination

**Date:** 2026-08-13
**Question:** How should the zero-shot promotion classifier's measured failure to discriminate promotion-worthiness (F1 0.46, near chance) be fixed — with a better vector representation, or by removing the embedding-based promotion gate in favour of the already-calibrated mechanical scorer?

```chart:bars
title: promotion signal quality — Spearman vs usefulness labels (higher is better)
supervised positive-centroid embedding (LOO): 0.04
multi-prototype embedding (LOO, upper bound): 0.36
mechanical PromotionScorer (holdout): 0.69
```

## Findings

### F1 — Usefulness is not encoded in the content embedding [MEASURED]

The 384-d embeddings of the 55 promotion-labeled rows show no cluster structure by usefulness: mean
cosine similarity is signal–signal 0.393, noise–noise 0.382, signal–noise 0.382. A promotable fact
is, on average, as close to a noise entry as to another promotable fact. Whatever "portability"
means to the rubric (RUBRIC.md: "is this true and useful outside this repo?") is not a direction the
bundled embedding model captures.

**Evidence:** `python3` 3.14.7 on this machine (macOS, `/Users/arasz/RiderProjects/ai-raccoon`).
Read the 55 embeddings from `~/.ai-raccoon/memory.db` `entries.embedding` (1536-byte float32[384]
BLOBs), joined to `/tmp/promotion-fixture.json` by hash; computed pairwise cosine in stdlib `math`.

### F2 — Even a fully supervised embedding classifier caps at F1 0.59 / Spearman +0.36 [MEASURED]

Leave-one-out supervised classifiers trained on the *true* usefulness labels — the strongest thing
any embedding-only approach could ever do — still cannot rank: a positive-centroid scores
F1 0.48 / Spearman +0.04; a nearest-positive-minus-nearest-negative prototype scores F1 0.59 /
Spearman +0.36 (the best of the methods tried); k-NN scores F1 0.47–0.56 / Spearman +0.18–0.30.
These are upper bounds on any zero-shot variant, and they sit well below usable.

**Evidence:** same run as F1; leave-one-out evaluation over the 55 labeled rows (16 signal ≥2,
39 noise ≤1). Methods: supervised positive centroid, multi-prototype (max-sim-to-positives −
max-sim-to-negatives), k-NN k∈{1,3,5}. The shipped single-reference classifier is F1 0.46 [READ,
docs/work/2026-08-13-zero-shot-threshold-calibration.md] — so a better representation buys at most
≈0.13 F1, and still fails as a gate.

### F3 — The mechanical PromotionScorer already does promotion quality at Spearman +0.69 [READ]

The scorer that ships alongside the classifier (provenance-archetype prior + zero-centred content
evidence + organic refinement, ADR-0018 round-3 lane-A) measures Spearman +0.687 on a 79-row
held-out set and +0.660 on the 292-row full set — more than 30 points of correlation above the best
embedding-only ceiling from F2. Promotion quality is not the missing piece; a *second* signal is
being bolted on that is strictly worse.

**Evidence:** docs/adr/0018-promotion-scoring-v2.md, "Round-3 lane-A" measured-numbers table
(`PromotionScoringRealDataTests`); gates holdout ≥0.60.

### F4 — The "ONNX instruct model" is specified but never implemented or downloaded [READ]

The plan and the benchmark name a "Qwen2.5-0.5B ~350 MB ONNX instruct model" for Approach B/C, but no
such model exists: `OnnxInstructPromotionClassifier.ClassifyCandidateAsync` (model-enabled branch)
embeds the candidate and a canonical reference through the bundled *embedding* model and compares
them by cosine at threshold 0.07 — it never loads or invokes an instruct/LLM. `BundledModel`
downloads only the 22 MB all-MiniLM embedding model + vocab (pinned SHA-256); there is no other
model-download path. `promotion model enable` (`PromotionCommands.SetEnabledAsync`) writes only the
`promotion.model.enabled` settings row and downloads nothing. No Qwen file is on disk, and the string
"Qwen" appears nowhere in `src` (only in the benchmark test's hardcoded report text and docs).

**Evidence:** src/AiRaccoon.Core/Memory/Promotion/OnnxInstructPromotionClassifier.cs:49-56;
src/AiRaccoon.Infrastructure/Embedding/BundledModel.cs:17-29,60-61 (only asset downloaded);
src/AiRaccoon/Setup/Cli/Commands/PromotionCommands.cs:11-16 (flag write only);
`find ~ -name '*.onnx' -o -name '*.gguf' -o -name '*.safetensors'` → only the 22 MB embedding model
and a 21 MB embedding gguf; grep for `Qwen|Instruct|0.5B` in `src` matches only comment/name text.

### F5 — The comparative benchmark measured latency only, never quality [READ]

The report `docs/work/2026-08-13-v4-promotion-classifier-benchmark-report.md` is generated by the
test `PromotionClassifierComparativeBenchmarkTests.CompareClassifiers_ApproachA_vs_ApproachB_vs_ApproachC`,
which loops the 181-row `search_quality_eval.json` (search *queries*, not promotion candidates)
through Approaches A/B/C and records only `Stopwatch` latency and GC allocation bytes. It deserializes
`usefulness_grade` but never uses it, computes `eligibleA/B/C` counts and discards them, and writes a
hardcoded markdown template — including the "Qwen2.5-0.5B / ~350 MB" figures — to the report file. It
never computes the correlation (r/MRR/nDCG) the WP5 plan promised, and the dataset is the wrong axis
in any case (search-result usefulness grades, not promotion portability). So the zero-shot classifier's
promotion-worthiness discrimination was never measured at implementation time; the threshold shipped
uncalibrated, and the first such measurement was the post-ship F1 0.46 calibration (F2).

**Evidence:** tests/AiRaccoon.Tests/Integration/PromotionClassifierComparativeBenchmarkTests.cs:53-141
(dataset = `search_quality_eval.json`, measures Stopwatch/GC only, `eligibleA/B/C` unused, hardcoded
report template at :120-136); the report file itself shows only latency/memory columns, no quality
column.

### F6 — The classifier is inert by default but is running in the live bank [READ]

`SharedExtractionRunner.FilterByClassifierAsync` returns rows unchanged when `!classifier.IsModelEnabled`
(the default), so out of the box the zero-shot path gates nothing. But the live bank has
`promotion.model.enabled = true` in `settings`, so the pre-screen (and the misnamed ONNX branch) is
running ahead of the mechanical scorer on every propose pass — passing almost everything at threshold
0.07, and adding no information.

**Evidence:** src/AiRaccoon.Core/Memory/SharedExtractionRunner.cs:76-97 (short-circuit) and :39
(called before `RankAll`); `settings` table in `~/.ai-raccoon/memory.db` reads `promotion.model.enabled
= true`, `extract.mode.global = propose`.

### F7 — The fix is to remove the embedding-based promotion gate, not to re-represent it [INFERRED]

Reasoning from F1–F3: the embedding ceiling (+0.36 Spearman) is far below the mechanical scorer
(+0.69), and F1 says it cannot be a gate, so no representation change recovers it. From F4: the
"semantic" branch is a stub, not a real model. From F5: the approach was never quality-validated. From
F6: the component is already inert by default, so removing it costs nothing in the default path. The
actionable fix is (a) delete or stop registering `ZeroShotVectorPromotionClassifier` and the
`CompositePromotionClassifier` pre-screen, leaving `PromotionScorer` as the sole promotion-quality
signal; and (b) either implement a real opt-in instruct model (with download-on-enable) or delete
`OnnxInstructPromotionClassifier` rather than keep a misnomer. Embeddings remain where they
demonstrably work: retrieval/semantic search and noise rejection of stereotyped text, not portability
judgement.

## Measured answer — A/B/C on the 55-row promotion fixture (2026-08-13)

The user's follow-up was answered by actually running the model: download
`Qwen2.5-0.5B-Instruct-q4_k_m.gguf` (469 MB, SHA-256 `74a4da8c…`) and judge each of the 55 rows
through LLamaSharp (greedy sampling, the rubric's 0-4 scale as a single-digit answer). All 55 rows
parsed.

| Signal | Spearman vs usefulness | best F1 (signal ≥2) |
|---|---:|---:|
| A — mechanical PromotionScorer | **+0.397** | **0.596** |
| B — Qwen2.5-0.5B judge | +0.132 | 0.457 |
| C — combined (mean of A, B) | +0.084 | 0.457 |

Qwen is near-chance and actively mis-grades: it rates obvious noise rows (u=0, scorer 0.43–0.50) as
"4", and rates genuine durable rows (u=3, scorer 3.56) as "0". Fusing it into the scorer *lowers*
the correlation (+0.397 → +0.084). The model gives nothing — worse than nothing — so the decision is
to remove the promotion-classifier feature and restore the mechanical scorer as the sole promotion
signal.

**Evidence:** `dotnet test --filter TempPromotionAbcHarness` (throwaway harness, since deleted) on
this machine; fixture `/tmp/promotion-fixture.json` (55 rows, the reference-labels joined to the live
bank); model at `~/.ai-raccoon/models/qwen2.5-0.5b-instruct-q4_k_m.gguf`. The scorer's +0.397 on this
fixture is below ADR-0018's +0.70 because the fixture is the small, noise-skewed promotion subset and
the labels are joined to live-bank content that has drifted since labeling — the A/B/C comparison is
unaffected since all three see the same rows.

## Still open

- Whether a *larger* instruct model (not the 0.5B) would judge portability — the 0.5B clearly cannot;
  a bigger model is out of scope and would reintroduce the local-LLM dependency the project avoids.
- Whether the zero-shot **noise filter** (`ZeroShotEmbeddingNoisePolicy` + `BundledNoiseVectorProvider`),
  a separate concern for rejecting stereotyped noise (turn-mirrors, transcripts, status dumps), holds
  up to the same labelled-data scrutiny — its 11/12 result was against noise anchors, not promotion
  usefulness, and was not re-measured here.
