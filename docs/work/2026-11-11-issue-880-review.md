# Research: concurrent vector-search performance in issue #880

**Date:** 2026-11-11 **Question:** Which claims in issue #880 still describe current behavior, and what improvement approach and plan best address the remaining concurrent-search risk?

## Findings

### F1 — Issue #880 accurately identified the vec0 overflow-read bottleneck in 1.59.3 [READ]

The issue's diagnosis was not merely a hypothesis: ADR-0133 records the sampled live-server `pread`/cipher path, notes that vec0 incremental blob reads bypass SQLite's page cache, and reports the 64 MB cache A/B. That supports the causal
claim for the 1.59.3 metadata-column layout. The per-option timing and CPU figures in the issue are owner-reported measurements; this review did not rerun them.

**Evidence:** [Issue #880](https://github.com/Arasz/ai-raccoon/issues/880); `docs/adr/0133-ctx-is-the-vec0-partition-key-again.md:15-20`.

### F2 — The broad all-context scan claim was addressed by ADR-0133 and release 1.59.4 [READ]

ADR-0133 restores `ctx` as a partition key for `vec_entries`, `vec_structure`, and `vec_code`, so matching KNN queries prune other contexts' chunks. Its copy-bank comparison reports one-search wall time improving from 0.23 s to 0.10 s and
20-search wall time from 3.94 s to 1.21 s, with server system CPU falling from 76.4 s to 14.2 s. The 1.59.4 changelog describes the same shipped change. Therefore the issue's statement that every KNN scans every project's vectors describes
the pre-fix schema, not the intended/current schema after 1.59.4.

**Evidence:** `docs/adr/0133-ctx-is-the-vec0-partition-key-again.md:22-47`; `docs/changelog/1.59.4-partitioned-vector-search.md`.

### F3 — Partitioning accepts a measured storage cost and does not solve a single dominant context [READ]

The change increases the measured 995 MB bank to 1,051 MB (about 56 MB or 5.6%). A search still reads chunks in its own context; ADR-0133 says a context that contains nearly the whole bank sees little benefit and identifies an in-process
vector store as a possible follow-up. ADR-0068's earlier small synthetic probe is not a sound reason to reverse the decision: it measured a different corpus and single-query latency, and is explicitly superseded.

**Evidence:** `docs/adr/0133-ctx-is-the-vec0-partition-key-again.md:38-57`; `docs/adr/0068-ctx-is-a-vec0-metadata-column-not-a-partition-key.md:25-42`.

### F4 — Live caller-visible search still queued heavily under concurrency after 1.59.4, but the cause is unlocated [READ]

A later live run measured about 0.7 s for one call and about 14.2 s for batches of 20, with throughput near 1.4 searches/second. Server telemetry in that window reported vector search at 10.8 ms p50 / 13.8 ms p95 and total search at 203 ms
p50 / 386 ms p95. The report explicitly says these data do not identify whether the queue is in the MCP host, transport, or server, and are not comparable to the ADR copy-bank test. This makes an unconditional vector-cache rewrite or KNN
semaphore premature: neither is shown to address the observed live end-to-end delay.

**Evidence:** `docs/work/2026-10-19-live-parallel-search-1-59-4.md:13-33`.

### F5 — The next improvement should first locate queueing, then optimize only the measured hot stage [INFERRED]

This follows from F2 and F4: the identified database scan was substantially reduced in an isolated 1.59.4 comparison, while a later end-to-end run still had poor caller-visible throughput and much shorter measured vector-phase times.
Instrumentation across request admission, storage/search phases, and response delivery should distinguish queue wait from service time. If vec0 reads in a dominant single context remain expensive, benchmark an in-process vector cache
against the partitioned baseline, including invalidation and memory cost. If queue wait is elsewhere, fix that queue instead. Add a KNN concurrency cap only if the new measurements show concurrent KNN service time or system CPU degrades
under load.

### F6 — The issue's 1.59.3 figures have not been independently reproduced in this review [UNVERIFIED]

The original measurements and `sample` stack counts were not rerun here. The current repo contains a later ADR that cites the same diagnosis and records a controlled before/after copy-bank measurement, but that does not independently
validate each value in the issue body.

## Proposed approach and plan

1. **Establish the current baseline.** Record deployed CLI/server version, schema, context-size distribution, and bank size. Run the same fixed search set at concurrency 1, 8, and 20 for at least three rounds; capture caller wall time,
   throughput, server CPU, and per-stage timings.
2. **Separate queue wait from service time.** Add or use bounded measurements for request admission/queue wait, vector query, FTS, fusion/snippet work, and response serialization/delivery. Keep client-side batch timings alongside server
   timings so the transport boundary is visible.
3. **Choose the smallest fix from the profile.** If KNN service time and direct reads dominate within a large context, prototype an in-process vector cache behind a feature flag. Define bounded memory use, context/model/schema versioning,
   and write/delete/rebuild invalidation before implementation. Compare it against partitioned vec0 for identical result sets and concurrency. If MCP/server admission or response handling dominates, improve that queue/path instead. Use a
   semaphore only if measured resource contention supports it.
4. **Gate and stage rollout.** Require search-result equivalence, concurrent read/write correctness, cache invalidation coverage where applicable, memory ceiling, and benchmark evidence on both a large-context bank and many-small-context
   bank. Keep the partitioned vec0 path as fallback during the experiment; roll out only if the target workload improves without unacceptable storage or memory cost.

## Still open

- Which exact server/CLI version and schema served the 2026-10-19 live run, and has the deployment since changed?
- Where is the queue located between MCP dispatch, storage search, and response delivery? Existing telemetry does not settle this.
- What are the real context-size and vector-count distributions, and what memory budget could a cache use?
- Does a concurrent cache prototype improve end-to-end throughput after cache warmup while preserving write visibility and crash recovery?
