# MOE code-reviewer report — HTTP serve-mode design

Review of: `docs/work/2026-08-06-http-serve-design.md` (394 lines)
Reviewer lane: architecture, security, robustness, honesty of claims
Date: 2026-08-06 · Branch: `task/switch-from-stdio-to-http`

---

## 1. Verdict

**APPROVE-WITH-CHANGES** — the architecture (single watchdog service + atomic timestamp, foreground serve, stdout reporting, busy-port fail-fast) is sound and mostly minimal, but two spec-internal defects must be fixed before implementation (a DI wiring claim that is false and would throw at first request; a tick-period that makes the design's own acceptance gate A6 impossible), and the Q1 default should be gated to `serve` so an existing launch path is not changed with no opt-out.

## 3. Answers to the five open questions

### Q1 — Watchdog default applies to bare `--transport http` launches (4h, no opt-out on that path)

**Ruling: reject the design's choice; gate the default to `serve` only.**

The design's leak argument ("a headless HTTP server with no requests for 4h is a leak") is directionally right, but the cost is a semantic change to an existing launch path whose users **cannot turn it off** — the escape hatch (`--idle-timeout 0`) exists only on `serve` (§3.3 explicitly). That combination is a trap: any script, supervisor, or tmux session that has been running `ai-raccoon --transport http` since before this feature gets a silent `exit 0` death one idle afternoon, with no way to have opted out. The design's own honesty principle ("surprise beats honesty", §3.2, applied to ports) cuts the other way here. The bare path is undocumented, which shrinks the blast radius but does not remove it — undocumented users are still users, and they are the ones least likely to read the changelog. Gating costs one line in Program.cs (zero out `IdleTimeout` on the bare path before `CreateServerHost`) and keeps "serve is where the new defaults live and where help text announces them". If the owner wants bare launches protected too, that is a separate decision that must come with a root-level `--idle-timeout` (dropping the "no new root options" out-of-scope line), not a silent default. A12's gate then becomes "no behavior change at all", which is a cleaner gate to defend.

### Q2 — Activity = any `/mcp` request vs tools/call only

**Ruling: agree with the middleware (any `/mcp` request counts), with one honesty correction (F7).**

The zombie-keepalive hole is real: a connected, ping-only client keeps the server alive indefinitely, so the watchdog is not "4h without tool use" — it is "4h without any HTTP traffic". But the middleware choice is still right, for three reasons: (1) the alternative (SDK `AddCallToolFilter`) requires body parsing or a newer, less battle-tested SDK surface to distinguish `tools/call` from `initialize`/`ping`/`notifications/list`; (2) `Stateless = true` means there are no sessions to preserve, so the design's "never kill a live session" rationale is weak — but that cuts *toward* counting less, not more, and the decisive point remains (3): a connected client is, operationally, "in use" — a tool-idle-but-connected client costs nothing while a dead server costs a reconnect and possibly a broken client. The real failure mode the middleware prevents is killing a server the user is actively looking at. What must change is the claim's wording (F7): the design currently implies the server still dies 4h after "real activity" ceases; with heartbeat clients it may never die. That is an acceptable outcome — the watchdog's purpose is reclaiming *forgotten* servers, and a server with a live connection is not forgotten — but it must be stated as the actual guarantee. Also note A8's grep-gate is the right enforcement for "background services are not activity"; keep it.

### Q3 — `serve --mcp-entry` blocks and serves

**Ruling: agree with blocking-and-serving for the single verb.**

Render-and-exit would either lie about `--port 0` (impossible to render an unbound port) or silently constrain the feature to fixed ports, which is the exact "surprise beats honesty" failure the design correctly rejects elsewhere. The JSON is printed only once the port is bound, so the pasted entry is immediately usable — that is the honest contract. The standalone render-and-exit verb is correctly parked in out-of-scope as a possible follow-up; it is a different feature (config-authoring) and can be added later without breaking this one. Two corrections: the documented capture recipe is broken (F5 — `2>&1` corrupts the JSON file; use separate streams), and the design should state the entry's lifetime story (F13 — watchdog kills the server; long-lived pasted entries need `--idle-timeout 0`). Also define `--format` without `--mcp-entry` (F9).

### Q4 — One BackgroundService + atomic timestamp vs 2 services + Channel

**Ruling: agree with the single-service shape — but the wiring as written is broken (F1).**

The sketch's channel buys producer/consumer decoupling: bounded buffering, ordering, backpressure, consumer-crash isolation. None of those are real requirements for a per-request timestamp reset at loopback request rates — the channel would add an unbounded buffer and a second service lifecycle for zero behavioral gain. The single `Interlocked.Exchange` + `PeriodicTimer`(with `TimeProvider`) shape also matches the proven `ExtractionHostedService` pattern (same `PeriodicTimer` + `FakeTimeProvider` test technique), which is the right precedent for the repo. The baseline-at-start behavior (fresh server lives a full timeout even with zero requests) is correct. Two defects must be fixed: (1) the DI registration claim is false — `AddHostedService<T>` does not make `T` resolvable, so the factory `sp => sp.GetRequiredService<IdleWatchdog>()` throws on the first request (F1, probe-verified); (2) the hardcoded 1-minute tick period contradicts the design's own A6 gate (F2) — the period must scale with the timeout. Minor: read the timestamp with `Volatile.Read` for consistency (NIT, implied by the `Interlocked` discipline).

### Q5 — Silent http forcing vs hard parse errors

**Ruling: warn on `--transport`, but do not silently ignore root `--port` (F6).**

The `--transport http serve` muscle-memory path is real, and a hard error there would be gratuitously hostile — the codebase already has the warn-not-fail precedent (`SelectTransports` silently maps `https` → stdio with a warning today, verified in `McpServerSetup.cs`). Forcing http on a verb named `serve` is the verb's entire identity; a warning on an explicit conflict is the right weight. But the design applies two different standards to two root conflicts: `--transport` gets a warning, root `--port` gets silence. A user who wrote `ai-raccoon --port 5000 serve` has expressed a concrete intent (a port, which they may have wired into a client config or firewall); discarding it with nothing on stderr — which in the documented recipe goes to `serve.log` anyway — is the least honest option available. Honor root `--port` as the fallback when serve's own `--port` is absent, and warn when both are given and differ. One rule for root conflicts: warn-and-resolve when the verb's identity makes the outcome unambiguous, never silently discard a user value.

## 4. What the design MISSED

1. **The cross-repo contract (F4).** The owner's stated extension — ai-badger switching its declared ai-raccoon `.mcp.json` entry to the serve form — collides with the fixed default port on every additional client spawn, and the design neither handles it (no idempotent "already serving" mode) nor specifies the entry shape (URL entries only; a command-form spawn of `serve` breaks the stdio contract and the stdout URI line becomes protocol garbage). The stdout contract is airtight only if the design *mandates* URL-entry consumption and states who starts the server when the client no longer spawns it. This is the largest unaddressed operational gap.
2. **`--mcp-entry` + watchdog staleness (F13).** Pasted configs outlive their server by design; the workflow needs one sentence (`--idle-timeout 0` for long-lived entries).
3. **The operational model for URL entries.** Hermes `url:` entries (verified present in the user's `~/.hermes/config.yaml`) do not spawn anything — someone must start `serve` out-of-band (terminal, login item). The design never says who, or what happens when the client starts before the server (connection refused, no retry story). Acceptable, but it should be a stated decision.
4. **A6 vs tick period (F2)** — the spec contradicts its own gate; must be resolved before WP2 starts.
5. **Bind-failure taxonomy (F8)** — narrow the catch so only genuine address-in-use maps to exit 3.
6. **Supervisor semantics of exit 0 (F12)** — worth one line in help/README so the intentional-shutdown exit code is documented rather than discovered.
7. **`--idle-timeout` validation wiring (F10)** — "System.CommandLine's normal error path" requires an `AddValidator`; the design names no mechanism.
8. **Double-serve of one bank (F11)** — port guard ≠ bank guard; document single-instance-per-bank.
9. **Windows backgrounding** — the `&` recipe is Unix-only; a Windows note (or omission) is needed since the repo is cross-platform-capable.

- ✓ stdout reservation for the stdio protocol is a written rule (`mcp.instructions.md`), so serve's stdout claim holds *within the process*.
- ✓ Hermes config has `url:`-only entries (playwright, microsoft-docs) — the §3.4 hermes shape is credible.
- ✓ ai-badger's `.mcp.json` currently declares ai-raccoon as bare `command` (stdio, no args) — the cross-repo change is real and imminent.
- ✗ **"`AddHostedService<IdleWatchdog>()` already registers the class as a singleton" — false (F1; live probe throws `InvalidOperationException`).**
- ✗ A6's "~5s" with a hardcoded 1-minute tick — impossible (F2).

### Security notes (no new exposure)

Loopback-only, unauthenticated, unchanged from today's HTTP transport — acceptable for the stated threat model (single-user workstation), and `Stateless = true` keeps the surface minimal. One observation: loopback is per-host, not per-user; on a shared machine any local user can call the memory tools of a running `serve`. Same as today's `--transport http`; worth one line in the README's serve section so the "safe to leave running" claim is scoped honestly.
