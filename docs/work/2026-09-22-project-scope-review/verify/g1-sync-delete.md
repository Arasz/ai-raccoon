### F29 — CONFIRMED
**Method:** live repro: `ai-raccoon --data-root docs/work/2026-09-22-project-scope-review/verify/g1/data --port 7901 serve`, then MCP over HTTP: `memory_write {projectId:"g1proj",content:"context-delete resurrection probe g1",context:"ctxA"}` → hash `1606f7de…`; `harness sync …/data g1proj …/cloud` → `sent=1 received=0`; `memory_delete_context {projectId:"g1proj",context:"ctxA"}` → `{"deleted":1}`; `sqlite3 -readonly … "SELECT count(*) FROM entries | FROM sync_tombstones"` → `0 | 0`; sync again → `sent=1 received=1`, row back as `1606f7de scope=custom label=ctxA`. Source re-read: `SqliteMemoryStore.cs:302-321` (bare `DELETE FROM entries WHERE {filter}`, no tombstone) vs `:744-785` (`DeleteCoreAsync` writes one); `SyncService.cs:439-456` (entries leg re-inserts any remote row with no matching tombstone) and `:519-524` (apply).
**Result:** No tombstone after `memory_delete_context`, entries 0 → 1 on the next sync with identical hash/scope/label — the exact resurrection claimed. Counter-arguments closed: no doc/ADR grants context deletes a sync exemption — `MemorySql.cs:170-171` states the tombstone policy ("Sync propagates deletes through tombstones (FR-NM-8)") and ADR-0023 lists `DeleteContextAsync` among the covered deleters; ADR-0052/0051/0024 treat it as a real destructive delete. HIGH severity stands.

### F30 — CONFIRMED
**Method:** live repro on the same scratch root. (a) `memory_workspace_begin` → ws `01a0c9565afc…`; workspace write then committed write of `"f30 twin-row resurrection probe"` → both hash `9e56b5f1…`, same path; rows id2 `scope=NULL, ws=…` then id3 `scope=project`. `memory_delete {hash 9e56b5f1…}` → `{"deleted":1}`; `entries`-for-hash `0`, `sync_tombstones` `0`; next sync → `received=1`, the committed twin back (`scope=project`). (b) two-replica build (bank A custom `ctxC` + bank B project, same hash `080484a674…` via push/pull): `memory_delete` → 2 rows deleted, exactly **1** tombstone (`scope=custom`); the next sync re-pulled the unrecorded `project` row. Source: `SqliteMemoryStore.cs:752-753` single unordered probe, `:760-761` multi-row `DELETE`, `:764-769` one conditional `UpsertTombstone`; `MemorySql.cs:172-173` probe has **no `LIMIT`/`ORDER BY`** (Dapper's `QueryFirstOrDefault` takes whichever row SQLite returns first; the workspace row won in both my runs).
**Result:** Both halves reproduced: zero tombstones when the first probed row is workspace-scoped (committed twin resurrected), and one tombstone for N=2 deleted committed rows with the other scope's deletion left unrecorded (that row resurrected on the next sync). One evidence-line correction: the cited text `SELECT scope FROM entries … LIMIT 1` is not the constant's text — the constant is `SELECT scope FROM entries WHERE hash = @hash AND project_id = @projectId AND (@scope IS NULL OR scope IS @scope)`; the "arbitrary first row" mechanism and the HIGH/severity are unchanged. A second-committed-twin can't be made by two `memory_write` calls (`SelectCommittedByValue`, `MemorySql.cs:67-78`, returns the existing row), but the two-replica path proves the state is reachable.

HIGH severity stands.

## Still open
- **F30 first-row order is unspecified.** Both my runs returned the workspace row first (rowid order), matching the finding, but no `ORDER BY` guarantees it; on a planner/index change the failing shape ("none when the first row is workspace-scoped") could require the workspace row to win the scan. The "at most one tombstone for N rows" half is order-independent and was measured with a real N=2 delete.
- **F30's "two committed rows" was reached via a two-replica push/pull, not two `memory_write` calls** (the committed-value dedupe at `MemorySql.cs:67-78` prevents the latter). The partial-suppression behaviour itself was reproduced live.
- **F32's same-named-index-over-different-columns variant is code-read, not measured** — I only ran the same-columns/non-unique case live. The names-only `SchemaDoctor` comparison makes the variant's outcome unambiguous, but it was not independently executed.
- **F35's watcher run asserts outcomes, not the call path**: the row vanished with zero tombstones and the only delete method reachable from `WatchDigestExecutor.DeletePathAsync` is `DeleteSourcePathAsync` (src scan), but I did not instrument the process to prove which method produced the delete.
