### F70 — CONFIRMED
**Method:** read `src/AiRaccoon/Hosting/Common/ServerProbe.cs:69` (`body.Contains("jsonrpc")`), `BackendLauncher.cs:53-56`, `NodeRunner.cs:71-83,249-258`, `BackendSessions.cs:40-43,111-121`, `ServerRestart.cs:69-70,133-134`, `docs/adr/0043-...:49`, `docs/plans/2026-08-09-mcp-loopback-token-flow.md`; then live squatter runs in `docs/work/2026-09-22-project-scope-review/verify/g3/f70/` against scratch roots `data-fresh` / `data-existing` on ports 17311/17313 with a token I minted myself via `serve`.
**Result:** CONFIRMED. With a token file present, the proxy attached to a squatter advertising `serverInfo.name = "squatter-not-ai-raccoon"`, sent it the file's token byte-for-byte plus the full `memory_write` payload (confidential canary included), and handed the squatter's forged tool result to the agent's stdout; plain `serve` attached with exit 0, and a squatter whose `/observability` returns `"ai-raccoon"` received the real token on `POST /shutdown` from `serve --restart`. The finding omits one precondition I measured: on a never-served data root the proxy exits 6 ("holds no token") and leaks nothing, so the attack needs the token file to pre-exist — which it does after any prior `serve`. No cited doc ratifies the handover: ADR-0043:49's "a JSON-RPC reply on `/mcp` ⇒ an ai-raccoon server holds the port" is exactly the inference my non-ai-raccoon squatter falsifies, and the loopback-token design asserts the opposite invariant ("port answers ⇒ token file exists"; "the token proves the caller can read a file in the data root"), which a squatter that never reads the file violates.
