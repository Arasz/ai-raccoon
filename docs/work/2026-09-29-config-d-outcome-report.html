Config D: outcome report

ai-raccoon 1.54.0 · task air-config-d-memory-1022-chunks · written 2026-09-29 · PR #804, PR #810 (merged), issue #809 (open)

The memory chunk budget now follows the bundled model manifest at 1022 tokens, up from 254. Code chunks stay at 510. The query-trim budget follows the same manifest number, so long queries are trimmed at 1022 instead of 254. Existing banks re-chunk and re-embed themselves on their first 1.54.0 start, with tool calls refused while that runs. Everything is on main and green in CI. One merge used admin privileges to get past a review rule no available reviewer could satisfy; that is documented on the PR.

What went out

The change itself is small. One number in one committed manifest, chunkTokens, moved from 254 to 1022 in ai-raccoon.manifest.json. Memory chunking, the query-trim budget and the "query too long" warning all read that number, so all three moved together. Code chunking reads its own budget and stayed at 510. The arithmetic is clean: 1022 content tokens plus the model's two special tokens is 1024, which fits the model's padded buckets with no waste, and 1022 sits well under the validator's 8188 ceiling.

The hard part was existing banks. A new ChunkBudgetReconciler phase runs inside the model-migration drain, after the vector-dimension reconcile and before the embed loop, so every path that closes a migration passes through it. It re-chunks note groups by proving their reassembly (the stored rows must join back into the exact text whose SHA-256 the note's path names, found by backtracking, never a greedy match) and re-ingests file mirror rows from disk under their own scope, context and workspace bucket. Replacement is one transaction per group: tombstone the vanishing hashes, delete, insert in text order carrying path, source_file, section, the bucket keys, source_id, agent_id, created_at and ttl_days forward. The embedding.chunkBudget stamp exists only when the last run converged at that budget. Unprovable groups get three passes per resolved budget and then stop gating the stamp, so one pathological note cannot re-open the migration (and its refusal window) forever. Event 448 logs the phase counts so a partial migration is visible to an operator.

Second piece: the MLX precondition pin the owner asked for. A real MLX session must pad a short input row up to a full 64-token bucket and match the CPU session's vectors to a cosine of 0.9999. The test skips where the MLX plugin is absent, and an AIRACCOON_REQUIRE_MLX=1 flag turns that skip into a hard failure. The new build-mlx macOS job sets the flag, so a green run there is proof that real MLX executed rather than that everything skipped.

Paperwork: ADR-0125 records the decision and its accepted costs, ADR-0108 carries supersession pointers, the changelog and breaking-changes entries name the migration outage and the metadata resets, and VERSION is 1.54.0.

How it was built: a 21-row plan in five packages (reconciler machinery, MLX pins, the manifest flip, documentation, integration test) implemented by parallel worktree lanes, then two review lanes (implementation and test quality) with twelve and four mutations respectively, a join review of the fix batch, a research-harness fallout batch, and a CI-green batch that repaired budget-coupled test fixtures across eight classes. Roughly 6,300 tests run green on the result.

Why

254 was a stopgap. It came from a MiniLM-era budget, was pinned by ADR-0108 so every measurement in that ADR stayed comparable, and no measurement had ever argued it was right for this model. Two research records changed that. The 2026-09-25 chunk-size study found the cost curve bends at 512 tokens, an attention cliff at 128 that larger chunks simply clear, and memory retrieval gains between +0.078 and +0.254 with bigger chunks (part of that range is a wider net rather than better ranking, and the record says so). The 2026-09-28 query-budget study settled the second half: 254 was never a query decision, it was the chunk budget seen through the query-trim coupling, and no source on record argued 254 tokens of query context is right. Live-bank traffic made the stakes concrete: median query length is 61 characters, about 8 tokens, so almost nobody felt the trim at all.

The owner then made five calls, all recorded in ADR-0125: adopt config D (memory 1022, code 510); migrate existing banks by re-chunking and re-embedding; let the query budget follow the same manifest number; skip any pre-adoption retrieval measurement (queries at or under roughly 255 tokens are unaffected, and longer ones were being trimmed before, so the change is strictly more context); and treat the 254-versus-1022 retrieval measurement as its own follow-up after the merge.

Accepted costs, in the owner's words as recorded: rows whose chunk boundaries move lose their per-row rating, access count and last-access time (there is no honest 1:1 mapping across new boundaries), notes keep their TTL, mirror rows re-ingested from disk lose theirs (a file carries no TTL to read), rows with nothing re-chunkable keep their stored bounds and only get re-embedded, and code re-embedding churn happens only for banks using the bundled-default code engine.

Consequences

First start on 1.54.0 migrates the bank. Every bank re-chunks and re-embeds once, on its own, and refuses tool calls until that finishes. Expect minutes on a large bank (the measured anchor below: 357 seconds for 25,917 rows). The outage window is honest and bounded, and the phase order guarantees the migration cannot close with any row unembedded.

Search behavior changes for long content and long queries. Chunks carry up to 1022 tokens of prose, so a hit brings roughly four times the context it did. Queries are trimmed at 1022 tokens instead of 254, and the length warning fires around 4,024 characters instead of 1,000. Code retrieval is untouched.

Metadata resets where boundaries moved. Rating, access count and last-access time go away on re-chunked rows. Notes keep their TTL across the re-chunk (with one rule: the group's first row is the template, so divergent per-row TTLs collapse to its value). Mirror rows re-ingested from disk lose the TTL and stop expiring until someone runs memory_set_ttl again. The ADR and changelog list exactly what goes.

CI now enforces real-MLX coverage on the named run, and the first live run of that job failed exactly as designed (absent plugin became a loud failure instead of a silent skip), which exposed a job-setup gap: the plugin copy into the build output is RID-gated, and the job was building RID-agnostic. PR #810 fixed the job to build osx-arm64-qualified. Green on that job now means MLX executed. Separately, the research harness derives its embed window from the manifest rather than a hardcoded 256, and a committed-pin guard test now catches manifest drift in the local harness before CI does.

One consequence is deliberately deferred: the retrieval measurement. Issue #809 tracks the 254-versus-1022 retrieval study, the WebGPU memory footprint at the larger budget, and the re-chunk phase wall-clock on a real large bank, alongside the eval-set re-anchor and a byte-band re-measure the harness lanes uncovered.
