## Issues

### QA-1: `--help` / `--version` do not exit — they fall through to proxy launch
- Repro: `ai-raccoon --version` prints the version to stdout, then attaches to the server on
  7721 as a proxy (ServerProbe + BackendSessionClient HTTP traffic observed) instead of
  exiting. `ai-raccoon --help` prints help to stderr (2599 bytes) and stays alive >4s (proxy
  attach) instead of exiting. With nothing on 7721, the fall-through proxy SPAWNS a backend —
  a stray `--version` can boot a server (observed: it spawned a 1.8.0 serve on 7721).
- Same family on verbs: `ai-raccoon sync --help` and `ai-raccoon access --help` print the
  help and then RUN the dispatcher on the bare verb path → "ai-raccoon: unhandled command:
  sync" on stderr and exit 1 (should be help + exit 0).
- Pre-refactor (af38d804^ Program.cs): help/version were rendered via the TryParse-false path
  and the process exited; the AppRunner refactor lost the early exit — `Run` falls through
  `IsCommandInput`/`IsProxyInput` to `RunProxy`.
- Impact: every `--help`/`--version` invocation on a machine with a live server hangs until
  stdin closes or spawns a backend; scripts calling `ai-raccoon --version` (rollout watchdogs,
  setup scripts) can block; `--help` on any verb exits nonzero.
- FIXED (TDD): AppRunner.Run early-exits with Success when ShowHelp/ShowVersion, right after
  RenderTo. CliCommandRunnerTests.Version_ExitsWithoutLaunchingTheProxy +
  VerbHelp_ExitsZero_WithoutRunningTheVerb (both RED before, GREEN after). Live: the deployed
  1.8.1 `ai-raccoon --version` exits 0 instantly with no proxy traffic.

### QA-2: `model set local` hung once (>180 s), re-run completes in 0.2 s
- Repro: after `model reset` (bank → FTS5-only), the FIRST `ai-raccoon model set local` wrote
  the setting but did not exit within 180 s. The re-run completed in 0.208 s (exit 0).
- Likely transient (bank open/checkpoint contention during the reset window, or first-load
  of the ONNX session); not reproduced on re-measure. Watchlisted, not scheduled for a fix.

### QA-4: quiet-mode proxy emits HttpClient INFO logs to stderr (f: from owner)
- Repro: a Hermes stdio bridge (`ai-raccoon --quiet`) started against 1.8.1 logs every relayed
  request to the terminal:
  `info: System.Net.Http.HttpClient.BackendSessionClient.LogicalHandler[100] Start processing
  HTTP request POST http://127.0.0.1:7721/mcp` (+ ClientHandler/Sending/Received/End lines).
- Cause: AppRunner.RunProxy/RunCliCommand build their own ServiceCollection with
  `AddLogging(b => b.AddConsole(... LogToStandardErrorThreshold = Trace))` — unconditional, and
  quiet mode is never consulted. QuietLogging.Configure only runs in HostLogging (server
  hosts), so the proxy's HttpClientFactory handlers log at Information to stderr regardless
  of `--quiet`. The released 1.8.0 (pre-refactor) applied quiet via HostLogging on every path;
  the refactored AppRunner bypasses it.
- Impact: every Hermes memory-provider session prints per-request HTTP logs on the user's
  terminal — quiet mode's contract ("nothing reaches stdout/stderr") broken on the proxy path.
- FIXED (TDD): QuietLoggingTests.QuietProxy_HttpClientRelayLogs_StayOutOfStderr (RED on the
  leaking build, GREEN after AppRunner.ConfigureConsoleLogging routes quiet to
  QuietLogging.Configure) + LoudProxy_HttpClientRelayLogs_ReachStderr positive control.
  Redeployed 1.8.1; live check: `ai-raccoon --quiet --port 7721` → stderr 0 bytes.
  Existing noisy bridges keep running old code until they restart.

### QA-3: `watch enable <target>` silently writes enabled=false
- S.CL bool ARGUMENTS default to optional-with-false, so `ai-raccoon watch enable X` (the
  natural invocation) parsed cleanly and wrote watch.enabled.X = false — the opposite of the
  verb. `watch enable X true` is the explicit form.
- FIXED (TDD): the enable/disable bool arguments are now ArgumentArity.ExactlyOne — the
  shorthand is a parse error instead of a silent disable.
  WatchCommandsTests.Enable_WithoutTheBoolArgument_IsAParseError (RED→GREEN) +
  Enable_WithExplicitBool_SetsIt control.

### QA-5: `encryption unset` on an env-keyed bank leaks a Guard exception
- Repro: no AIRACCOON_DB_PASSPHRASE set, env-keyed bank → `ai-raccoon encryption unset`
  printed `ai-raccoon: Parameter "encryptionData.SecretId" (string) must not be null or
  whitespace, was null` instead of the documented warning path.
- Cause: DI positional injection — EncryptionCommands takes a single IEncryptionKeyProvider
  ("env"), and the container's last registration for that interface is the BITWARDEN
  provider, whose Guard validates SecretId. Pre-refactor the CLI composed the command by
  hand with the env provider.
- FIXED (TDD): CommandsRegistration now registers EncryptionCommands via an explicit factory
  that selects EnvEncryptionKeyProvider from the provider set.
  CliCommandRunnerTests.EncryptionUnset_EnvKeyedBankNoPassphrase_WarnsAndExitsOne (RED→GREEN).
