# HTTP serve mode — independent review (dotnet-engineer lane)

Date: 2026-08-06 · Reviewer: dotnet-engineer (independent, MOE) · Input: `docs/work/2026-08-06-http-serve-design.md`
Scope: implementation feasibility against the actual codebase (worktree `switch-from-stdio-to-http`) + cross-repo ai-badger integration.
Method: every claim below was verified against source in this worktree, against the referenced NuGet packages (decompiled `System.CommandLine` 2.0.10, `Microsoft.Extensions.Hosting.Abstractions` 10.0.10, `Microsoft.AspNetCore` 10.0.10, `ModelContextProtocol.AspNetCore` 2.1.0), and against the ai-badger repo (read-only). No files were modified.

---

## 1. Verdict summary

The design is fundamentally sound and — rare for a design doc — almost every "verified against code" claim in §2 checks out (EventId inventory, transport/host shape, stdout contract, busy-port pattern, `web.Urls` read, SCL version, MCP SDK hooks). The architecture (one BackgroundService + atomic timestamp, middleware activity hook, foreground blocking serve, fail-fast busy port) is right, and the WP split has no file contention.

However, **two MUST-FIX defects would ship broken code as written**, both in WP2:

1. **The watchdog DI wiring cannot resolve `IdleWatchdog`.** `AddHostedService<T>()` registers `IHostedService → T` only (`TryAddEnumerable(ServiceDescriptor.Singleton<IHostedService, THostedService>())` — decompiled from 10.0.10). `sp.GetRequiredService<IdleWatchdog>()` throws "No service for type … has been registered" on the first MCP request. The design's parenthetical claim ("AddHostedService already registers the class as a singleton") is the exact wrong belief.
2. **Acceptance A6 is unpassable with the specified watchdog cadence.** The watchdog checks the idle condition only on a 60-second `PeriodicTimer` tick; with `IdleTimeout = 2s` (A6), shutdown lands on the next minute tick — up to ~62 s, not "within ~5 s". The tick period must be derived from the timeout.

Everything else is SHOULD-FIX/NIT precision work. WP1 and WP3 build as planned; WP2 builds only after fix 1; A6 only after fix 2. The ai-badger extension (changing the declared command to `ai-raccoon serve`) must be **rejected as designed** — it is not merely collision-prone, it is transport-broken (see §4.1); the recommended default is to keep `.mcp.json` stdio and switch only the Hermes side to URL-based.

## 3. Feasibility per work package

**WP1 — CLI surface + config plumbing: BUILDS, with two precision fixes.** Verb + `Verbs` array + tree are mechanical (`CliCommandTree` is exactly the growth point its doc comment claims). `ServerConfig` 4th positional defaulted param is zero-churn (F11). `ExitCode.PortInUse` conflicts with nothing. `DefaultOptions.IdleTimeout` as a `static readonly` follows the `DataRoot` precedent in the constants class. Two items need the design's wording fixed, not its structure: the SCL "no TimeSpan" justification and the unspecified parse-error mechanism (F4); and a decision on whether `CliArgs.cs` actually changes (the design lists it as touched but nothing in `TryParse`/`ReadOptions` needs to — the `serve` verb rides the existing `Verbs`/`CommandPath` machinery; only new tests + `IdleTimeoutParser` land there). The static Option fields work as verified (F8). **Gate: `dotnet build` + updated `CliCommandTreeTests`/`CliArgsTests` — will pass.**

**WP2 — watchdog: DOES NOT BUILD AS WRITTEN (F1), and A6 as written cannot pass (F2).** Everything else is sound: the `PeriodicTimer(period, timeProvider)` + `FakeTimeProvider` pattern is proven by `ExtractionHostedServiceTests`; the HTTP-only gating in `CreateWebHost` is structurally identical to the `ExtractionHostedService` precedent; `ConfigureMcpEndpoints` wiring works (F14); EventIds 610–612 are free (F13); `StopApplication` → graceful → `Success` is standard. Fix F1 (registration), F2 (tick cadence), F5 (path guard) and WP2 is fully feasible. Note for the host-shape tests: existing `McpServerSetupHostTests` use the 3-arg `Config()` helper → `IdleTimeout = Zero` → no watchdog → **existing tests stay green unchanged**; A7 additions construct with an explicit timeout.

**WP3 — serve runtime + reporting: BUILDS, with signature/robustness fixes.** The Program.cs pre-branch is clean and required (F7). The bootstrap sequence duplicates Program.cs locals (F10). `ServeRunner` as specced cannot read serve's options or detect an explicit `--transport` (F6) — pin the signature. Busy-port catch (F9). The `web.Urls` read after `StartAsync` mirrors `HostExtensions.RunAsync` exactly (including the `TrimEnd('/') + "/mcp"` normalization) — correct, and `--port 0` reporting works because Kestrel mutates `IServerAddressesFeature` before `StartAsync` returns. One ordering detail worth pinning: print the stdout line *after* `StartAsync` returns (as designed) — never before, or the printed URL can lie. The A13 "no serve path leaks into ConfigCommands" test is straightforward (`CommandPath is ["serve"]` never reaches the dispatcher).

**WP4 — docs: BUILDS.** Add the cross-repo note (F12) and a POSIX-only caveat on the backgrounding recipe (`> serve.log 2>&1 &` is not a Windows shape).

**Serialization:** confirmed — WP2 touches only `McpServerSetup.cs` (+ new files), WP3 only `Program.cs` (+ new files); no cross-WP file contention; WP1 must land first. One addition: F1's fix lives in `McpServerSetup.cs` (WP2-owned) — no conflict.

## 4. ai-badger integration assessment

### 4.1 Cross-repo assessment

Verified state of `/Users/arasz/RiderProjects/ai-badger` (read-only; no WIP branch exists — `task/ai-raccoon-integration` is the already-merged 0.78.0 stdio work):

- `features/common/stack-mcp.json`: `{"name": "ai-raccoon", "command": "ai-raccoon", "declare": true, "availability": {"command": "ai-raccoon"}}`.
- `features/common/mcp/ai-raccoon/meta.json`: **stale** — `"package": "arasz.ai-raccoon"` (actual `PackageId` is `ai-raccoon`, verified in `src/AiRaccoon/AiRaccoon.csproj`) and description "served over MCP stdio" (becomes half-stale once serve mode exists; stdio stays the default).
- `tests/test_common_ai_raccoon_mcp_server.py`: pins `AI_RACCOON_COMMAND = "ai-raccoon"` (comment: "zero-arg stdio launch — no args!"), the availability probe, and the rendered entry `{"command": "ai-raccoon", "tools": ["*"]}` with **no `args` key** (asserted at line 123–126).
- Scaffold rendering: `split_on_whitespace(command)` (verified in `features/common/skills/welcome-ai-badger/scripts/mcp_tools.py`) splits into `(executable, args)`; `GENERATED_ENTRY_KEYS = {command, args, cwd, env, tools}` — the scaffolder **cannot emit** `{"type": "http", "url": ...}` entries (it only *preserves* user-authored ones, per `test_unavailable_ai_raccoon_does_not_remove_a_user_authored_entry`).

**If the command becomes `"ai-raccoon serve"`** the rendered entry is `{"command": "ai-raccoon", "args": ["serve"], "tools": ["*"]}` — a **stdio-shaped entry**. Claude Code spawns it as a stdio MCP server and expects a JSON-RPC `initialize` handshake on stdin/stdout. `ai-raccoon serve` is HTTP-only: it never reads stdin, and its stdout carries the URL line, not JSON-RPC. **The handshake fails even on a free port** — the client's server is dead on arrival regardless of port collisions. This is decisive: option (ii) is not "collision-prone", it is transport-broken.

Even setting transport aside, the per-client-spawn × fixed-port-7721 combination is hostile: every concurrent Claude Code session beyond the first spawns `ai-raccoon serve`, gets `ExitCode.PortInUse = 3`, and has a dead MCP server; and the 4 h idle watchdog kills the shared server for **all** clients at once (a per-client stdio server dies only with its client).

**Option (iii) — idempotent serve (port busy → print URL, exit 0) — does not rescue the scenario.** The spawned process still exits immediately; Claude Code's stdio client has no process to talk to and no URL to connect to (it never reads the printed URL — for `url`-based entries it doesn't spawn a process at all). An idempotent mode only helps a *shell* script that wants "start if not running", which the shell already does.

**Option (i) is the simplest correct default.** The 5-minute recycle problem is a Hermes-gateway behavior (the measured 1048 registrations/day). Claude Code spawns a stdio server per session and keeps it for the session — stdio is native and reliable there; there is no recycle problem to fix. The Hermes side is the one that needs HTTP: run `ai-raccoon serve --mcp-entry --format hermes` once (or `hermes mcp add ai-raccoon --url http://127.0.0.1:7721/mcp`), get a URL-only entry matching the entries already in the user's `config.yaml`, and the gateway stops recycling. This also matches the design's own out-of-scope line ("registry entry stays stdio").

**Recommendation for the ai-badger PR:** do not change `stack-mcp.json`'s command. Scope the PR to: (a) `meta.json` — `"package": "ai-raccoon"`, description mentioning both the stdio default and `ai-raccoon serve` for a long-lived HTTP endpoint; (b) optionally a `server.md` note pointing at serve mode; (c) leave `AI_RACCOON_COMMAND` and the rendered-entry assertions untouched. If HTTP-by-default in `.mcp.json` is ever wanted, the real extension is new scaffold capability to emit `{"type": "http", "url": ...}` entries (with URL templating for the fixed port) — a deliberate feature with its own schema, not a command-string change. `ExitCode.PortInUse = 3` remains the right CLI contract (F16); it just never gets exercised by the ai-badger path.

## 5. Risks the design missed

1. **A6 vs. 60 s tick** (F2) — the sharpest test-design gap: as written the acceptance gate is impossible with the specified cadence.
2. **Bare `--transport http` gets the watchdog with no opt-out** (F3) — the design's own Q1 framing misses that the escape hatch is serve-only. Highest user-visible surprise risk of the whole feature.
3. **Middleware counts non-`/mcp` traffic** (F5) — contradicts the stated "only /mcp signals" contract; cheap to fix, silently wrong otherwise.
4. **First mutable shared symbols in the CLI layer** (F8) — the static Option instances create cross-parse shared state (parent chaining) and a theoretical parallel-test-build race; benign in 2.0.10 but an upgrade hazard (a future SCL enforcing single-parent would throw at tree build, which today would fail only in tests, loudly — acceptable, but worth the comment).
5. **Watchdog-shutdown exit code masks "I died" for scripted servers** — a scripted `serve` that the watchdog kills exits `Success` (0). The design's intent ("intentional, clean shutdown") is defensible, but a supervisor cannot distinguish watchdog-death from a healthy stop; if that ever matters, the log line 611 is the only signal. Acceptable; document it.
6. **`--mcp-entry` JSON goes stale by design** — the printed URL is only valid while the process lives; a 4 h-idle watchdog death leaves the pasted config pointing at a dead port. The design accepts this; the WP4 docs should say "restart with the same command" explicitly, and the serve help recipe could mention it.
7. **Windows shape** — the `> serve.log 2>&1 &` recipe is POSIX-only; the tool is cross-platform and the README should not imply otherwise.
8. **`ServeRunner` bootstrap drift** (F10) — duplicated key-probe/embedding bootstrap between Program.cs and ServeRunner is a future silent-divergence point.

None of §5 items change the architecture; all are precision/test/doc fixes.
