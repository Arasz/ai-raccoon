# MoE panel — Expert E: cross-cutting quality

Date: 2026-08-07
Scope: correctness, async/concurrency, error handling, observability, configuration, security — across all three projects.
Method: read-only. Every finding cites a line read in this worktree. Findings that did not survive a second read are listed under *Refuted*.

## Verdict

The cross-cutting chassis is in better shape than most codebases this size: the high-performance-logging invariant holds **absolutely** (zero direct `logger.Log*` call sites in 342 source files, 56 `[LoggerMessage]` methods), async hygiene is genuinely good (no `async void`, no `.Result`, no `.Wait()` anywhere in `src/`), the hand-rolled SSH key parser — the thing I most expected to be broken — is correctly bounds-checked on every path, and the Bitwarden subprocess invocation uses `ArgumentList` with a real timeout and process-tree kill. The problems are concentrated in three places. First, **observability lies**: all 23 tool call sites record `result=success` *before* the DB work that can still throw, so a failing tool call is counted as a success and its span marked `Ok` (F-01), and `PromotionQueueMetrics` tags five instruments with an unbounded `project_id` (F-02) in direct contradiction of ADR-0002, which deliberately kept that tag off metrics. Second, **two trust boundaries are unguarded**: `memory_ingest_file`/`memory_ingest_directory` accept any client-supplied path with no containment at all (F-03) even though the codebase already has and uses the containment primitive for `memory_watch_add`; and cloud sync merges the *entire* remote settings table unconditionally (F-04), which includes the access-mode control and the sync credentials themselves. Third, **configuration is fragmented** — settings keys live in eight classes across all three projects under three incompatible naming conventions, with no options validation anywhere. ADR-0002 is materially stale: its Non-Goals assert "AiRaccoon does not host an HTTP server," which stopped being true when `serve` shipped. A full census of all 117 catch clauses found error handling otherwise disciplined — 111 legitimate, zero log-and-swallow, one empty catch — with the residue clustered in **parse-failure paths that cannot be distinguished from absence** (F-07, F-22, F-23), which is where the real damage is.

### Concrete failure scenarios for the High findings

- **F-01** — `memory_search` succeeds, then `WrapAsync` → `GetMetaAsync` → `GetStatsAsync` hits `SQLITE_BUSY` because `BankMaintenanceHostedService` is mid-`VACUUM`. The client gets an MCP error; the operator watching `dotnet-counters` sees `ai_raccoon_tool_invocations{result="success"}` increment and no error at all.
- **F-02** — A developer with 40 repos on one machine, user-scope bank. `ai_raccoon_queue_queued` alone carries 40 tag values; across 5 instruments that is 200 time series that never retire, growing with every new project id ever proposed.
- **F-03** — Malicious or confused client calls `memory_ingest_directory(projectId, path="/Users/<user>")`. Every `.md`/`.txt` under the home directory is chunked, embedded, indexed, and returned by future `memory_search` calls — and pushed to the object store if sync is configured. Default `rw` access mode permits it.
- **F-04** — A snapshot in the configured bucket (shared team bucket, loose write ACL, or stale credentials) contains `sync.endpoint`/`sync.accessKey`/`sync.secretKey` rows. One `memory_sync` merges them; the **next** `memory_sync` pushes the entire memory bank to the attacker's endpoint. The same merge can set `access.mode.global` to `full` and `sweep.threshold` to `5.0`, after which one `memory_sweep` deletes every non-shared project entry (shared rows are exempt per `SweepService.cs:33-36`).
- **F-22** — A project has 5 allowlisted watch paths. The `watch.scope.<projectId>` row is truncated by a crash mid-`SetSettingAsync`. The user runs `ai-raccoon watch scope add /new/path`; the CLI prints "added /new/path to watch scope", and the stored row is now `["/new/path"]`. The other 4 paths are gone permanently. The user discovers it later when `memory_watch_add` throws `PathOutsideScopeException` for a path that was authorised yesterday.
- **F-05** — First run on a large docs tree. `EnqueueInitialScan` starts; the idle watchdog fires at 4h or the user hits Ctrl-C. The host stops cleanly, the process exits, and half the tree is indexed. Next start reads a watermark implying the scan completed, so the unindexed half is never picked up.

## Refuted — checked and dropped

These looked like findings on first read and did not survive the second:

- **Alpha read path unclamped.** `SqliteMemoryStore.ReadStructureAlphaAsync:779-782` **does** clamp `alpha is >= 0.0 and <= 1.0` before it reaches `StructureFusion.Fused`, which would otherwise throw. Only the *display* path (`SettingsCommands.cs:185-188`) skips the clamp, which is harmless.
- **Negative watch concurrency.** `WatchConfig.ParseInt:37` accepts negatives, but `WatchScheduler.GateFor:92` applies `Math.Clamp(..., 1, MaxConcurrency)` at the point of use. Defended.
- **`PromotionQueueMetrics._utilization` is a single field shared across projects.** It is fed from `stats.TotalCount / cap`, both bank-global (`PromotionQueueService.cs:52, 88`). A single global value is correct here.
- **Division by zero in `RecordUtilization`.** `ReadCapAsync` → `ParseQueueCapacity` returns the default for anything ≤ 0, so `cap` is never 0. The `Math.Max(1, ...)` guard at `:88` is redundant, not load-bearing.
- **`HttpTransportListening` logged at `Warning`.** Deliberate: `--quiet` sets the minimum level to `Warning` (`McpServerSetup.cs:76-79`, `CliCommandTree.cs:75`), so the bound URL — the only discoverability channel for `--port 0` — must be at Warning to survive quiet mode.
- **`SqliteMemoryStore.cs:374` and `MemorySchema.cs:306, 386` catch-alls.** All are `ROLLBACK` + `throw`. Correct.
- **MCP tool `catch (Exception ex) { activity.RecordError(ex); throw; }`.** Rethrows. Correct (the *ordering* is the bug — F-01 — not the catch).
- **Missing `ConfigureAwait`.** Generic-host console app, no `SynchronizationContext`. Not a bug.
- **`BitwardenCliSecretManager.cs:77-78` `GetAwaiter().GetResult()`.** Reads are started before the blocking `WaitForExit`, which is the correct anti-deadlock ordering; no `SynchronizationContext`. Not a deadlock.
- **`WatchPipeline.TickOnceAsync:147-168` mutating a dictionary during `foreach`.** `Dictionary.Remove` of a visited key during enumeration is permitted; only `Add` throws.
- **SSRF via sync endpoints.** `SyncTools.Sync` takes only `projectId` — no endpoint parameter. Endpoints are CLI-only (`SyncCommands.cs:69`), set by the machine owner. This is the weak, owner-controlled case. (F-04 is the real exposure, and it is a *different* mechanism.)
- **Secrets in tracked files.** The one `AccountKey=` hit is the published Azurite emulator key; `test-bws-token-0123` is obviously fake; ed25519 fixtures are synthesized from named seed arrays. Clean.
- **Argument injection into `bws`.** `ProcessStartInfo.ArgumentList` throughout, `UseShellExecute = false`, executable hardcoded to `"bws"`. Clean.

## What is already good

Stated plainly, because it is unusual:

- **The logging invariant holds without exception.** Zero direct `logger.LogInformation/Warning/Error/Debug/Trace/Critical` call sites across 342 source files; 56 `[LoggerMessage]` methods in 20 nested static `Log` classes. This is the cleanest instance of that invariant I have seen in this codebase family. Only the *numbering* (F-12) drifted.
- **Async hygiene.** No `async void`, no `.Result`, no `.Wait()` anywhere in `src/`. `PeriodicTimer.WaitForNextTickAsync(stoppingToken)` in both interval services. `IdleWatchdog` uses `Interlocked.Exchange`/`Interlocked.Read` consistently for the cross-thread activity timestamp. `SyncService`'s `SemaphoreSlim` is `WaitAsync`, released in `finally`, on a genuine singleton. `WatchEventSource` holds its lock only around synchronous dictionary access and invokes callbacks outside it. `OnnxEmbeddingGenerator`'s `Task.Run` wraps genuinely CPU-bound inference — the correct use.
- **The SSH key parser is correct.** This was the highest-suspicion item in the brief and it holds up: every length prefix is read as `uint`, cast to `int`, and rejected when negative or beyond the remaining buffer *before* any slicing (`OpenSshPrivateKeyParser.cs:146-176`). No attacker-controlled allocation. Every malformed-input path throws a specific `EncryptionKeyException` subtype rather than `IndexOutOfRange` or OOM.
- **The Bitwarden subprocess is invoked safely.** `ArgumentList` throughout (no concatenation), `UseShellExecute = false`, hardcoded executable name, enforced timeout with `Kill(entireProcessTree: true)`, and the retrieved secret never reaches a log or exception message — only bws's own stderr does.
- **HTTP serve binds loopback only**, with no code path to `0.0.0.0` anywhere in `src/` (`McpServerSetup.cs:81`). The absence of auth is a documented, accepted risk in SECURITY.md rather than an oversight.
- **`memory_watch_add` enforces real containment** against a CLI-only allowlist the MCP surface cannot modify. The primitive exists and works — F-03 is about the ingest family not using it.
- **`ToolCallMetrics` keeps metric cardinality bounded** (`tool`/`result`/`error_type` only) exactly as ADR-0002 specified, and tool-layer instrumentation coverage is complete: 22 `[McpServerTool]` methods, 22 `ToolExecutionActivity` sites, wired in **both** stdio (`Dependencies.cs:109` via `CreateAppHost`) and serve (via `CreateWebHost`, reached from `ServeRunner.cs:53`).
- **`BankMaintenanceConfigKeys` and `ExtractionConfigKeys` are the right pattern**: key, default, and clamping parser co-located, including an explicit `MaxVacuumIntervalDays = 36500` with a comment naming the `TimeSpan.FromDays` overflow it prevents. F-09 is a plea to make the other seven key homes look like these two.
- **Error handling is genuinely disciplined.** A full census of all **117** real catch clauses in `src/` (the raw `grep` count of 133 includes comments and identifiers like `WatchCatchUp`) classified **111 as legitimate**, with **zero** log-and-swallow-at-Debug cases and exactly **one** empty catch (F-24). The cloud-sync layer's 27 catches are all typed exception translation to `SyncAuthFailedException`/`SyncNetworkException`/`SyncConflictException`/`SyncCorruptFileException` — a sync failure is never reported as success. The background-loop catches all log at Warning/Error and `WatchPipeline` additionally surfaces failures into per-path state readable via `memory_watch_status`.
- **SECURITY.md is honest** about what is not covered (no CI, no secret scanning, no release automation) rather than implying coverage that does not exist.

## Durable project facts

- **Observability is BCL-only by deliberate decision** — `System.Diagnostics.Metrics` + `ActivitySource`, no OpenTelemetry SDK packages (confirmed: zero OTel entries in `Directory.Packages.props`). Two meters: `AiRaccoon.MemoryTools` and `AiRaccoon.PromotionQueue`. Read locally with `dotnet-counters monitor -n AiRaccoon <meter>`. Source: `docs/adr/0002-opentelemetry-observability.md:30-32`, `src/AiRaccoon/Observability/`.
- **Metrics exist only at the MCP tool boundary.** Watch-driven ingestion, embedding generation, SQLite queries, and cloud sync have **no metric signal at all** — they never pass through `ToolExecutionActivity`. A file-watch ingest is invisible to telemetry. Source: `src/AiRaccoon/Observability/ToolExecutionActivity.cs`, `src/AiRaccoon.Infrastructure/Watch/`.
- **Hosted-service registration is asymmetric by transport.** `WatchHostedService` and `BankMaintenanceHostedService` register unconditionally; `ExtractionHostedService` registers **only** when the transport set contains Http/Https. In stdio mode background extraction never runs. Source: `src/AiRaccoon/Setup/Dependencies.cs:113-124`.
- **`--transport` is single-valued.** `SelectTransports` always returns a one-element collection, so the "stdio + http combined" host path documented in `McpServerSetup` is unreachable dead code. Source: `src/AiRaccoon/Setup/McpServerSetup.cs:22-25`.
- **The settings table is the only runtime config channel.** `builder.Configuration.Sources.Clear()` is called in *both* host builders — there is no appsettings.json, no environment-variable binding, no `IOptions<T>`. `InfrastructureOptions` is a plain record registered as a singleton and built from CLI args. Source: `src/AiRaccoon/Setup/McpServerSetup.cs:51, 72`, `Dependencies.cs:33`.
- **The settings table is synced across machines and merged remote-wins.** It carries cloud credentials, the access-mode security control, and every tuning knob. Any reasoning about settings must treat a remote snapshot as an input. Source: `src/AiRaccoon.Infrastructure/Sync/SyncService.cs:279-284`, `SyncSettingsKeys.cs`.
- **The guard idiom is three-way split and the BCL statics dominate**: 85 uses of `ArgumentNullException.ThrowIfNull` / `ThrowIfNullOrWhiteSpace` / `ArgumentOutOfRangeException.Throw*` (concentrated in `SqliteMemoryStore.cs`, 34 alone), 32 `CommunityToolkit.Diagnostics.Guard.*` (concentrated in `Core`), 45 `ThrowHelper.*` — of which ~43 are the `x ?? ThrowHelper.ThrowArgumentNullException<T>(...)` expression form in `ConfigCommands.cs`/`SyncCommands.cs`, which is closer to the `?? throw` shape the invariant discourages than to a guard clause. Only 5 literal `?? throw` sites remain. **Consistency should be measured against the BCL statics**, since that is what the codebase actually settled on — not against `Guard.*`. Source: grep across `src/`.
- **Encryption has three key providers**, resolved in order by `EncryptionKeyResolver`: None, Env (`AIRACCOON_DB_PASSPHRASE`), and Bitwarden (via the `bws` CLI). A JSON **sidecar** next to the bank file — not the settings table — is the pre-open source of truth for which source is active; settings only mirror it. Source: `src/AiRaccoon/Setup/Dependencies.cs:149-157`, `Sqlite/Encryption/EncryptionSourceSidecar.cs`.
- **`WatchPath.Normalize` is lexical only** (`Path.GetFullPath`) — it resolves `..` and relative segments but does **not** resolve symlinks. A symlink inside an owner-authorised watch directory can still point outside scope. Source: `src/AiRaccoon.Core/Watch/WatchPath.cs:19-37`.
- **Every MCP tool call pays one extra SQLite round-trip**: `WrapAsync` calls `queue.GetMetaAsync` → `GetStatsAsync` purely to populate envelope metadata, on all 23 return paths. Relevant to both latency work and F-01. Source: `src/AiRaccoon/Tools/MemoryTools.cs:329-330` (and the identical helper in the other six tool classes).
- **`SqliteMemoryStore` has no `ILogger`.** Its primary constructor takes only `(SqliteConnectionFactory, TimeProvider, IChunker, EmbeddingService)`. The largest and most failure-prone class in the codebase cannot log anything; any fix that needs a log line there requires a constructor change. Source: `src/AiRaccoon.Infrastructure/Sqlite/SqliteMemoryStore.cs:20-24`.
- **FluentValidation is referenced but scoped to two MCP request DTOs only** (`SearchQuery.Validator`, `MemoryWriteRequest.Validator`). It is not used for settings or options anywhere. Source: `src/AiRaccoon.Core/Memory/SearchQuery.cs:47`, `MemoryWriteRequest.cs:14`.
- **The live MCP tool count is 22** (MemoryTools 9, WorkspaceTools 4, WatchTools 3, PromotionTools 2, ShareTools 2, SweepTools 1, SyncTools 1). ADR-0002 says 19/20, SECURITY.md says 19, and several docs say 19 or 21. Verify by counting `[McpServerTool]`, never by trusting a doc.
