## Verdict

The Python side of this repo is in noticeably better shape than the average "scripts/ dir" — a
deliberate, documented refactor (`docs/plans/scripts-refactor.md`) moved logic into
`scripts/src/`, backed it with 137 passing pytest tests that pin real behavior (golden hashes,
exact error messages, round-trip equality), and the `.sh`→`.py` rename propagated cleanly through
CI and docs. The `hermes-provider/` plugin is well-engineered for its integration surface:
explicit connect/call/close timeouts, a documented protocol design (`docs/work/2026-08-06-hermes-
ai-raccoon-provider-protocol.md`) that the code matches decision-for-decision, and a deliberately
handled hyphenated-package-name loading pattern (spec-loaded by path, not imported). The .NET
build/packaging side is coherent: central package management, one version number
(`1.1.2`) consistent across `AiRaccoon.csproj`, `.mcp/server.json`, and the latest git tag, and a
publish pipeline that already carries the scar tissue from a real multi-RID shipping bug (the
`patch-tool-shell.py` self-gating step exists because of a past "shell referenced one RID only"
incident). The two real gaps are process, not code: (1) neither the `scripts/tests` suite nor the
`hermes-provider/tests` suite is wired into any GitHub Actions workflow, so nothing catches
regressions here except a human running pytest manually, and the latter's 39 core-provider tests
can't even run outside a real Hermes venv (`ModuleNotFoundError: No module named 'agent'`); (2)
`scripts/baseline-results.json` is tracked in git despite the refactor plan explicitly deciding it
should stay untracked/orphaned — it was swept in by an unrelated commit. No hardcoded secrets,
no lint/format/type-check gate, and no CHANGELOG mechanism exist in this project — all three are
reported plainly below rather than proposed as fixes this review wasn't asked to make.

## Refactor opportunities

1. **Wire `scripts/tests` and `hermes-provider/tests` into CI** (G1). Current shape: pytest suites exist and pass locally but nothing in `.github/workflows/` runs them. Proposed: a `python-tests` job in `build.yml` (or a new lightweight workflow) running `python3 -m pytest scripts/tests` unconditionally, and `python3 -m pytest hermes-provider/tests` gated to skip (not fail) the 39 `agent`-dependent tests when that module isn't importable — e.g. a `pytest.importorskip("agent")`-style guard at the top of `test_provider.py`/`test_status.py`, or a minimal stub package for CI. Blast radius: 1 new/edited workflow file, optionally 2 test files for the import guard. Effort: S (CI wiring) + S (import guard). Risk: low — additive, doesn't touch shipped code. Independently shippable — touches only `.github/workflows/*.yml` and test files, no shared file with anything else in this report.

2. **Resolve `scripts/baseline-results.json`'s tracked status** (G3). Current shape: tracked, stale, no consumer. Proposed: either `git rm --cached` it and add a `.gitignore` entry (matching the plan's original intent), or — if the owner still wants it as a committed artifact — document why and what regenerates it. Blast radius: 1 file + 1 `.gitignore` line. Effort: S. Risk: none (dead weight either way). Independently shippable.

3. **Collapse the `sha256_file`/`sha` duplication** (G4). Current shape: two 6-7 line identical helpers in `scripts/src/download.py` and `scripts/src/fresh_install.py`. Proposed: move one into `bundle.py` (already the shared-constants module per the plan) and have both import it. Blast radius: 2 src files + their 2 test files. Effort: S. Risk: low, covered by existing tests. Independently shippable, but trivial enough it's arguably not worth a dedicated PR on its own (bundle with G8 or a routine touch of those files).

4. **Document the actual Python interpreter for `scripts/tests`** (G6). Current shape: `pyproject.toml`/plan says `python3 -m pytest scripts/tests`; the default `python3` on the reference dev machine has no pytest. Proposed: note the working interpreter (or a `requirements-dev.txt`/venv instruction) in `pyproject.toml` or the plan doc. Blast radius: docs/config only, no code. Effort: S. Risk: none. Independently shippable.

None of these four require serialization with each other or with anything outside `scripts/`, `hermes-provider/`, and `.github/workflows/` — they touch disjoint files.

## What is already good

- **The scripts-refactor plan was actually executed, not just written.** `scripts/src/` has all 12 modules the plan specified, `scripts/tests/` has all 9 test files, the three `.sh`→`.py` conversions happened, `run-baseline-queries.py`/`scoring-form.html` were removed, and a repo-wide `grep -rn 'scripts/.*\.sh'` (Agent A, verified) shows zero live/CI references left — only historical docs and the plan document itself, exactly per its own exclusion list.
- **Test quality is real, not decorative.** 137 tests pass; spot-checked assertions pin golden SHA-256 hashes, exact XML content, exact `SystemExit` messages, and round-trip equality — not `assert x is not None` filler.
- **`hermes-provider/ai-raccoon/client.py` is a genuinely careful integration client**: explicit `CONNECT_TIMEOUT_S=30`, `CALL_TIMEOUT_S=15`, `CLOSE_TIMEOUT_S=10` applied via `future.result(timeout=...)` on every transport operation (`client.py:28-30,64,78,95`), a background-thread-owned persistent asyncio session so stdio children aren't re-spawned per call, and a documented leak-prevention path (`connect()` cancels and closes on a timed-out `_open`, `client.py:63-70`). No call can hang forever.
- **The hyphenated `ai-raccoon` directory name is a deliberate, correctly-handled pattern, not a bug.** `hermes-provider/tests/conftest.py:1-7` documents it explicitly: "the plugin directory is named `ai-raccoon` ... so it cannot be imported as a normal Python package; these fixtures spec-load it the same way the Hermes memory-plugin loader does (importlib from file location)." `__init__.py:38-41` has a matching `try/except ImportError` fallback for the relative-vs-absolute import case.
- **Code matches its design doc exactly.** `docs/work/2026-08-06-hermes-ai-raccoon-provider-protocol.md`'s D1-D6 decision table (stdio default + HTTP option, curated 4-tool surface, `hermes-<profile>` project scoping, assistant-message sync content, no session-end summary, bridge coexistence) is implemented line-for-line in `hermes-provider/ai-raccoon/__init__.py` — no drift found.
- **MCP tool-name coupling is protocol-level, not path-level**, and therefore robust: `client.py` calls MCP tool names (`memory_search`, `memory_write`, `memory_stats`, `memory_share`) via the official `mcp` SDK rather than hand-rolled HTTP routes; those names are confirmed present server-side as `[McpServerTool(Name = TnMemoryWrite)]` etc. in `src/AiRaccoon/Tools/MemoryTools.cs:24-25,27,49,90`.
- **Version consistency holds today.** `PackageVersion`/`InformationalVersion`/`AssemblyVersion` in `src/AiRaccoon/AiRaccoon.csproj:14-16`, `.mcp/server.json`'s top-level `version` and package `version` (both `1.1.2`), and the latest git tag `v1.1.2` all agree; the release-commit convention (`chore(release): bump version to 1.1.2 (#86)`, `e23e0df`) is the project's real (undocumented-as-a-policy-but-consistent) release marker.
- **Central package management is clean**: `Directory.Packages.props` pins every dependency with an explicit `Version`, no floating versions found; two packages carry explanatory comments about *why* that exact version/provider was chosen (SQLite3MC encryption bundle choice, sqlite-vec pre-v1 pin).
- **The publish pipeline shows real engineering scar tissue, correctly retained**: `publish.yml`'s `patch-tool-shell.py` step exists specifically because of a shipped multi-RID bug (v1.0.2 shell uninstallable on macOS), is self-gating (fails unless all 6 RIDs appear exactly once), and its RID list matches the csproj's `RuntimeIdentifiers` exactly.
- **No hardcoded secrets anywhere in tracked files** — verified by direct grep and manual inspection of `nuget.config`, `.mcp/server.json`, and the only passphrase-related identifier (`AIRACCOON_DB_PASSPHRASE`) which never appears with a value.

## Durable project facts

- The scripts-refactor plan at `docs/plans/scripts-refactor.md` is not aspirational — it was executed. Its §1 inventory table and §2 target layout are accurate descriptions of `scripts/` as it exists today (verified 2026-08-07), except it predates `scripts/hermes-provider-setup.py`, which is real, tested, and simply missing from that plan's inventory.
- The only working Python test-runner interpreter found on this dev machine is `/usr/bin/python3` (system, has pytest) — the Homebrew `python3` (3.14.6) has no pytest installed. `pyproject.toml:6-8` sets `testpaths = ["scripts/tests"]`, which means a bare `python3 -m pytest` from repo root does NOT pick up `hermes-provider/tests` — that suite has its own `conftest.py` and must be invoked with an explicit path.
- `hermes-provider/tests/test_provider.py` and `test_status.py` (39 of 56 tests) require the `agent` package from a real Hermes installation (`agent.memory_provider.MemoryProvider` ABC) and cannot run in this repo's environment alone — `ModuleNotFoundError: No module named 'agent'`. Only `test_client.py` (4 tests, no `agent` dependency) and `test_setup_script.py` (subprocess-driven, ~6 tests) run standalone here.
- MCP tool-name source of truth for the AiRaccoon server lives in `src/AiRaccoon/Tools/MemoryTools.cs` as `Tn*` string constants (e.g. `TnMemoryWrite = "memory_write"` at line 24); the Hermes provider client hardcodes matching literal strings in its `_TOOL_DISPATCH` table (`hermes-provider/ai-raccoon/__init__.py:118-135`) — there is no shared contract test between the two repos, so a server-side tool rename would silently break the plugin.
- The multi-RID native-asset story (ONNX runtime, SQLite3MC, sqlite-vec) has no explicit per-RID `ItemGroup` wiring in `src/AiRaccoon/AiRaccoon.csproj` — those packages ship their own `runtimes/<rid>/native` assets and get selected automatically by `dotnet pack -p:RuntimeIdentifiers=<rid>`, one job per RID in `publish.yml`'s matrix. The only project-owned native asset is the bundled embedding model (`Models/*.onnx`, `Models/vocab.txt`), fetched fresh on every publish run by `download-embedding-model.py` (gitignored, SHA-pinned).
- This project has no CHANGELOG file, no `docs/changelog/` directory, and no automated release-notes generation. The de facto "release traceability" marker is: a `chore(release): bump version to X.Y.Z (#NN)` commit + a matching `vX.Y.Z` git tag, both created manually by the owner before dispatching `publish.yml`. `PackageReleaseNotes` in the csproj just points to the GitHub Releases page.
- `publish.yml` is `workflow_dispatch`-only (fully manual/human-gated) and uses NuGet Trusted Publishing (OIDC) with a `production` environment required-reviewer gate — no API key is stored in the repo.
- `build.yml` (PR/push-to-main gate) runs `dotnet build` + `dotnet test --filter "Speed=Fast"` only; the full test suite (including slow/integration/retrieval tests) runs only on `nightly.yml`'s schedule or manual dispatch — the workflow's own comment warns scheduled runs are best-effort and can be silently dropped by GitHub.
- `AIRACCOON_DB_PASSPHRASE` is the one security-relevant env var in this project (encrypted memory bank passphrase); it is declared with `isSecret: true` in `.mcp/server.json:16-19` and referenced only by name across the codebase, never with a value.
