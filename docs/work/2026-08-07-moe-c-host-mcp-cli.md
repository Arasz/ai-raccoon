# MoE panel — Expert C: host composition, MCP surface & CLI

Reviewer lane: `src/AiRaccoon/Program.cs`, `Setup/`, `Tools/`, `Access/`, `Observability/`, `Prompts/`.
Worktree: `.ai-badger/worktrees/full-project-review`. Read-only review; no production code touched.

## Verdict

The two-mode host is in better shape than its size suggests: the stdio/HTTP split is deliberate,
documented ruling-by-ruling in `docs/work/2026-08-06-http-serve-design.md`, and pinned by
`McpServerSetupHostTests` — I went looking for accidental divergence between the modes and found
that the two divergences that exist (HTTP-gated `ExtractionHostedService`, watchdog armed only by
`serve`) are both intentional and test-locked. The high-performance-logging invariant holds
completely: zero direct `logger.Log*` calls in 177 source files. Where the project has genuinely
eroded is **MCP stays thin**, and it has eroded in exactly one place, badly:
`ShareTools.ShareExtract` is not a tool, it is the shared-extraction pipeline — it validates
arity and limits that no service below it enforces, gates `autoPromote` on `confirm` as a rule
that exists nowhere else, and orchestrates store → extractor → queue in a loop that is
**duplicated byte-for-byte** in `ExtractionHostedService`, down to an identical private
`ToQueueCandidates` helper and its doc comment. Two copies of one pipeline, one of them living in
the transport layer, is the single most valuable thing to fix in this lane. Secondary themes: ~175
LOC of `RequireProjectId`/`RequireAsync`/`WrapAsync` copy-paste across all seven tool classes, a
third composition root in `CliCommandRunner` that builds a different object graph than DI does,
and `ServeRunner` as a stateful static class with its own logger factory that silently ignores
`--quiet`. The CLI is competent System.CommandLine usage with one fragile spot (parsing
`ParseError.Message` strings) and six interfaces that no second implementation will ever fill.

### Considered and dropped

These looked like findings and did not survive re-reading. Recording them so the panel doesn't re-litigate:

- **"stdio and HTTP hosts register different services — accidental divergence."** Dropped. `ExtractionHostedService` is HTTP-gated at `Dependencies.cs:118-124`, and that is documented three times (`2026-08-06-http-serve-design.md:53-58` citing PR #58 precedent; `README.md:59`; `docs/reference/agent-memory-server.md:248-249`) and pinned by `McpServerSetupHostTests.StdioOnlyHost_DoesNotRegisterTheExtractionHostedService` / `HttpHost_RegistersTheExtractionHostedService`. `WatchHostedService` and `BankMaintenanceHostedService` run in **both** modes. (A memory entry claiming "STDIO-only mode runs zero background services" is stale — the current code contradicts it.)
- **"`ai-raccoon --transport http` and `ai-raccoon serve` behave differently — unintentional."** Dropped as a defect; kept as a durable fact. Ruling R3 in `docs/plans/2026-08-06-http-serve-mode-plan.md:21` and `2026-08-06-http-serve-design.md:240-244` state the watchdog is `serve`-only *by construction*, via `ServerConfig.IdleTimeout` defaulting to `Zero`. Pinned by `ServerConfigTests.ToServerConfig_DoesNotSetIdleTimeout` and `McpServerSetupHostTests.HttpHost_WithoutIdleTimeout_DoesNotRegisterTheWatchdog`.
- **"`IdleWatchdog` drops in-flight work."** Dropped. `StopApplication()` triggers standard graceful shutdown: Kestrel drains in-flight requests and hosted services get their `stoppingToken` cancelled, bounded by `HostOptions.ShutdownTimeout` (framework default — grep confirms nothing overrides it). Background passes deliberately never signal the watchdog (`IdleWatchdog.cs:8`, design §3.3). The narrow residual case is C16.
- **"`CliCommandRunner` constructs services with `new` instead of DI."** Dropped as a violation. It is a self-documented one-shot composition root (`CliCommandRunner.cs:16-20`) that deliberately skips host bootstrap; that is the sanctioned chassis exception, and it is consistent across the whole file. The object-graph *difference* it produces is a real finding and is filed separately as C5.
- **"`memory_promotion_list` without `projectId` bypasses access control."** Reduced to C21 (Low). Reads are permitted in every access mode (`MemoryAccessGuard.cs:31-34`), so the skipped check grants nothing.
- **"Captive dependencies in the composition root."** Dropped — none found. Every registration in `Dependencies.cs` is a singleton, tool classes depend only on singletons, and the HTTP host runs `Stateless = true`, so nothing scoped is captured.
- **"`--transport https` is silently broken."** Dropped. It is explicitly declared unsupported and warns once (`McpServerSetup.cs:102-105`, `:189-192`).

## What is already good

- **The logging invariant holds completely.** Zero direct `logger.Log*` calls across 177 source files in all three projects, verified by several independent regex passes. All 56 `[LoggerMessage]` methods carry an explicit `EventId`. 19 of 20 `Log` classes are nested in their consumer; the one exception (`Program.cs:103`) is forced by top-level statements.
- **The two-mode split is designed, documented and tested, not accidental.** Every divergence I probed traced back to a numbered ruling in `docs/work/2026-08-06-http-serve-design.md` or `docs/plans/2026-08-06-http-serve-mode-plan.md`, with a matching test in `McpServerSetupHostTests`. The R1 three-registration/one-instance watchdog shape even carries an inline comment explaining *why* `AddHostedService<T>` alone would break the middleware.
- **`ServeRunner`'s probe-attach and bind-race handling is genuinely careful.** Probing before any bank/key/embedding work (`:44-51`), re-probing once on `AddressInUse` (`:70-77`), and refusing to silently fall back to a random port (`:73`) are the right calls, and `IsAddressInUse` (`:182-198`) correctly walks the inner-exception chain rather than matching a message first.
- **`IdleWatchdog`'s tick sizing.** `min(60s, timeout/4)` (`:38`) with the comment explaining that a fixed 60s tick would overshoot a 2s timeout by 62s — the kind of detail that usually only shows up after a flaky test.
- **Six of seven tool classes are genuinely thin.** `MemoryTools`, `WorkspaceTools`, `WatchTools`, `SweepTools`, `SyncTools` and `PromotionTools` do exactly guard → access check → delegate → map → envelope. `WatchTools.Add:52-70` and `SyncTools:71-98` translate typed domain exceptions into stable `McpException` error codes without adding rules — that is correct protocol-boundary work, not business logic.
- **`ToolExecutionActivity`** (`Observability/ToolExecutionActivity.cs`) is a clean, idempotent (`_recorded`) span+metrics unit applied uniformly across all 22 tools.
- **CLI output discipline is uniform** — errors to stderr, results to stdout, cancellation tokens threaded through every async signature, with no exceptions found across the 8 command files.
- **The single-channel configuration ruling is honoured.** Both host builders clear `Configuration.Sources` (`McpServerSetup.cs:51`, `:72`) so the settings table really is the only runtime channel.

- **`ExtractionHostedService` is registered only for HTTP/HTTPS hosts** (`src/AiRaccoon/Setup/Dependencies.cs:118-124`) because a stdio process is recycled in minutes. **`WatchHostedService` and `BankMaintenanceHostedService` run in *both* modes** (`Dependencies.cs:114-115`) — a memory entry claiming stdio runs zero background services is stale.
- There are **three composition roots**, not one: `McpServerSetup.CreateAppHost`/`CreateWebHost` (DI host), `Setup/CliCommandRunner.cs` (hand-built, no container, no host), and `Setup/Serve/ServeRunner.cs` (DI host + its own `LoggerFactory`). The CLI root builds a **different object graph** — `new SqliteMemoryStore(...)` at `CliCommandRunner.cs:38` skips the `MemoryExtensionHost` decorator that `Dependencies.cs:53-56` installs everywhere else.
- **All settings are bank-global, not per-project** (`docs/work/2026-08-04-cli-config-findings.md:16,147`). `ForgettingPolicyService.GetSweepThresholdAsync`'s `projectId` parameter is vestigial; `CliCommandTree.cs:133` correctly exposes `sweep threshold set {0..1}` with no project target, unlike `access set {project-id|*} …`.
- **The tool surface is 22 tools across 7 classes**: `MemoryTools` 9, `WorkspaceTools` 4, `WatchTools` 3, `ShareTools` 2, `PromotionTools` 2, `SweepTools` 1, `SyncTools` 1. Every tool returns `ApiEnvelope<T>` (`src/AiRaccoon.Core/ApiEnvelope.cs:11`) whose `ResponseMeta` always carries the waiting-promotions count — zero is informative, never absent.
- **`SelectTransports` (`McpServerSetup.cs:22-25`) always returns exactly one transport**; the combined `[Stdio, Http]` host path exists only via the internal 2-arg `CreateServerHost` overload used by tests. Anything reasoning about combined-transport behaviour is reasoning about a test-only path.
- **`--transport https` is declared but unimplemented** — `HandleHttpsTransport` (`McpServerSetup.cs:189-192`) returns the builder untouched; the single warning is emitted in `ConfigureMcpEndpoints` (`:102-105`) where the app logger exists.
- **System.CommandLine is pinned to 2.0.10** (`Directory.Packages.props:45`) and `Setup/Cli/CliRendering.cs` string-matches `ParseError.Message` templates, so a version bump is a **breaking change for CLI error messages** — the file says so at `:9`.

- **Serve reads `--port` and `--idle-timeout` instance-based, never by name** (`ServeRunner.cs:99-126`) — ruling R12: name-based `GetResult("--port")` resolves the *root* option, not serve's own.
