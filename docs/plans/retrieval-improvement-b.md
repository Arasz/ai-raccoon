# Retrieval Improvement Plan B — Measurement-First, Algorithmic View

> **Based on:** baseline-retrieval-report.md (2026-08-04)
> **Approach:** Make the baseline reproducible, then tune the algorithm against it
> **Parallel plan:** retrieval-improvement-A (source-first architecture, separate agent)
> **Point of view:** evidence-driven — every improvement claim must be measured against a
> reproducible harness before it ships. Complements plan A's structural view; where they
> overlap (source as first-class citizen) B treats it as a *searchability* problem, not only
> a data-model problem.

---

## 0. The Finding That Changes Everything: the Baseline Is Not Reproducible

Before any improvement is planned, the measurement itself must be trustworthy. Reading the
repo state against the report produced four discrepancies:

| # | Report claim | Repo state (verified 2026-08-04) |
|---|--------------|----------------------------------|
| 1 | "Seeded: 681 chunks from 166 files" | Committed `jsaa-memory.db` has **6675 entries / 352 distinct paths** — 10x more, and **71% (4723) from `docs/work/`**, which the ingestion design explicitly EXCLUDES |
| 2 | "Method: hybrid search (BM25 + vector)" | The committed DB has **0 embedded rows** (`embed_state='pending'` on all 6675), **empty `settings` table** (no embedding provider), and an empty vec0 table → `SearchAsync` degrades to **FTS5-only**. The report's hybrid numbers cannot come from this DB |
| 3 | "Matched at rank ≤3: 6/10" | `RetrievalBaselineTests` **hardcodes `IsExpectedSource=false`** (line 66) and `ExpectedSourceMatchesAtTop3=0` (line 85) — the C# test *cannot* produce the report's match figures. The Python runner needs `scripts/chunk-hash-map.json`, which **does not exist** in the repo (the script warns "isExpectedSource detection disabled") |
| 4 | Report dated 10:36Z | `scripts/baseline-results.json` is a **failed run** (403 Forbidden on every query — server not up). The report's source run is not in the repo |

**Root cause:** the report was generated by the *curated* ingestion pipeline
(`ingest-jsaa-docs.py` → structured paths like `docs:adr/0011...#decision` → live MCP server
→ `run-baseline-queries.py` + a local `chunk-hash-map.json`). The committed DB was produced
by a *different* path — `memory_ingest_directory` semantics (absolute paths, raw
TokenizerChunker chunks, no structured section anchors, no embeddings). The two pipelines
have **diverged**, and the committed artifact cannot reproduce the committed report.

**Consequence for every downstream improvement:** any change measured against the broken
harness produces unverifiable numbers. Wave 0 of this plan is the measurement fix.

## 1. What Works Well (evidence, not vibes)

Measured on the committed DB (FTS5-only, since the vector modality is dead in it) for the
report's 10 expected-source queries:

| Query | Expected | Rank on committed DB (FTS) | Report |
|-------|----------|---------------------------|--------|
| A1 shadcn/ui | ADR-0011 | **1** | 2 |
| A2 UUID | ADR-0004 | n/a (not checked in repro) | 3 |
| A3 offer-page fetch | ADR-0006 | **1** | 4 |
| A4 MCP server | ADR-0060 | **1** | 5 |
| A5 LLM cost NFR | ADR-0046 | n/a | 3 |
| A6 data erasure | ADR-0067 | 4 (ADR-0068 wins at 1) | NOT FOUND |
| A7 ADR-0070 | ADR-0070 | NOT FOUND (README wins) | NOT FOUND |

1. **Whole-file-path indexing pays off.** Because the committed DB stores the absolute file
   path per entry and chunks carry the ADR number in their title, A3/A4/A6 rank *better* than
   the report claims. The pipeline finds the right *file* when the query names a distinctive
   token ("mcp", "offer-page").
2. **100% coverage is real.** All 35 queries return results even in FTS-only mode — the
   OR-joiner guarantees recall, at the cost of precision.
3. **Short, keyword-dense documents win** (invariants at rank 1). BM25's length
   normalization rewards dense chunks — a property to exploit, not fight.
4. **The fusion/sweep measurement infra already exists.** `SweepRunner`, `SweepMatrix`
   (k ∈ {10,30,60} × weights), `RetrievalMetrics` (nDCG@k, MRR, recall@k), the golden
   parity harness, and `ManagedHarness` are all in `tests/Unit/Retrieval` — built for
   exactly the parameter/quality work this plan proposes, currently wired to the benchmark
   corpus rather than the JSAA baseline.

## 2. What's Bad, Mapped to Features

### 2.1 The measurement harness is disconnected (critical)

- **Symptom:** report unreproducible; test asserts `totalWithResults >= 1` only.
- **Missing feature:** an in-repo, deterministic baseline runner that (a) uses one canonical
  DB, (b) computes expected-source matches itself, (c) emits nDCG/MRR/recall, (d) is a gate.
- **Where:** `RetrievalBaselineTests.cs`, `scripts/run-baseline-queries.py`,
  `scripts/chunk-hash-map.json` (absent), DB provenance.

### 2.2 Custom context labels are write-only (structural gap vs design)

- **Symptom:** `memory_write(context="docs:adr")` writes `scope='custom'` rows that
  `SearchContexts.For` never queries (it only builds shared/project/workspace filters).
  The ingest script had to **smuggle the context into the content text**
  (`"[docs:adr] docs:adr/0011-...#decision\n\n## Source: ..."`) to make it retrievable.
- **Why it matters:** the design (§2.2, §3.4) promised typed, searchable contexts. Today the
  source identifier lives in three inconsistent places — `path` column (absolute path),
  content text (`## Source:` header), and `agent_id` — and **none of them influences
  ranking**.
- **Missing feature:** searchable source identity — the user's "source as first-class
  citizen" ask, formulated as a retrieval feature: an FTS-indexable source field that
  ranking can weight, not a string buried in `value`.

### 2.3 FTS query construction destroys precision

- **Symptom:** A7 "What is ADR-0070 about?" → normalized to
  `what OR is OR adr OR 0070 OR about`. Stopwords and generic tokens match nearly every
  document; BM25 then ranks by length, so `README.md` beats the ADR itself.
- **Verified mechanism:** ADR-0070 has 19 chunks in the DB, but **only 1 contains the token
  "0070"** (the title chunk). The number lives in the title; the content lives in 18 other
  chunks. `bm25()` length normalization then punishes those long chunks.
- **Missing feature:** query rewriting — stopword removal, phrase/AND semantics for
  identifier-heavy queries, and numeric-token handling ("ADR-0070" should become a
  *required* `adr AND 0070` clause, not one OR token among six).

### 2.4 Chunk/token granularity vs identifier retrieval

- **Symptom:** ADR numbers appear only in title chunks; section-level queries ("What does
  ADR-0011 *decide*?") have no anchor to target.
- **Missing feature:** section-aware chunk identity (plan A's `ChunkIndex`/`section_slug`),
  plus a way for the query to say "this ADR, this section".

### 2.5 No modality attribution

- **Symptom:** we don't know which queries are keyword-carried vs semantic-carried; the
  report's hybrid claim is unverifiable because the committed DB has no vectors at all.
- **Missing feature:** per-query ablation (FTS-only / vector-only / hybrid) in the baseline
  report, and a gate that fails when a modality is silently dead (0 embedded rows should
  have been a red flag).

### 2.6 Baseline blind spots (agree with plan A, add two)

- Per-query relevance grading (binary `isExpectedSource` is too coarse — rank 4 vs 5 vs
  absent all count as "miss").
- **Difficulty stratification** (easy/medium/hard by token overlap and document length).
- **Cross-chunk relevance** (any chunk of ADR-0067 acceptable, not a single hash).
- **Negative-test honesty:** with 71% of the committed DB from excluded `docs/work/`,
  "H2 what happened today?" now legitimately hits work records — the exclusion contract is
  violated by the corpus itself, so negative tests are meaningless until the corpus is fixed.

## 3. New Baseline Cases to Expose More Detail

### 3.1 Reproducibility cases (must exist before anything else)

```
R0  Same DB, same code, two runs → identical top-5 per query (determinism gate)
R1  Embed the committed DB (memory_configure + embed_pending) → report hybrid + FTS-only
    side by side; flag any query where the modalities disagree on the expected source
R2  Corpus-integrity checks: expected excluded dirs absent (docs/work/, state.json,
    now.md), expected included files present, embed_state='embedded' for 100% after R1
```

### 3.2 Query-construction exposure cases

```
Q1  "What is ADR-0070 about?"            → expected: any ADR-0070 chunk
Q2  "ADR-0070"                            → same expectation (identifier-only variant)
Q3  "documentation structure trust model" → same expectation (content-only variant,
                                            no number) — isolates numeric-token reliance
Q4  "What does ADR-0011 decide?"          → expected: the Decision-section chunk
Q5  "offer-page fetching security"        → expected: ADR-0006 (no question words)
Q6  "Is TDD required?"                    → control: must stay rank 1 under all rewrites
```

The Q1/Q2/Q3 triplet is the key instrument: it tells us whether the failure is
tokenization (Q2 fails, Q3 works), content spread (all fail), or ranking (found, wrong
rank).

### 3.3 Ablation & attribution cases

```
For every expected-source query: run FTS-only, vector-only, hybrid; record which modality
first surfaces the expected source and at what rank. Gate: no query may regress in hybrid
vs the better single modality (RRF must be >= max(single) in rank terms, not just in score).
```

### 3.4 Cross-document discrimination cases

```
X1  "ADR-0046 vs ADR-0022: which was retired?"   → ADR-0046 must outrank ADR-0022
X2  "erasure" (A6 family)                        → ADR-0067 and ADR-0068 both in top 5
X3  "aspire config" (H3)                          → should return ADR-0029/architecture,
                                                    NOT docs/work/plans
```

## 4. Improvements

### 4.1 Wave 0 — Make the baseline reproducible (gate for ALL other work)

1. **Pick one canonical corpus.** Either regenerate `jsaa-memory.db` via the curated
   pipeline (structured paths, `## Source:` headers, section chunks) or commit the
   *current* DB as "FTS-only baseline" — but stop pretending the report describes the
   committed DB. Recommend: **regenerate via `ingest-jsaa-docs.py`** (it matches the
   design and the report), then commit the DB + `chunk-hash-map.json` together.
2. **Fix `RetrievalBaselineTests`** to compute expected-source matches itself (path/prefix
   or hash-map matching), assert the actual match rate, and emit a machine-readable report.
3. **Embed the corpus** before measuring hybrid (one `memory_configure` + `embed_pending`
   step in the harness); add an assert that embedded count == entry count.
4. **Wire `SweepRunner`/`RetrievalMetrics` to the JSAA baseline** (they exist; point them
   at the 35 queries): nDCG@5, MRR, recall@5 per category.

**Gate:** the test reproduces the report's 6/10 (or documents the new number) on a clean
checkout; two consecutive runs are byte-identical.

### 4.2 Wave 1 — Query construction (algorithmic, test-first)

1. **Stopword drop** in `FtsQueryNormalizer`: strip question words/articles/prepositions
   (`what, is, the, how, does, about, are, do, ...`).
2. **AND for short identifier queries:** if the query contains an identifier token
   (e.g. `\bADR-\d+\b` → `adr` + number), emit `adr AND 0070`; otherwise keep OR for
   recall. This directly targets Q1/Q2.
3. **Phrase support for quoted input** (future-proof; not needed for the 35).
4. Re-run baseline; gate: Q1/Q2 expected source found at rank ≤3, C1 (TDD) unchanged at 1.

**Expected effect:** the noise tokens that let README beat ADR-0070 disappear; BM25 scores
concentrate on real signal. Cheap, no schema change, immediately measurable.

### 4.3 Wave 2 — Source as a *searchable* first-class citizen (structural)

Plan A proposes the schema/ranking side (source_file column, chunk index, source-affinity
boosts). This plan's complementary slice, framed as retrieval:

1. **Stop embedding provenance in `value`.** The `## Source:` header and `[context]`
   prefix currently pollute BM25 (path tokens count as content tokens) *and* make hash
   matching fragile (hash depends on the exact prefix formatting).
2. **Index the source separately.** Add the structured source path to the FTS index as an
   additional column (or a `source` column joined in) with a **column weight**, so
   `ADR-0070` and `decision` match the *source*, not the content. FTS5 supports
   `bm25(fts, 0.0, 1.0)` per-column weights — the mechanism is already there.
3. **Expose source in results** (plan A's `SourceFile`/`ChunkIndex` in
   `MemorySearchResult`) so clients can group/display provenance — a reporting win even
   with zero ranking change.
4. **Make `context_label` searchable:** either include custom-scope rows when a context
   filter is requested, or map context labels into the project scope with a `context_label`
   filter on search. This restores the design's §2.2 promise.

**Gate:** Q4 (section query) finds the Decision chunk; results carry source identity; a
query for a source path (`docs:adr/0011-frontend-chassis-stack.md#decision`) returns that
chunk. No regression on invariants.

### 4.4 Wave 3 — Ranking: length normalization & fusion tuning

Measured findings to act on (not guesses):

1. **BM25 length normalization vs chunk size.** Long ADR chunks lose to short docs purely
   on length. Options: (a) reduce chunk max tokens for ADR-like content, (b) accept it and
   let source-column matching carry identifier queries, (c) test `bm25` column weights.
   Decide with a sweep, not an opinion.
2. **RRF parameter sweep on the JSAA baseline** using the existing `SweepMatrix`
   (k ∈ {10,30,60} × weights {(1,1),(1,2),(2,1)}), extended if needed:
   - k=30 rewards top ranks harder (good if precision is the goal);
   - vector-weight=2 favors semantic matches (helps conceptual queries like A6);
   - fts-weight=2 favors keyword matches (helps identifier queries like A7).
   Select the Pareto point on nDCG@5/MRR; record it in an ADR. **This is pure
   configuration — the sweep harness exists today.**
3. **minScore interplay:** the MCP default `minScore=0.7` with RRF-normalized scores can
   silently drop rank-3+ results; the baseline uses 0.0. Measure what fraction of
   *correct* results sit below 0.7 and tune the default or the normalization.

**Gate:** chosen parameters beat current (k=60, 1:1) on nDCG@5 without regressing C1-C6;
sweep results committed alongside the ADR.

### 4.5 Wave 4 — Corpus hygiene & negative-test honesty

1. Re-ingest with the curated exclusions (`docs/work/` and friends) so negative tests are
   meaningful again.
2. Add the integrity checks from R2 as permanent harness assertions.
3. Add graded relevance (1-5) for the 10 expected-source queries (plan A's proposal), plus
   the Q/X cases from §3.

**Gate:** H1-H3 pass *because the corpus excludes the content*, not by luck of ranking;
R2 checks are green.

## 5. Sequencing & Dependency between A and B

| Wave | Plan A (structural) | Plan B (algorithmic) | Depends on |
|------|--------------------|----------------------|------------|
| 0 | — | Reproducible baseline | nothing |
| 1 | source_file column, chunk index | Query construction | B0 (to measure) |
| 2 | Source-affinity RRF boosts | Source-indexed FTS, searchable context | A1 + B1 |
| 3 | Document-first ranking | RRF/BM25 sweep, minScore | B0 + A1 |
| 4 | Baseline enrichment | Corpus hygiene, graded relevance | both |

A's schema/ranking work and B's query/sweep work are **independent once B0 exists** — they
touch different files (`MemorySchema`, `SqliteMemoryStore` search path vs
`FtsQueryNormalizer`, `ReciprocalRankFusion`). The merge point is the baseline harness:
both must run their gates against the same reproducible runner.

**Recommended merge order into the combined plan:** B0 (reproducible baseline) →
B1/A1 in parallel → A2/B2 converge on source identity → B3 (sweep) → A3 → B4.

## 8. Open Questions for the Combined Plan

1. **Which canonical corpus?** Regenerate via `ingest-jsaa-docs.py` (matches design +
   report, but requires the jsaa tree at a pinned commit) vs commit the current DB as an
   explicit "FTS-only, raw-ingest" baseline. This decision gates B0; recommend asking the
   repo owner.
2. **Where did the committed DB come from?** It matches `memory_ingest_directory`
   semantics, not the curated script. If the jsaa side now ingests via its own pipeline,
   the *shared* contract for source identity (structured path format) must be agreed
   between repos — plan A's `source_file` schema and B's FTS source column both depend on
   that contract.
3. **Stopword list:** fixed list vs corpus-derived (token frequency). Start fixed; revisit
   only if a query regresses.
4. **minScore default:** is 0.7 a product decision (fewer, better results) or an accident?
   Sweep data will tell us the cost; the product owner decides the default.
5. **Context-label searchability:** should `memory_search(context="docs:adr")` search only
   that label, or boost it? Plan A's schema change and B's filter change must agree.
