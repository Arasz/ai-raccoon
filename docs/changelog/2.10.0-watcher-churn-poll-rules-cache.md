# 2.10.0: the watcher polls every 10 s, keeps its ignore rules, and stops logging a skip as a write

Performance release. No schema change.

- **The watch registration poll runs every 10 seconds, not every second.** Each pass opened the bank once for
  the registration list and twice per enabled registration for its settings — 3–4 unpooled opens per second at
  idle, on a loop that ran 86,400 times a day. What rides on the interval is only how fast a registration another
  process added, removed or disabled is acted on. A watch added by the CLI, or by this server, becomes live at the
  next pass — watcher started, initial scan queued — for a registration that pass does not already hold active and
  that watching is enabled for: up to one interval plus the time the pass before it and the pass that starts it each
  spend getting to that point, instead of about a second. Ten seconds is the delay between passes, not a deadline.
  File events still drain on their own one-second tick.
- **`ai-raccoon.ignore` is parsed once per root, not on every filesystem event.** The parsed rules are reused
  while the file's last write time and length stay put, and re-read as soon as either moves, or when the watch
  observes an edit to the ignore file itself — so an edit is still seen, and a repo under active edit stops
  re-opening the same file for every event (twice per digest). Renaming the ignore file away now invalidates the
  cached rules and queues the same full rescan a delete does, which it did not before. The one edit that can still go
  unseen is a same-length rewrite inside one timestamp tick on a filesystem with coarse timestamps (FAT, 2 s) whose
  edit event never arrives — there, the previous rules stay in force until the file's timestamp next moves.
- **A replace-by-path skip logs at Debug, under its own EventId 896, with its reason.** A watch digest that
  loses the race for its own path — another digest already committed the fingerprint, or holds the path's claim —
  writes no rows. That is correct behaviour, but it was printed at Information through EventId 899 with
  `0 row(s) written`, so a healthy skip read like a write, and on Windows (where one save delivers several
  events) the line was continuous. EventId 899 now means a replace ran. `write.replace.wait_ms`, `held_ms` and
  `rows` still record on both paths that reach them — a claim-stage skip and a completed replace — so a skip stays
  measurable; a digest that returns before either, because the fingerprint already matched, records nothing either
  way.

Found by a Windows report of constant disk reads and a log full of `Replace-by-path waited 0.0 ms … 0 row(s)
written`. #963. [ADR-0151](../adr/0151-the-watcher-polls-at-10s-caches-ignore-rules-and-logs-a-skip-at-debug.md)
