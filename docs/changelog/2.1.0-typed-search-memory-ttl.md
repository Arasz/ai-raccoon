# 2.1.0: typed search and Memory-only TTL

PR #913 adds the Memory/File distinction within the memory bank and makes it part of search.
`query` takes `entryType`, a comma-separated, case-insensitive subset of `memory`, `code`, and
`file`. Omission searches everything, including rows not yet classified. Narrow selections
restrict FTS, content vectors and structure vectors before candidate truncation, so a minority
type cannot disappear behind excluded neighbors. Code keeps its separate corpus.

`get_entry` requires one `entryType`. A hash shared by corpora resolves only in the selected
type. The response's existing `entryType` still names its corpus; the added `entryKind` names
Memory, File or Code. Update callers and reconnect clients to refresh the tool schema.

Memory means agent notes and transcripts. File means a mirrored document; notes that cite a
file remain Memory. Explicit write-path declarations win over historical shape classification.
`set_memory_ttl` accepts Memory, including chunked transcripts, and refuses both setting and
clearing a File TTL. Sync and rechunking prevent new File TTLs. Cleanup still honors an explicit
TTL stored before this change.

The bank upgrades through v20 (stored kind), v21 (native typed vector partitions) and v22
(search-quality masks). Historical quality records retain their identities, grades and usage;
the old `memory` selection becomes Memory plus File. New queries record their exact mask.
Fresh banks and upgrades from released versions enforce the kind domain in SQLite.

**Back up before upgrading. 2.1.0 migrates your bank to v22; 2.0.x can no longer open it.**
There is no automatic downgrade. Unreleased development banks that already had the kind column
are not rebuilt merely to change its constraints; the doctor still exposes their unclassified
or unknown values.
