# 1.59.3: concurrent searches run in parallel

Performance fix. No tool schema or settings changes.

- Searches issued at the same time no longer queue behind each other. SQLite's allocation
  statistics took one process-wide mutex on every malloc and free, so connections running at
  once spent most of their time waiting on it; they are now switched off before the library
  initialises (`SqliteEncryptionInit`). On a 1,500-entry bank, eight concurrent searches take
  about 3x one search instead of about 11x, and sixteen about 5x instead of 20x.
- `memory_performance` buffers measurements and flushes every 30 seconds
  (`settings performance flush-interval`), so a window opened right after a burst of calls can
  show only the ones already flushed.
