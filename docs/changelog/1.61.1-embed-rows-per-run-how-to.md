# 1.61.1: the embed drain's rows-per-run, and how to change it

The `embed-rows-per-run` setting was widened to 64..4096 in 1.61.0, and the mechanics of a
drain pass were written down for the first time. What was still missing was the thing an
operator actually needs: a page that says how to change the value, and the CLI help that names
the setting it writes.

**A how-to page** ([docs/how-to/change-the-embed-rows-per-run.md](../how-to/change-the-embed-rows-per-run.md))
walks the whole path. It gives the command
(`ai-raccoon settings maintenance embed-rows-per-run <rows>`), the settings key it writes
(`maintenance.embed-rows-per-run.global`), the table the row lands in (the bank's `settings`
table), who reads it (the embed drain, on every pass, for both corpora) and when it takes
effect (the next pass, no restart). It shows the read-back (`settings maintenance list`), the
refusal for a value outside the range, the exit codes the command can end on, what a bigger
pass costs in managed memory, and what the value does *not* change (the per-row cost, the
native ONNX peak, the transaction scope).

**The CLI help names the path too.** `settings maintenance embed-rows-per-run` now says which
settings key it writes and how to read the value back, and the `settings maintenance` node
describes the third verb it has always had. The range, the default and the "next pass, no
restart" wording are unchanged.

Every command in the page was run against a temporary bank, and the row it writes was read back
out of that bank's `settings` table.
