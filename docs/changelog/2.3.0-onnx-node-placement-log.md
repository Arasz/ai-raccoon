# 2.3.0: the log says where ONNX Runtime put each model's nodes

## New

Each ONNX Runtime session the server builds now logs one line naming which execution provider got which
nodes, for example:

```
ONNX Runtime node placement for granite-embedding-small-english-r2/model.onnx: CoreML: 305/400 original nodes in 37 fused partitions; CPU: 95 — Reshape×48, Neg×24, MultiHeadAttention×12, Slice×4, Expand×2, Range, Abs, Greater, Unsqueeze, Gather
```

It replaces ONNX Runtime's generic warning, "Some nodes were not assigned to the preferred execution
providers…", and its "Rerunning with verbose output" hint. The same line covers every provider: CPU, CoreML,
WebGPU, MLX and CUDA. CoreML's partitions are counted against the original graph from CoreML's own report.
Other providers that compile fused partitions show the partition count, and the rest show their op types.
When ONNX Runtime reports no placement for a session, the line says so (event 451) instead.

Events: 450 is the placement line, 451 is "not reported", and 452 is any other ONNX Runtime warning or error
from a session being built, now written through the server's logger instead of straight to stderr.

## How it works

ONNX Runtime reports node placement only when the session logger is exactly at verbose severity. The server
now creates the ORT environment with a log callback and builds every session at verbose. The callback keeps
the placement lines while a session is being built and drops every verbose and info line after that.
Measured on an Apple M4 with WebGPU, which logs about 337 info lines per run: 13.5 ms per run with or without
verbose (300 runs, three rounds), and no CPU difference above run-to-run noise. Research record:
[2026-10-23-ort-node-placement-logging.md](../work/2026-10-23-ort-node-placement-logging.md).
