# 1.53.4: watched files whose change event was missed get re-digested

Fix release.

- A watched file whose change event never reached the server (a `git checkout` burst, a digest
  that failed, a watch stopped after five failures) is now re-digested. Until now the catch-up scan
  compared each file's mtime with the watch's last-change time, which every digest of any other
  file moves forward, so one later digest of a sibling hid the missed file for good. The scan now
  compares each file with the time its own fingerprint was written, and with the file size the
  digest recorded, which also catches content restored with an old mtime (`cp -p`, `tar -x`)
  ([ADR-0121](../adr/0121-restart-catch-up-compares-each-file-with-its-own-fingerprint.md)).
- The server no longer waits for a restart to heal. Every watch that has not stopped gets that scan
  every 5 minutes, and a watch whose digests start succeeding again after a failure is scanned
  right away.
- The catch-up scan no longer walks `.git`, `node_modules`, `bin`, `obj` or other hidden and
  excluded directories. On the author's ten watched roots one scan went from about 7.5 CPU-seconds
  to about 0.1. `memory_ingest_directory` uses the same walk, so an unreadable `node_modules` or
  `.git` no longer makes it fail.
- Banks that already hold stale files heal on the first scan after the upgrade, with no command
  needed. The bank gains a `watch_files.size` column on first open; existing rows fill it in as
  their files are next digested.
