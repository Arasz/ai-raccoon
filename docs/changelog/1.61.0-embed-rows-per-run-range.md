# 1.61.0: the embed drain's rows-per-run is configurable from 64 to 2048

The embed drain — the single consumer that turns pending rows into embeddings for both the memory
and the code corpus — takes one signal and drains a bounded number of rows per pass. That bound
has been settable since WP11-C (`ai-raccoon settings maintenance embed-rows-per-run {rows}`), but
the accepted range was "any positive integer, at most 4096", so a value of 1 was legal.

The range is now **64 to 2048**, default still 128:

- **The floor (64)** is two full embedder sub-batches (the embedder batches 32 rows per generator
  call). A drain pass that reaches its budget re-signals itself, and every pass opens the bank,
  reads the setting and opens a telemetry span before it embeds anything — below 64 rows a pass
  does at most one generator call, so that fixed cost stops being amortised over the work.
- **The ceiling (2048)** keeps the reason the old 4096 ceiling had: the drain materialises its
  whole `SELECT … LIMIT` result as one list before sub-batching it, and 2048 rows is half the
  previous worst-case burst. It is also still 16× the default.

The default is unchanged, so a bank that never set the value behaves exactly as before. A value
outside the range is invalid: the CLI refuses to write it, and a value already in the settings
table is clamped to the nearest bound by the drain, which warns once per distinct bad value
(event id 1006) instead of silently using it.

```bash
ai-raccoon settings maintenance embed-rows-per-run 512   # 64..2048
ai-raccoon settings maintenance list                     # shows the effective value
```
