# 1.54.0: memory chunks and query trimming move to 1022 tokens

Feature release: config D chunk budgets. The code corpus stays at 510-token chunks.

- Memory chunks are now 1022 content tokens (were 254), set by the bundled model manifest's
  `chunkTokens`. The 2026-09-24/25 measurements behind the change are summarized in
  [ADR-0125](../adr/0125-config-d-memory-chunks-1022-code-stays-510.md): memory retrieval gains
  about +0.166 MRR at 1022, while code retrieval loses there — so code chunks stay at 510.
- Query trimming follows the chunk budget to 1022 tokens by design (the coupling is deliberate,
  ADR-0125). A query is trimmed only past 1022 tokens now (was 254), and the "query too long"
  warning fires later — past roughly 4,000 characters of English prose instead of 1,000.
- **Upgrading migrates your bank on first start.** Every bank re-chunks and re-embeds once on its
  own; the bank refuses tool calls until that finishes, minutes on a large bank. Rows whose chunk
  boundaries move lose their per-row rating, access count and last-access time — for notes nothing
  else goes (source, section, scope, the creation timestamp and the entry TTL carry over; the
  update timestamp is refreshed), while file rows
  re-chunked from disk also lose their TTL: a file carries none for the ingest to read, so an
  expiring file row stops expiring until a TTL is set again. Rows with nothing re-chunkable —
  source file gone, unreadable, or a type the product cannot chunk — keep their stored chunk
  bounds and are only re-embedded. A note whose chunks never reassemble provably is retried across
  three server starts and then left as-is, so one unprovable note cannot re-open the upgrade
  forever (ADR-0125).
- On `device mlx` the chunker's 1022-token rows align exactly with the 64-token padding buckets
  (1022 + 2 = 1024), so the padded footprint stays near 3.7 GB. The padding precondition is now
  pinned by tests (ADR-0114).

- The research harness under `scripts/` now follows the shipped budget instead of repeating it:
  its embedding window is read from the bundled manifest (`chunkTokens` + 2), and the stale
  256-token literal in `data/knobs.json` is gone.
- `scripts/retrieval_tuning/corpora/eval-set-100.json` stays byte-stable on the bank-copy pin it
  was generated from (that copy is retired), for research comparability and because the MiniLM
  golden-vector tests read its query texts. Its copy-gated refresh test now reports a moved copy
  as the provenance gap it is instead of failing on an honest pin; the eval set re-anchors once,
  against the first 1022-era bank copy.

Planned follow-up, not in this release: a post-merge 254-vs-1022 retrieval measurement on a live
bank, including the WebGPU footprint question and the re-chunk pass's own wall-clock (ADR-0125).
