# 1.53.2: one memory row that cannot embed no longer blocks the rest

Fix release (#537, PR #774).

- A memory row whose embedding call fails used to fail its whole 32-row batch on every drain
  pass. The healthy rows beside it stayed pending, `memory_embed_pending` kept failing for the
  project, and an open model migration could never finish, so the bank stayed locked. A failed
  batch is now retried one row at a time. A row that fails on its own is given up on after three
  attempts, logged as event 444 with its id and source, and still counted in
  `memory_stats.pending`. Rewriting the entry or switching the embedding model gives it a new try.
- An engine that cannot answer at all, or a bank busy with another writer, fails the pass as
  before and gives up on no row.
- The structure-vector backfill in `memory_embed_pending` skips a heading that cannot embed
  instead of failing the call. The row keeps its content vector.
- Existing banks gain an `entries.embed_attempts` column on first open. Rows already stuck
  behind a bad row recover on the next drain with no manual step.
  ([ADR-0119](../adr/0119-poison-memory-rows-are-isolated-and-abandoned.md))
