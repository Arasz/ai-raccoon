# 0050. The sweep gates search with pinned query vectors

Date: 2026-08-14

Status: Accepted — the decision stands; the pinned values were regenerated at ADR-0090.
`gate-query-vectors.json` carries query text and embeddings only, never document text, so the
mechanism ported unchanged when the corpus was replaced; its 44 vectors were re-derived on
arm64 for the new query catalog.

## Context

ADR-0049 measured that the bundled u8s8-quantized model returns materially different query vectors
on three arithmetic paths, and that `SourceAffinitySweepTests`' and `RrfParameterSweepTests`'
`chosen.AdrNdcg5` is therefore a function of the host CPU:

| Host arithmetic | AdrNdcg5 |
|---|---|
| macOS arm64 (NEON) | 0.5260827785380623 |
| Linux x64, no VNNI | 0.5587755695473325 |
| Linux x64, VNNI | 0.48859561353453607 |

Both gates pinned the arm64 number, which no GitHub-hosted Linux runner produces. A green Linux run
meant the job landed on a non-VNNI host, not that ranking was correct.

The two sweeps exist to measure fusion and ranking *configuration* — RRF k, the weight ratio,
minScore, the candidate window, source-affinity λ, the consolidation threshold, the document-score
formula. The embedding model is an input they were never trying to vary. The corpus vectors are
already fixed (committed in `tests/AiRaccoon.Tests/Resources/jsaa-memory.db`); only the *query*
vector was recomputed per run, because the sweeps search with `VectorWeight: 1` against a bank
carrying `embedding.provider='local'`. That asymmetry is what the gates were measuring.

ADR-0049 listed three ways forward and took none of them, because two are product decisions:
re-quantizing with `reduce_range` and shipping the fp32 model both change what the server returns
to users. Its option 1 — pinning the query vectors — changes only what the tests feed themselves.

## Decision

**Give the two sweep gates a committed query vector per catalog query, so their metric is a
function of the ranking configuration and the corpus alone.**

`tests/AiRaccoon.Tests/Resources/gate-query-vectors.json` carries one entry per query in
`scripts/baseline-queries.json` (44 of them): the query text, the 384-float vector as base64
little-endian float32, and its sha256. `PinnedQueryEmbeddingService` is an `IEmbeddingService`
that answers from that file and **throws** on any text it does not carry — there is no fallback to
the live model. `SourceAffinitySweepTests` and `RrfParameterSweepTests` construct their store with
it. Nothing in `src/` changes; the shipped model, the shipped embedding path and the product
question ADR-0049 raised are all untouched.

The fixture is regenerated by `GateQueryVectorRegenerationTool`, env-gated on
`AIRACCOON_REGENERATE_GATE_QUERY_VECTORS`, which records the arithmetic path, the runtime, the
model and vocab sha256, and the date into the file it writes.

**These vectors are not ground truth.** They are one of ADR-0049's three answers — the arm64 one,
because that is the machine the fixture was generated on, and the machine
`JsaaCorpusRegenerationTool` produced the corpus vectors on, so query and corpus at least come from
the same arithmetic. Which of the three is correct remains open and is not decided here. The
fixture says so in its own `Note` field, and a gate asserts that text is still there.

### Re-pinning

Both gates move from `>= 0.526 - RankingTolerance` to `>= 0.5260827785380623 - RankingTolerance`.
The number is the same to three decimals — the fixture reproduces the arm64 path exactly — but what
it measures is not. This is the one re-pin in this suite that is a correction rather than an
evasion: the old pin was a property of a machine, this one is a property of the fixture and the
ranking configuration. `GoldenFile.RankingTolerance` is unchanged at 5e-3; no bound was widened.

## Consequences

**What the gates no longer notice.** They stop exercising the live ONNX query-embedding path, so an
embedding regression cannot fail them. That coverage was never theirs alone and did not move:
`Integration/Embedding/EmbeddingServiceTests` asserts the local engine's dimension, unit norm and
semantic ordering; `BaselineMetricsTests`, `SectionTargetedRetrievalTests`, `SourceIdentityTests`,
`QueryConstructionTests`, `RetrievalBaselineTests` and `RelativeScoreFloorTests` all still search
the same corpus through the live model; `PlatformNumericsProbe` still reproduces ADR-0049's table
on demand. What is genuinely gone is the *accidental* signal these two sweeps carried — a red CI run
that turned out to be a numerics finding. ADR-0049 is that finding, written down.

**What keeps the fixture from drifting silently.** Four things, each watched failing before being
trusted:

- The lookup key is the exact query text. A changed query embeds nothing and throws — it cannot
  quietly fall back to the live model and reintroduce the host variable.
- `Fixture_CoversExactlyTheQueryCatalog` derives the expected set from `scripts/baseline-queries.json`
  and fails in both directions, so a query added to the catalog or left behind in the fixture is a
  red test, not a runtime surprise.
- `Fixture_RecordsTheModelThatProducedIt` compares the fixture's recorded shas with
  `BundledModel.ModelSha256` / `VocabSha256`. Taking either of ADR-0049's remaining options —
  re-quantizing or shipping fp32 — changes those constants and fails here, so a new model cannot be
  scored against stale query vectors.
- `Fixture_RecordsItsProvenance` and `Fixture_VectorsAreUnitNormAtTheDeclaredDimension` keep the
  date, the arithmetic path, the "NOT ground truth" note and the per-entry sha256 honest.

**What still moves the gates.** Measured by mutation, each applied as a real edit, run, and
reverted: inverting RRF's rank decay drops `AdrNdcg5` to 0.1032 and fails the re-pinned floor in
both sweeps; changing the decay to `k + rank*rank` fails `RrfParameterSweepTests`' hybrid-vs-single-
modality fusion gate (hybrid exact rank 3 against a best single modality of 1); widening
`SourceAffinityRanker`'s adjacency window from `== 1` to `<= 2` fails `SourceAffinitySweepTests`'
A1 file-rank gate (5 against a bound of 3). The nDCG assertion remains a one-sided floor, so a
change that *improves* the metric still passes it — the `k + rank*rank` mutation raised
`SourceAffinitySweepTests` to 0.5430 and that gate stayed green on the floor alone. Making the pin
two-sided is the obvious follow-up and is not taken here: it asserts cross-platform bit-stability
of the remaining float path (sqlite-vec distances, bm25) that nobody has measured on a Linux runner
yet.

**Slack that is now visible.** The A6 file-rank bound of 8 in both sweeps was ADR-0015's
cross-platform envelope. The rank is deterministic at 4 now, so four ranks of that bound are dead
weight. Tightening it is a ranking decision left to whoever first confirms the value on Linux; it
was not widened, and the comments say what it is.
