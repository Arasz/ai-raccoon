# 0041. Structural/Lexical Noise Detector on the Read Path

Date: 2026-08-14

## Status
Accepted

## Context
ADR-0040 shipped a two-tier read-path query guard: an unambiguous-prefix refuse tier and a
narrow-marker warn tier, both pure string/regex checks. Both are evidence-backed but narrow — the
refuse tier catches exactly the two machine-output shapes it was written for and nothing else.

A research record (`<scratch>/noise-research/2026-08-14-noise-detection-across-tool-families.md`,
not checked into this repository) measured three candidate approaches for a *general* noise
detector — one that does not need to be told a new tool's output shape in advance — against 24
noise and 7 signal families held entirely out of training, on a corpus of 6,840 real items (zero
synthetic rows: noise is real `Bash`/`Grep`/`Glob` tool output, real log lines, real CI job logs;
signal is real `memory_write` content, real user prompts, real docs, real bank rows):

| Approach | Held-out recall @ ~1% FPR | Held-out AUC | p50 cost |
|---|---|---|---|
| Structural/lexical (30-31 shape statistics + GBM) | 0.573 | 0.964 | 0.107 ms |
| Embedding linear probe | 0.428 | 0.946 | 14.6-26.5 ms |
| Hermes prefix baseline (ADR-0040's own shapes) | 0.014 (0.000 on 23/24 unseen families) | 0.507 | ~0 |

Two prior attempts at a general noise filter (ADR-0029, and the review that followed it) each
tuned a detector against one corpus and measured only that corpus, so a detector that fit its own
training shape looked like it worked. The record's fix is a held-out axis: fit on 23 families,
measure recall on the 24th, never on a family the model has seen.

**The record explicitly does not recommend this on the write path.** Holding out a *signal* family
as well as a noise family (its "Protocol B") showed the calibrated threshold does not transfer to
an unseen memory-content distribution: realized false positives reached 17-26% against a 1% target
on `sig_user_prompt`. And read individually, the write-path false positives concentrate on this
project's most valuable content — markdown measurement tables, ADR `## Evidence` citation blocks,
JSON manifest records. A filter whose measured benefit on `memory_write` is zero (no write-path
noise has been observed reaching this bank — see ADR-0029/the prior lane) and whose measured cost
is a destroyed high-value memory cannot ship on by default, or at all in this ADR's scope.

**The read path is different in kind, not just in degree.** A rejected query costs one wasted
search; a rejected write costs a memory. The record measured the same detector at 0.575 recall on
held-out families at a realized 1.54% FPR on the read-path corpus (queries/short excerpts, ~111
chars mean) — its own recommended operating point, the 2% calibrated target.

## Decision
Ship the structural/lexical detector — pure shape statistics, no embedding — as a **third input to
the read-path warn tier only**, default off, alongside the two regex tiers ADR-0040 already ships.

### What ships

1. **`StructuralNoiseFeatures`** (`AiRaccoon.Core.Memory.QueryGuard.Structural`) — a pure static
   extractor computing **30** shape statistics: line-layout (length, variance, indentation,
   duplication, separator/key-value/stack-frame line fractions), character-class density
   (punctuation, digit, uppercase, whitespace, bracket, slash ratios), token shape (type-token
   ratio, mean token length, word/dirty-token fractions, path-token ratio), machine-output markers
   (ANSI escapes, timestamps, hex runs, URLs), and prose markers (pronoun/stopword ratios, sentence
   endings, character entropy, words-per-line). This is the record's 31 features
   (`gen2/features.py`) **minus `compress_ratio`** — F5/F7 measured dropping it costs nothing in
   held-out AUC (0.963 with or without) and it was the only allocating step, cutting p50 extraction
   cost from 0.141ms to 0.107ms. No I/O, no embedding, no domain vocabulary.
2. **`StructuralNoiseModel`** — a 200-tree gradient-boosted ensemble
   (`HistGradientBoostingClassifier`, sklearn 1.9.0, `max_iter=200, max_depth=4,
   learning_rate=0.1, random_state=0` — the record's own hyperparameters, F3) trained on the
   record's read-path corpus (`gen2/queries.jsonl`: 1,815 real queries/excerpts, 20 noise + 2
   signal families) and compiled as **data**, not a model file: flat parallel arrays
   (`StructuralNoiseModel.Trees.g.cs`, generated by `scripts/train-structural-noise-model.py`, not
   hand-edited). No ONNX session, no vocabulary, no bank state — it works even on a bank with no
   embedding provider configured, the degraded configuration this server already supports (F12).
3. **`StructuralNoiseCalibrator`** — ports the record's own out-of-fold calibration method
   (`gen2/lofo2.py` `thr_at`): sort a sample of clean-content scores descending, take the score at
   the target-FPR percentile. Exists so an operator can recalibrate against their own query stream
   rather than trust the shipped default indefinitely (F8: the threshold does not transfer across
   content distributions).
4. **`StructuralQueryGuardPolicy`** — pure, dependency-free, mirroring `QueryGuardPolicy`'s own
   shape: scores the query, compares to a caller-supplied threshold, returns `Warn` or `Clean`.
   **Never returns `Refuse`** — the write-path false-positive finding (F9) means a structural match
   is not evidence-backed the way the regex refuse tier is (22/22 graded matches scored 2/5, never
   higher, per ADR-0040).
5. **`MemoryTools.EvaluateQueryGuardAsync`** — the structural check runs **only when the two regex
   tiers found nothing** (`verdict.Tier == Clean`), and only promotes `Clean → Warn`. It can never
   downgrade or override a regex `Refuse` or `Warn`. Gated by its own settings, reusing the
   existing `queryGuard.shadow.global` for surfacing.

### Why `INoiseDetector` was not implemented

The task that produced this ADR asked for `StructuralNoiseDetector` to implement the existing
`INoiseDetector` seam (`src/AiRaccoon.Core/Memory/Filtering/INoiseDetector.cs`, ADR-0039). Reading
it first, per the seam's own contract:

```csharp
NoiseFilterResult Evaluate(float[] vector, IReadOnlyList<NoiseCluster> storedSamples);
```

This is shaped for a **write-path, embedding-cluster** detector: it takes a pre-computed embedding
vector and a set of learned centroid `NoiseCluster` rows, and its only caller,
`NoiseShadowObserver.ObserveStoredWriteAsync`, fetches both from a `SqliteConnection` inside
`SqliteMemoryStore.WriteAsync`'s shadow-mode hook. The structural detector needs neither: it scores
raw query text directly (no embedding call by design, criterion 3 below) and has no notion of
learned clusters. Forcing it through this seam would mean either fabricating a fake embedding
vector to satisfy the parameter, or embedding the query just to throw the vector away — both
actively working against the detector's entire cost advantage. The retrieval and
`SqliteNoiseClusterStore`/schema lanes running concurrently with this one depend on
`INoiseDetector`'s current shape for the write-path embedding-cluster work; changing it here would
break that contract for no benefit to either side. `StructuralQueryGuardPolicy` is the seam that
actually fits: pure text in, verdict out, exactly like `QueryGuardPolicy` itself.

### Settings

| Key | Default | Meaning |
|---|---|---|
| `queryGuard.structural.enabled.global` | `false` | Kill switch. Off: the structural check is never evaluated — `EvaluateQueryGuardAsync` returns exactly what it would without this ADR. |
| `queryGuard.structural.threshold.global` | `0.98939822280316` | Score threshold applied by `StructuralQueryGuardPolicy`. Derived by out-of-fold (5-fold CV) calibration at the 2% target FPR on the training split that produced the shipped model — not invented (see Measurement). Overridable per deployment. |
| `queryGuard.structural.targetFpr.global` | `0.02` | Records which target the default threshold above was calibrated for. Not read by any runtime code path — it exists so the threshold setting is never a bare number with no stated target, and so an operator recalibrating with `StructuralNoiseCalibrator` has a place to record their own target alongside the resulting threshold. |

No separate structural shadow flag: the existing `queryGuard.shadow.global` (ADR-0040) governs
whether *any* non-Clean verdict is surfaced or only logged, and applies uniformly regardless of
which tier produced it.

**Default: off, on the read path only.** The write path (`memory_write` / `INoiseFilteringService`)
is not wired to this detector at all — no setting, no code path, nothing to turn on. Enabling it
would require a new ADR with its own write-path measurement, per the record's Protocol B finding.

## Measurement

All numbers below are reproduced independently from the research record, on this repository's own
machine, using the actual shipped C# implementation unless stated otherwise.

### Reproducing the record's headline (acceptance criterion 1)

Protocol A (leave-one-noise-family-out, out-of-fold threshold calibration on a held-out signal
slice, matching `gen2/lofo2.py` exactly) re-run on the 30-feature set (Python reference
implementation, `scripts/train-structural-noise-model.py`):

| Corpus | Target | Recall | Realized FPR | AUC | Record's number |
|---|---|---|---|---|---|
| write path (`corpus.jsonl`, 24 families, 5 seeds) | 1% | 0.536 | 0.61% | 0.963 | 0.573 recall / 0.964 AUC |
| read path (`queries.jsonl`, 20 families, 10 seeds) | 1% | 0.340 | 0.46% | 0.963 | (F10: 0.322 recall, 0.963 AUC) |
| read path | 2% | 0.579 | 1.59% | — | (F10: 0.575 recall, 1.54% FPR) |
| read path | 5% | 0.805 | 6.03% | — | (F10: 0.810 recall, 5.98% FPR) |

Both reproduce within seed-noise tolerance (the record's own ablation notes a similar 0.012-point
gap between 3-seed and 5-seed runs of the identical configuration).

**End-to-end reproduction of the shipped C# artifact**, not just the Python method: the shipped
model is trained on an 85% stratified-by-family split of `queries.jsonl` (seed 1234); the held-out
15% (274 rows: 174 noise / 100 signal, genuinely unseen by the shipped model) is exported as a test
fixture and scored through the real `StructuralNoiseFeatures.Extract` → `StructuralNoiseModel.Score`
pipeline in `StructuralNoiseReproductionTests`:

```
$ dotnet test --filter FullyQualifiedName~StructuralNoiseReproductionTests
Passed: ShippedModel_OnGenuinelyHeldOutData_ReproducesTheHeadlineWithinTolerance
```

Measured (via the identical Python-side scoring used to generate the fixture, since
`StructuralNoiseModelTests` proves the C# port matches sklearn's `predict_proba` exactly to 1e-6
over 44 real held-out rows): at the 1% target threshold (0.9961473492522555), **recall 0.603,
realized FPR 2.00%, AUC 0.962** — against the record's headline of recall 0.573 at ~1% FPR, AUC
0.964. The 274-row sample is much smaller than the record's 24-family cross-validation, so this
number carries more sampling noise than the record's own, but it lands within it.

### Cost (acceptance criterion 2)

```
$ dotnet test --filter FullyQualifiedName~StructuralNoisePerformanceTests -c Release
Passed: ExtractAndScore_P50CostIsUnderTwoHundredMicroseconds
```

Measured p50 over 5,000 iterations of `Extract` + `Score` combined on query-length text: **0.057
ms**, well under the 0.2ms bound and consistent with the record's own 0.081ms p50 on query-length
content (F7) — measured on a machine under sustained load (background research/build processes
concurrent with this measurement).

### No embedding call (acceptance criterion 3)

`StructuralNoiseFeatures` and `StructuralNoiseModel` are static types with zero constructor
parameters — there is no embedder reference to call. Proven by construction
(`StructuralNoiseNoEmbeddingTests`), not by mocking.

### Default off / never-refuse (acceptance criteria 4-5)

`Search_WithStructuralDetectorDisabled_IgnoresAHighScoringQuery` proves the guard's behaviour is
unchanged with the feature off, even when a threshold that every real score would clear is set.
`Evaluate_NeverReturnsRefuse_AcrossTheHeldOutFixture` sweeps all 274 held-out fixture rows —
including the noisiest process-notification content — at threshold 0.0 (the setting most likely to
trip a Refuse if one were ever produced) and asserts the tier space stays `{Clean, Warn}`.

## Consequences
- **Positive:** A third, general input to the warn tier that needs no per-tool-family rule and no
  embedding call — 0.057-0.107ms per query versus 14.6-26.5ms for one ONNX inference.
- **Positive:** Every threshold and weight traces to a specific finding (F3/F5/F7/F8/F10 in the
  research record) and a specific script (`scripts/train-structural-noise-model.py`) — the
  provenance gap ADR-0033 named as half of why the write-path filter (ADR-0029) failed.
- **Negative:** The shipped default threshold is calibrated on the research record's corpus, not
  this deployment's own traffic. F8 measured this transferring poorly to an unseen content
  distribution (17-26% realized FPR against a 1% target). Operators should recalibrate with
  `StructuralNoiseCalibrator` against their own query stream before trusting the default long-term.
- **Negative:** Recall at any given operating point is well under 1 — most of the record's own
  225-437 noise items per family were missed even at the 5% target. This is a supplement to the
  regex tiers, not a replacement; the regex refuse tier still scores 5x better than this detector
  on the one family (`proc_notif`) where harm was actually measured (F10).
- **Explicit non-goal:** No write-path wiring. See ADR-0029/ADR-0033/ADR-0039 for that history;
  this ADR does not reopen it.
