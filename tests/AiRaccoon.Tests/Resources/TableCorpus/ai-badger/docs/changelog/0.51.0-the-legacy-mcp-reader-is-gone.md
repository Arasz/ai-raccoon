# 0.51.0 — MCP rebuild step 8 of 8: the legacy MCP reader is gone

Step 8, the last, of the MCP rebuild
[ADR-0014](../adr/0014-mcp-support-is-configuration-not-retrieval.md) describes. Step 4 deleted
`features/common/mcp-servers.json` and `features/common/external-tools.json` and left both
readers standing "for one more release". That release is over. **The ADR-0014 migration is
complete: `features/<stack>/stack-mcp.json` is the only file that declares an MCP server.**

## Removed

| removed | what replaces it |
|---|---|
| `McpTools.collect_stack_mcp_servers` | `collect_catalog_mcp_servers` — same merge (common first, then `config.stacks` order, last writer wins on name), reading `stack-mcp.json` |
| `McpTools.collect_external_tools`, `fill_merged_external_tools` | nothing: `external-tools.json`'s `instructions` are `features/<stack>/mcp/<server>/server.md`, its `package` is `meta.json`, its `generate_mcp_json` is `declare` |
| `McpTools.merge_mcp_servers` | `declared_servers()`, now a one-reader dict comprehension over `declare: true` |
| `McpTools.fill_instruction_sources` | `fill_mcp_described()` — there is one instruction source left, so the wrapper had nothing to wrap |
| `ScaffoldContext.merged_external_tools`, `.external_tools_merged` | `ScaffoldContext.mcp_described`, already the catalog's side of the same channel |
| `{{EXTERNAL_MCP_INSTRUCTIONS}}` in `CLAUDE.md.tmpl` and `HERMES.md.tmpl` | `{{MCP_INSTRUCTIONS}}`, which now stands alone on the line |
| `schemas/mcp-servers.schema.json` + its `validate.py --all` row | `schemas/stack-mcp.schema.json`, which inherits `scope`, `env` and `agentOverrides` |
| the `mcp-servers` row in `docs/authoring-a-feature.md` | a paragraph naming both retired files and the note a stack shipping one now gets |

## A retired file is named, not ignored

A stack that still ships `mcp-servers.json` or `external-tools.json` — none in this framework,
but a consumer overlay could — gets a scaffold note and no declaration:

```
features/python/mcp-servers.json is no longer read (ADR-0014 step 8) — move the servers it
declared into features/python/stack-mcp.json, where 'declare: true' is what writes a launch
config now
```

Presence is the whole test: the file is never parsed again, so an unparseable one is reported
just the same. The note fires once per run however many times `declared_servers()` is read, and
never for a stack that ships neither file. Silently ignoring a file whose servers stopped being
declared is the failure mode this repository keeps rediscovering; naming it is the house style.

**If you maintain a stale overlay:** move each server into that stack's `stack-mcp.json`, adding
`"declare": true` to the ones whose launch config ai-badger should write (`generate_mcp_json`
became `declare`, and its default flipped to `false`); move any `instructions` blob into
`features/<stack>/mcp/<server>/server.md` beside a `meta.json`, or nothing injects it. Then
delete the retired file.

## Rendered output does not move

Re-scaffolding this repository against itself twice: `CLAUDE.md`, `HERMES.md`,
`.github/copilot-instructions.md`, `.ai-badger/CLAUDE.md`, `.ai-badger/HERMES.md`, `.mcp.json`
and `.github/mcp.json` are byte-identical to their pre-change contents and to each other across
the two runs. Only `.ai-badger/manifest.json` moves, and only where it records the hash of a
*source template* that lost the slot — the rendered targets it points at are unchanged.

That the slot's removal is free is not luck: it rendered `''` for every input in this repository
and sat immediately after `{{MCP_INSTRUCTIONS}}` on the same line, which is what step 2 arranged
it for. `GOLDEN_MCP_REGION` in `tests/test_mcp_catalog_instructions.py` pins the bytes.

## What this does not do

`config.exclude.mcp` still does not exist — `mcp` is not a name-addressable feature type — so
declining a catalog-declared server is `config.mcp.decline`'s job and nothing else's. That is
unchanged by this step, and so is the gap 0.51.0's step 4 filed.
